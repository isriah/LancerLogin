Privacy boundaries

Stored by your installation

  • Organization configuration, users, roster, meetings, attendance, corrections, and audit records in your D1 database
  • Encrypted integration credentials in D1; saved values are never displayed
  • Sensor slot-to-member mapping, queued events, and pairing material locally on the Pi
  • Fingerprint templates exclusively inside the R503 sensor

Never sent in anonymous usage reports

  • Organization name
  • Roster or personal names
  • Attendance records
  • Fingerprint templates or raw scans
  • Raw IP address

Anonymous usage reporting

Anonymous usage reporting is enabled by default on the first-Admin form and can be unchecked to opt out before setup completes. When enabled, LancerLogin may send a random installation ID, release version, active kiosk count, scrubbed error category, and best-effort city/metro derived from the connection. Raw IP is not read into the payload or stored. An Admin can turn reporting off later, which clears the anonymous installation ID.

RoboLancers operates the isolated community collector. It hashes the random ID before storage, keeps at most one report per installation per UTC day, and deletes reports after 30 days. Only designated maintainers can access authenticated aggregates, which never expose installation references or hashes. Metro groups smaller than five installations stay hidden.

Deletion and incident contact

While anonymous usage reporting is enabled, an Admin can copy the deletion-request reference shown in Setup → Anonymous usage reporting and email it to robolancers@gmail.com. Maintainers verify the request and use the authenticated deletion route to remove matching reports and the pseudonymous installation row. Request deletion before turning reporting off if you want retained reports removed.

Send suspected reporting privacy or security incidents to the same address. RoboLancers will investigate, contain or disable the collector where needed, and publish a plain-language repository notice for incidents that could materially affect community installations. Support is best-effort without an SLA.

Data remains in the adopter-owned installation until an Admin deletes it. Exporting creates a copy and does not remove the stored records. LancerLogin provides no migration path from earlier installations.
