# Pinned application-schema recovery experiment (WU-113)

This P0 experiment extends the disposable recovery proof to the application schema from migrations **0001-0038**, without changing the application database, production or Pi. It is not the final P6 updater or an application backup/restore implementation. Later migrations are intentionally outside this pinned experiment. The maintainer alone performs hosted stages on the already approved `lancerlogin-v2-example-recovery-test` in `example/LancerLogin`.

## Data and boundaries

The model runs all 38 hash-pinned migration files locally, creating 56 application tables and 16 triggers. Entirely synthetic records include attendance, one member with a zero-prefixed external ID, an Admin with **no password hash or email**, hour settings/category/activity, a public original receipt, reasoned correction and terminal void with immutable history/resolutions, and two counted entries. Domain services generate the hour graph. IDs and clocks are deterministic. No live application backup, user, provider token, encrypted connection or usable credential is copied. New synthetic rows cover public-admission counters, Drive feasibility configuration/Picker/proof state, a Discord correction draft, opaque unusable provider connection cells, and Google/Discord event publication intents, ownership generations and processing operations. This is valid domain/schema data, deliberately not a usable signed-in installation.

The existing `recovery_fixture` and `recovery_job` tables must retain their exact original two rows and idle checkpoint-two failed-migration state. The new runner cannot create/delete databases, choose arbitrary tables, accept SQL paths, or operate on an application/updater database. Before every stage it checks explicit repository/account/UUID arguments, the existing private recovery identity, credential account, and the provider's current exact name/UUID/account. CLI origin must match the approved private repository. SQLite internals and the evidenced D1 `_cf_KV`/`_cf_METADATA` system tables are excluded and never modified. Unknown application schema objects, row differences, busy fixture state, migration changes, artifact tampering or mismatched approval stop execution.

Each mutation needs the SHA-256 manifest approval printed by prepare. The manifest includes identity, migration hashes, pinned Wrangler protocol version, expected application graph, fixture digest and initialization digest. Artifacts/checkpoints use exclusive creation or atomic replacement in Git-ignored `.provision/application-recovery-spike/`. Do not edit/delete checkpoints to force a retry. Run one operator with exclusive access; this local checkpoint is not a distributed lock, and concurrent external activity invalidates attribution.

## Export and canonical restore

Wrangler **4.127.1** implements table-filtered export as `dump_options.tables` and import using `init`/MD5 ETag, presigned PUT with matching ETag, `ingest`, then bookmark polling. The runner implements this [official export](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/) and [official import](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/import/) protocol directly. This avoids Wrangler's unconditional signed-export-URL debug logging. Only authenticated provider-returned HTTPS R2 storage URLs are used, without bearer headers or redirects. Signed URLs exist only in memory; they never enter logs, errors or checkpoints. API/output bodies and SQL artifacts are bounded to 1 MiB; requests have 30-second limits, polling has at most 30 requests and a 120-second monotonic budget. Including transfer/init, export is bounded to 150 seconds and import to 180 seconds. There are no background CLI retries; already submitted provider operations may continue after exit.

Export includes only the explicit 56-table application allowlist, preserving the separate fixed recovery tables. The **original dump is not assumed directly restorable**. Pinned local D1 emits table/data blocks in alphabetical order regardless of requested table order, so a foreign-key child may precede its parent. Its table-filtered export also omits index/trigger definitions; the earlier schema 1-34 local export was 45,503 bytes and required reconstructing 36 such definitions (28 indexes and eight triggers). An original-byte replay therefore fails locally with a missing referenced table/foreign-key error.

Validation uses the pinned Wrangler SQL splitter and an in-memory SQLite authorizer, not a homemade SQL parser. Parsing disables FK enforcement solely to read the unordered export; filesystem attachment, extensions, virtual tables, views, foreign objects, arbitrary functions and data-changing operations other than expected inserts are denied. All table definitions, columns and rows must exactly match the synthetic model. Only `CREATE ... IF NOT EXISTS` is normalized in parsed schema metadata. Missing **indexes/triggers only** are reconstructed from the pinned migration model; altered or additional definitions are rejected. Full foreign-key and graph checks then run. This parser mode is validation, not evidence of D1 restore success.

A distinct canonical artifact uses table definitions, indexes, validated data from that **one exported snapshot**, then triggers. It never combines two separately timed exports. Cleanup drops only expected application triggers/tables, in reverse foreign-key dependency order; it never drops the fixed recovery tables. Original export and canonical import have separate SHA-256 digests. This is a deliberately narrow known-schema/synthetic reconstruction, not a general SQL importer. The original eight rejection behaviors remain tested after replay: overlap INSERT/UPDATE, immutable revision/receipt, terminal void, activity-date history, and immutable request/resolution. Before/after complete schema/data and fixed-fixture digests are also compared.

## Coordinator stages

Use the integrated checkout with locked dependencies and Node 24. Set `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` securely; never put the token on the command line. The existing `.provision/recovery-spike/identity.json` must be present. The maintainer takes a fresh independent snapshot before external writes. No stage below has been executed against Cloudflare by the implementation agent.

All commands use this suffix (replace only the approved identities):

```text
--repository example/LancerLogin --expected-account ACCOUNT_ID --expected-database DISPOSABLE_DATABASE_ID
```

1. `node scripts/application-recovery-spike.mjs prepare` plus suffix: read-only remote preflight, local deterministic model and private manifest. Requires only the original fixed fixture remotely. Review returned `manifestDigest` and the pinned scope.
2. `initialize` plus suffix and `--approve-manifest MANIFEST_SHA256`: intent before import, create synthetic application schema/data alongside fixed fixtures, read back exact graph.
3. `export` with the same approval: record intent, export one table-filtered snapshot, validate, record original digest/bytes and reconstructed object names, and read back unchanged remote baseline.
4. `damage` with approval: verify export, record intent, change only the synthetic organization label and verify exact expected damage.
5. `restore` with approval: validate the original export again, generate/hash canonical import, record intent before provider import, and verify complete baseline plus unchanged fixed fixtures.
6. `verify` with approval: record probe intent, require all nine known trigger errors from actual provider responses, then verify the entire baseline and fixtures. Completion can be rechecked without repeating probes.
7. `status` plus suffix: read-only current baseline/damage/fixture comparison and durable phase.

An ambiguous initialize/restore invocation never repeats init, upload or ingest. WU-116 requires a recorded successful provider completion or a validated saved operation bookmark; only that bookmark may be polled before checking the exact expected graph. Legacy pending imports without a transport checkpoint remain blocked even if rows appear complete. Damage alone can still reconcile its exact expected state. Successful reconciliation is labeled `reconciled:true`; it is not proof of provider atomicity. A saved export can be reconciled from its validated bytes; absent artifacts, partial schema/data or incomplete probe evidence stop for maintainer review. Provider failure can leave destructive import partially applied; do not claim rollback unless separately observed. The old fixed fixture must still verify after every successful stage.

## WU-116 import transport checkpoints

Dependencies: WU-113 pinned experiment and the maintainer's observation of an interrupted initial import. That observed failure does not establish its cause. A strict local request-union mock reproduces the old polling body mismatch: pinned Wrangler sends only `action` and `current_bookmark` for an import poll, while the earlier helper retained ingest-only `filename` and `etag`. WU-116 now uses the exact union. Successful nonterminal responses may omit `status` as documented, but require a valid `at_bookmark`; explicit `active` remains supported. Unknown status values are rejected. Every ingest/poll/already-uploaded result must have inner `success:true` before completion is accepted; an initial upload ticket is validated separately.

The existing state file gains an internal `transport` record, bound to operation (`initialize` or `restore`) and the exact input SHA-256. It contains version1, a fixed substage, a bounded opaque bookmark or null, and optionally a fixed diagnostic category/HTTP status. It never contains signed URLs, filenames, ETags, SQL, credentials or provider messages. Checkpoint writes flush the new file before atomic replacement, and are awaited before provider dispatch. This is process-interruption protection, not a demonstrated power-loss or distributed-lock guarantee.

Substages: `init-dispatched`, `upload-ready`, `upload-dispatched`, `upload-complete`, `ingest-dispatched`, `poll-ready`, `poll-dispatched`, `complete`, and `terminal-failure`. A polling response's bookmark is saved before the next poll. The upload URL remains only in memory; a lost upload session cannot be reconstructed from checkpoints.

Resume behavior:

- `poll-ready` or `poll-dispatched` with a valid bookmark: issue only bounded polling for that recorded operation, save updated bookmarks/completion, then verify the full synthetic application graph and original fixture.
- `complete`: do no import call; verify the exact graph before advancing.
- Missing/legacy checkpoint, absent/malformed bookmark, terminal failure, or interrupted init/upload/ingest without a recorded operation: stop without reissuing anything. This deliberately also holds provably pre-ingest states for maintainer review; it provides no reset/retry command.
- `status` exposes only the phase, fixed substage and bookmark-presence boolean, plus existing graph/fixture booleans. A completely absent application schema can be inspected for pending initialization. Partial/unknown schema still fails closed.

The observed legacy `initialize-pending` record cannot be unblocked by this implementation. Preserve it. An empty database snapshot alone does not prove that a dispatched import will not finish later. The maintainer must independently establish provider operation state; any later recovery transition needs a separate reviewed procedure. Never delete or edit pending checkpoints to force a new import.

Diagnostic output uses fixed categories (`provider_transport`, `provider_http`, `provider_envelope`, `provider_inner_failure`, `provider_shape`, `storage_url`, `storage_upload`, `storage_etag`, `poll_limit`, `checkpoint_required`) and optional numeric HTTP status. It omits provider messages, URLs and bookmark values. A failure to save a checkpoint blocks the following dispatch. Local tests cover active ingest/exact polling, lost poll response/resume, no-bookmark ambiguity, failed inner results, sanitized errors and unchanged canonical recovery. No hosted retry or resource mutation was performed by WU-116.

## WU-119 storage transport diagnosis

Dependencies: WU-116 dispatch checkpoints and WU-117's supported Node recovery runtime. A storage upload throwing before an HTTP response now adds only `transportCause`: `dns`, `tls`, `socket`, `timeout`, `aborted`, `request_construction`, or `unknown`. Classification compares a fixed allowlist of Node/Undici error codes and timeout/abort names across at most eight error objects, including nested causes and bounded aggregate children. It never reads stacks, URLs, headers or socket metadata; the exact-literal exception below applies only to the invalid-argument code. The original exception is not attached to the sanitized error. Existing records without this optional field remain valid.

These categories describe the error signal, not a proven operational cause or retry authorization. Unrecognized codes and cycles remain `unknown`; only the explicit construction-code allowlist below may be emitted. The upload checkpoint still has no bookmark and cannot resume or dispatch init/upload/ingest again. Source references: [Node system/TLS errors](https://nodejs.org/api/errors.html) and [Undici error definitions](https://github.com/nodejs/undici/blob/main/lib/core/errors.js).

Local coverage exercises nested synthetic causes, cycles, an unreadable property, category persistence through the stage validator, blocked second attempts, and Node's actual Request construction with the existing Buffer/content-length options. No deterministic request-construction defect was established. The native Request probe does not exercise DNS, TLS, socket delivery or hosted R2, and the prior upload failure cannot be retroactively classified. No existing private checkpoint was changed and no hosted attempt was made by this unit.

A WU-119 follow-up adds `constructionCode` only for the five approved request-construction codes: `ERR_INVALID_URL`, `ERR_INVALID_ARG_TYPE`, `ERR_INVALID_ARG_VALUE`, `UND_ERR_INVALID_ARG`, and `UND_ERR_REQ_CONTENT_LENGTH_MISMATCH`. Other raw codes remain suppressed. The checkpoint validator requires this field to agree with `request_construction`. This diagnoses a future authorized attempt; it cannot recover the missing code from a prior checkpoint.

A native Node 24.14.1 loopback HTTP test successfully uploaded the exact Buffer, UTF-8 byte length and headers through production upload handling. An intentionally malformed content-length produced a real nested `UND_ERR_INVALID_ARG`, which was sanitized and checkpointed without dispatching ingest. All five construction codes have synthetic privacy cases. This establishes the diagnostic path and local Buffer compatibility, not the cause of the hosted R2 failure; no transport workaround is applied.

A further WU-119 diagnostic adds optional `constructionReason` only with `UND_ERR_INVALID_ARG`. It compares cause messages against exact static literals from Node 24.14.1 / bundled Undici 7.24.4, then retains only an enum: `duplicate_content_length`, `invalid_content_length`, `invalid_path`, `unsupported_body`, `proxy_configuration`, `proxy_tunnel`, or `unknown`. Unrecognized text, objects, and throwing message getters yield `unknown`; no raw message is attached, logged, or checkpointed. Other codes never inspect messages. The bounded cause traversal and fail-closed checkpoint rules remain unchanged. These categories are diagnostic clues, not proof that a request was or was not sent, and never authorize retry or import replay. Existing records without the optional field remain valid.

The separately reconciled hosted attempt 5 reported `invalid_content_length` at upload dispatch, before ingest. The next candidate removes the manually supplied Content-Length header for bounded Buffer uploads and lets native fetch derive it. Local loopback coverage uses the actual generated synthetic model SQL (51,379 bytes in the Windows observation; line endings may differ on Linux) with URL-object and string destinations carrying a synthetic signed-query shape. It checks exact received bytes/digest and Content-Length against that generated payload, no chunked encoding, and no Authorization or Cookie header. ETag validation, bounds, checkpoints, and fail-closed retry rules remain unchanged. This local evidence does not establish successful hosted upload; a separately reviewed development drill is still required.

Inner import rejections now retain `rejectedAt` (`init-dispatched`, `ingest-dispatched`, or `poll-dispatched`) plus `successState` (`true`, `false`, `missing`, `invalid`) and `statusState` (`complete`, `active`, `error`, `missing`, `unknown`). These fixed shape fields are saved atomically with the first terminal-failure checkpoint, so overwriting the stage does not erase its origin. No provider error text or unknown status value is retained. Old diagnostic-free records remain valid; partial or unrecognized diagnostic fields fail closed. The fields diagnose subsequent authorized execution only and cannot reconstruct attempt 6 or authorize replay. A private append-only journal may additionally record the same sanitized checkpoint objects through the existing save callback; it must be flushed before returning and must never capture raw provider responses.

Canonical SQL now requires the complete reviewed foreign-key dependency order from `tableOrder`, and emits both table definitions and table rows in that order. Triggers remain after row loading; all indexes, schema definitions and canonical rows are preserved. The previous alphabetical row order fails with a foreign-key constraint when statements commit individually; dependency ordering passes initialization and cleanup/restore under that same boundary with foreign keys enabled, original fixtures retained and operational triggers verified. The local D1 test now uses individual statement execution for both paths as well. This removes reliance on one large deferred-constraint batch. It changes payload and manifest digests; old private attempts must remain unchanged. Hosted SQL failure attribution and successful revised import remain unproven until a separately reviewed drill.

## WU-133: schema 38 synthetic recovery extension

The new model adds migrations 0035-0038 to the existing pinned migration list and includes each file's exact byte hash in its new manifest. Dependency-ordered canonical SQL, the bounded SQLite authorizer, complete row/schema comparison and original recovery-fixture preservation remain unchanged. The canonical `hours_publication_restore_guard` table is empty: it is a transaction-scoped assertion, not durable backup data. The new single-statement operational rejection probe proves that an uncertain dispatched publication blocks installation deletion without leaving assertion rows.

Raw SQL recovery deliberately drops application triggers before rebuilding the exact schema and snapshot. It therefore preserves admission counters, Picker/proof/draft state, publication leases, phases and ownership unchanged; it does **not** run the API logical-backup publication normalization or its installation-deletion guards. The synthetic expired lease and uncertain Discord create remain unchanged after raw replay. By contrast, `preparePublicationRestore` validates publication ownership and marks enabled intents for review, clears leases and marks incomplete operations for review. Local tests exercise that normalization on a copy and prove it does not mutate the recovered raw snapshot. This distinction must remain explicit in P6 recovery design before application backups can use raw recovery safely.

Post-replay Node SQLite and local D1 checks exercise activity revision/archive, module pause, provider pause and credential-generation rotation triggers. Local atomic failing batches test missing ownership, loss of a known provider event ID and matching ownership (with a forced final CHECK failure), rolling back every mutation and assertion row. Existing `tests/hours-publication-d1.test.mjs` remains the broader API logical restore/claim-race evidence; this extension does not duplicate its scheduler integration suite.

The successful hosted result recorded above remains **schema 1-34 only**. Schema 1-38 verification here is local synthetic SQLite/Miniflare D1 evidence, not hosted recovery, restoration of a private application backup, external provider asset recovery, usable credential recovery or the full updater. A future hosted drill needs a fresh manifest/checkpoint after the maintainer verifies exact disposable state and import inactivity; old attempts and their digests must not be rewritten.

Focused candidate verification: `node --test tests/application-recovery-spike.test.mjs` passed all 24 checks on Node 24.14.1. The schema 38 local D1 export was 57,049 bytes and reconstructed 48 pinned definitions (32 indexes and 16 triggers). Byte lengths are observations for this checkout, not cross-platform constants; manifest hashes retain exact source bytes.
