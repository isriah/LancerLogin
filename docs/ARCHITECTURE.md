# Architecture

## Components

```text
Admin browser ── Pages dashboard + /api proxy ── Worker API ── D1
                                                    │   │
                                                    │   └─ encrypted integration credentials
                                                    └──── Resend / Discord / Google OAuth / Google Calendar

Raspberry Pi kiosks ── local identity adapters ── R503, keyboard-wedge reader, or touch entry
       │                       │
       └── pairing code / HTTPS┴── Worker API

Web kiosks (browser, /kiosk on the Pages origin) ── touch entry: member ID, member search, PIN, Discord code
       │
       └── pairing code / same-origin /api proxy ── Worker API
```

The dashboard is a static Pages application with an advanced-mode `_worker.js` proxy for `/api/*`. Browser sessions therefore remain first-party on the adopter's Pages origin while API work is forwarded to the separate Worker through a Pages service binding named `API`, which keeps each visitor's network address for per-client limits. The Worker owns authorization, onboarding state, non-overlapping meeting-window validation, scan-time meeting resolution, data validation, encrypted secret handling, exports, and integration calls. Optional Google Calendar and Discord scheduled-event delivery each keep installation-scoped meeting mappings and durable retry operations in D1. Discord label role associations and manual full-server sync jobs are installation-scoped D1 state. Google Calendar keeps separate encrypted authorization and meeting titles, notes and times; Discord keeps its verified bot configuration and provider-specific event fields. LancerLogin remains authoritative and never imports provider changes. D1 contains organization-level data and, with optional cloud storage enabled, durable server-encrypted vault copies. Historical peer-encrypted deliveries and public identities may remain after peer sharing is retired. D1 stores no plaintext templates, raw fingerprint images, or raw badge and QR credentials. The Worker can decrypt the optional vault, but not peer-encrypted messages. Each Pi service owns its device's identity I/O, owner-only local pairing material, local identity mappings and active-roster cache, offline scan queue, kiosk display state, and PIN-protected local network and authentication tools. A web kiosk is the dashboard's `/kiosk` page running in a browser: it holds its kiosk credential, last configuration, active-roster cache and offline scan queue in that browser's IndexedDB, has no reader, and talks to the Worker through the same Pages proxy as the dashboard. The optional FIRST connection keeps encrypted Events API credentials and cached team answers in D1 and sends FIRST only team numbers.

The kiosk normalizes every supported method to one member identity before it enters the existing debounce, pairing capture, offline queue, Worker attendance resolution, and Welcome or Goodbye feedback path. Fingerprint is the default for newly paired kiosks. Migration 0073 preserves each existing kiosk's effective installation-configured method in its own configured field. The historical global field remains for older backup compatibility and cannot override per-kiosk choices. The dashboard stores each kiosk's configured method while each kiosk heartbeat reports the method actually applied, so a disconnected kiosk is shown as pending rather than relabeled from stale health data.

Modules contribute Worker routes, dashboard pages, settings, setup steps, jobs and tables to this structure. Attendance is a first-party module; plugins are composed into the dashboard and Worker at build time. See [module authoring](MODULE-AUTHORING.md) and [module plugins](MODULE-PLUGINS.md).

Each installation has its own D1 database. The Worker has no repository layer: route handlers and their helper files in `apps/api/src` write SQL with `db.prepare(...)` and send related statements in one `db.batch(...)`. Tables carry an `installation_id` column, and the statements name the one installation, `'primary'`, directly.

Every request enters `worker.fetch` in `apps/api/src/index.ts`. A path that a module declares in its `apiRoutes` first passes that module's check: a workspace route needs the module enabled and a signed-in Admin or Operator, a setup route needs an Admin, and a service route needs the module enabled, has no session and authenticates another way. The request then goes through one chain of path and method tests. Each branch that needs a session calls `requireRole`, which reads the signed-in user's current role from D1 and answers 403 for any other role; a branch without that call is not protected. Kiosk routes check the kiosk's credential with `kioskFor` instead. Health, CORS preflight, sign-in, first-time setup and kiosk pairing need no session.

Eight `.mjs` files in `apps/api/src` (`worker.mjs`, `d1-repository.mjs`, `security.mjs`, `attendance-service.mjs`, `pairing-service.mjs`, `roster-import.mjs`, `integration-workflows.mjs` and `test-harness.mjs`) are an early prototype with persistence adapters and a role capability map. Only tests import them; the Worker does not use them. [CONTRIBUTING.md](../CONTRIBUTING.md) has a file map and checklists for common changes.

## Background scheduler

Provider delivery (Google Calendar, Discord events, notices, channel status and label roles, plugin jobs such as Outreach publication and Guest Visits notifications) and installation housekeeping run as scheduler jobs, sized for one installation on the Cloudflare Workers Free plan: 10 ms of CPU per request or cron trigger and 50 subrequests per invocation. Cloudflare's limits pages count a D1 query (a batch is one) and an outbound request as subrequests alike, and list 50 D1 queries per invocation separately; they do not say whether the two share one counter, or how either applies to a Durable Object alarm. The scheduler budgets for the stricter reading everywhere: one limit of 50 for D1 queries and provider requests together, in a cron invocation and in an alarm invocation.

- **Slices.** Each invocation runs one *slice*: one batched D1 read (maintenance, runnable modules, scheduler state), one job's small batch, and one small state write with the outcome (the cron fallback also writes a "running" state first, which is its claim on the jobs). A slice's budget is 40 subrequests in all, D1 queries and provider requests together, with at most 30 D1 queries and 12 provider requests and 2 of the 40 kept for the closing write. A job that stops at its batch size or budget with work left reports more work.
- **The budget is enforced.** Every job checks the budget before work that costs subrequests, from its own estimate of that work. The budget also refuses, before it is sent, any query or request that would pass the limit less the closing reserve, so a job whose estimate was too low is stopped by the scheduler (recorded as failed, retried after its interval) rather than by the platform failing the invocation, and the closing state write always fits.
- **Steps and per-slice cost.** On Cloudflare a slice's CPU is mostly per call: measured on dev, about 1.5 ms plus 0.45 ms per D1 query and 1.5 ms per provider request, and 3-5 ms more for the first slice after the object wakes. A job with several kinds of work does one step per slice and names the next step as a `cursor` the scheduler hands back a second later: housekeeping (reconcile, prune, cleanup) and the Discord channel manager (kiosk status, help message) work this way. The object records the running job in its own storage rather than with a D1 write. A slice the platform stopped once, as a deploy or an eviction resetting the object does, simply runs its job again; a job whose slice is stopped twice in a row is marked failed and the next slice moves on. `tests-ts/scheduler-slice-cpu.test.ts` holds every Core slice to an estimated 7 ms.
- **Durable Object alarm.** With the `PLATFORM_SCHEDULER` Durable Object bound (a SQLite-backed class, available on Free), its alarm runs one slice per invocation and re-arms itself about a second later while work remains, otherwise when the next job falls due (at most five minutes). Writes that queue work, such as meeting saves and imports, label applies and plugin writes, poke the alarm so the work goes out within seconds; previews and dry runs on the same routes (the meeting impact check, a dry-run import, label and Discord role previews) queue nothing and do not poke. Continuations beyond 10,000 a day slow to one a minute, so a stuck job cannot use up the daily Durable Object request allowance.
- **Cron watchdog.** The 5-minute cron then only re-arms a missing alarm; it does no job work. Opening scheduler status does the same.
- **Cron fallback.** A deployment without the binding (or with `PLATFORM_SCHEDULER_MODE` set to `cron`) runs each due job's slice from the cron instead, once per tick within one pass of 46 subrequests in all (2 of them kept for the closing write). That keeps existing deployments working, but a full pass can exceed Free's 10 ms CPU, so Free installations need the Durable Object.
- **One runner.** Exactly one of the two runs jobs, and both decide which from the same setting. With `PLATFORM_SCHEDULER_MODE` set to `cron` and the object bound, the object runs no slice and keeps no alarm: an alarm armed before the switch stands down when it fires, and each cron tick first asks the object to stand down, which also waits for a slice still in flight (that request is the cron invocation's 47th subrequest at most). The cron pass's "running" write succeeds only if nobody has written the state since the pass read it, so a second delivery of one tick runs no jobs.
- **Failures back off.** A slice that throws is retried after 30 seconds, then 1, 2 and 4 minutes, then every 5 minutes until one succeeds. A slice that cannot read the scheduler state keeps none: it runs every due job once, as a cron pass does, and sleeps five minutes whatever the jobs report, since without state a job's request for another slice could never be recorded as served.
- **Calendar queue.** Meeting routes never call Google Calendar or Discord. Each appends set-based statements to the batch that changes the meetings (`apps/api/src/calendar-queue.ts`), so a request costs the same handful of D1 queries for one meeting or a 500-occurrence series, with or without integrations, and the change and its queued operations commit together. The two calendar jobs read their due operations through partial indexes (an operation is due once its `next_attempt_at` has passed) and deliver five Google or three Discord operations a slice. Work due at once goes deletes first, then by meeting start; retries follow. Housekeeping removes delivered operations after 30 days. Migration `0103_calendar_queue.sql` must be applied before this Worker runs: meeting saves, both calendar jobs and the integration cards read what it adds, and nothing falls back to the older schema. The update flow already applies migrations first, under maintenance. `tests-ts/calendar-queue.test.ts` holds each route to its subrequest count.
- **Backups and restores in parts.** A multi-season backup costs several times Free's 10 ms of CPU to read or write in one request, so the dashboard moves it in parts of about 64 KiB (`apps/api/src/data-transfer.ts`, `apps/dashboard/src/backup-transfer.ts`). A backup is copied into staged parts by one batch, so it is still one snapshot; a restore's parts are checked and staged as they arrive, and one final batch replaces the live rows from them inside D1, so a restore that stops early changes nothing. Migration `0105_data_transfer_staging.sql` must be applied before this Worker runs. See [backup and restore](BACKUP-RESTORE.md#backups-and-restores-in-parts).
- **State.** Job state and an Admin's Stop live in D1 (`platform_scheduler_state`), so status and Stop work the same on both kinds of deployment. A runner writes only the jobs it ran, each set in place, so two writers never put back each other's jobs. Stop pauses all outbound delivery, first attempts included, for 24 hours, then delivery resumes by itself; queued work is kept. Housekeeping still runs while stopped.

## Data boundaries

Web updates use Admin-only prepare/start/status control and an installation-scoped D1 request/executor lock. A fixed private GitHub Actions controller owns exact-release deployment, preserved-resource checks and recovery checkpoints. Worker dispatch credentials are secrets, excluded from D1/API/backups. Maintenance returns retryable kiosk errors while queued scans remain local. See [WEB-UPDATES.md](WEB-UPDATES.md).

Server-owned update-track consent lives in a separate operational table with revision-based atomic changes and audit records. Stable is the default. Web requests and kiosk commands retain the selected track, official tag and exact commit. Discovery and browser hint caches are partitioned by track. The canonical release policy is packaged with the kiosk resolver so it does not depend on a source checkout. See [UPDATE-TRACKS.md](UPDATE-TRACKS.md).

| Location | May store | Must not store |
| --- | --- | --- |
| R503 sensor | fingerprint templates | cloud credentials |
| Pi local storage | PIN hashes in the roster cache while Require PIN is on; slot/member mapping with optional immutable roster identity, keyed credential digests, local credential secret, active-roster cache, queued attendance, pairing material; optional sync private keys, trust, encrypted outbox and receiver journal; vault slot/retry metadata | plaintext fingerprint templates, raw badge or QR values at rest |
| Web kiosk browser storage | kiosk credential, last configuration, active-roster cache (with emails only for member search, and PIN hashes only while Require PIN is on), queued attendance, offline wrong-PIN counts | member PINs, Discord kiosk codes, fingerprint or badge data |
| D1 | roster, meetings, attendance, salted member PIN hashes, hashed one-time Discord kiosk codes, encrypted FIRST credentials and cached team answers, the encrypted Notion token and each module's chosen Notion databases, configured and reported authentication methods, settings, audit records, encrypted integration secrets; historical peer-sync public identities/deliveries; optional vault ciphertext and immutable enrollment metadata | plaintext fingerprint templates, raw biometric scans, vault root secret, kiosk private decryption keys, raw badge or QR values, local credential digests or secret, raw IP |

Fingerprint sharing is Attendance-owned operational state, excluded from portable backups, and optional cloud storage is its only active transport (peer transfer routes are retired). Cloud storage uses a server-managed `FINGERPRINT_VAULT_KEY` to derive distinct authenticated-encryption and keyed-digest keys; its tables hold generation and key identity, immutable roster binding and ciphertext. `/kiosk/roster` projects the immutable identity additively. Kiosk polling backfills at most two verified source slots per pass and requests up to eight missing templates per batch after a catalog revision change. Attendance queues contain no template data. See [SECURITY.md](SECURITY.md#optional-server-managed-fingerprint-storage) and [PRIVACY.md](PRIVACY.md#optional-fingerprint-cloud-storage) for trust, retention and revocation.

Compatible kiosks combine background reads through `/kiosk/poll`: commands every five seconds, fingerprint metadata every fifteen seconds and configuration every minute. Each response checks current kiosk and module authority. Revision-validated roster and vault metadata can be reused locally, while transfers retain their own authorization and recovery checks. Heartbeats remain separate writes. Older clients keep their existing endpoints; newer clients use those endpoints only when the combined route is explicitly unsupported.

## Security controls

- Pairing codes are single-use, time-limited, hashed at rest, and bound to one installation.
- Dashboard-to-Pi maintenance accepts six short-lived enumerated commands only (`reload_display`, `restart_service`, `reboot`, `reset_network_pin`, `install_latest`, `erase_unlinked_fingerprints`); it provides no remote shell or arbitrary arguments.
- Network and authentication maintenance controls are loopback-only, protected by a locally salted and rate-limited PIN, and backed by narrow Polkit permissions.
- An Admin can start a five-minute fingerprint enrollment session for one online kiosk from the dashboard. The kiosk confirms the member locally and uses a free reader slot for two scans. This session grants enrollment only, not general maintenance access. Every delivery checks current pairing, creator and member authority; sessions are operational state excluded from portable backups.
- Worker session tokens use Secure, HTTP-only, SameSite=Strict cookies through the same-origin Pages proxy; OAuth ID tokens are verified server-side.
- Every permission-sensitive API path reloads the active user and current role from D1 before checking Admin or Operator capability.
- Destructive actions require an explicit confirmation phrase and immutable audit record.
- Secret encryption uses AES-GCM with per-record random IVs and an installation-specific Worker secret.
- Integration test actions use least-privilege operations and do not reveal credentials.
- CSV export neutralizes leading spreadsheet formula markers before quoting cells.
- The Worker owns the versioned saved-report definition and curated column registry. `/reports/query` and both report CSV endpoints validate the same definition, resolve organization-local periods, and use the canonical attendance evaluator. Page and page-size state stay outside saved definitions.
