# Data backup and restore

This is the reference for backup formats and restore behavior. The everyday steps are in [Back up, restore, or delete data](https://isriah.github.io/LancerLogin/operations.html#data) on the documentation site. Back up before a web update, bulk deletion, or recovery decision. A backup is sensitive: it can contain attendance information, password hashes, encrypted integration values, kiosk credential hashes, and audit history.

## Dashboard backups

The dashboard's rejected-scan review list is an operational mirror of protected records retained on each kiosk. It is excluded from portable dashboard backups; review audits remain in audit history. Preserve kiosk state separately before recovery or replacement. Authorized kiosks send each retained record until the dashboard acknowledges it, then only send local review changes and check open records for dashboard reviews; records already reviewed in the cloud are not resent. An installation restore also revokes kiosk credentials and requires the documented pairing/recovery procedure. Do not assume a dashboard backup alone preserves every rejected scan.

Open **Settings > Data**. Each category has separate download, restore, and typed-confirmation deletion controls.

| Category | Includes | Important boundary |
| --- | --- | --- |
| Meetings and attendance | Meetings, audience label selections, scans, corrections, excuses, and contests | Deletion keeps roster, member labels, accounts, settings, integrations, and audit history. |
| Roster | Member identity/contact data, Discord links, active state, dated label changes, label definitions, attendance rules, the recent compliance window, and policy activation date | Dashboard accounts remain separate. Historical members missing from a restore remain inactive when referenced. |
| Entire installation | Portable retained D1 state, including saved private and shared reports, account-pinned report tabs, and Discord label-to-role associations | Restore only while the installation encryption secrets are unchanged. Operational role sync jobs and fingerprint relay state are not replayed from dashboard backups. |

Each JSON file records its scope and schema version. The dashboard rejects a file from another category and requires `RESTORE <CATEGORY>` exactly. The dashboard moves backups and restores [in parts](#backups-and-restores-in-parts), so a restore file may be up to 100 MiB; a restore holds at most 150,000 records.

A backup reads every table it contains in one D1 batch, which is a single transaction. The file is therefore one consistent snapshot, even when scans or edits arrive while it is being made, and a backup is one database query against the Workers Free limit of 50 per request however many tables Core and the installed plugins have. This includes the backup a web update asks for first. D1's limits apply to each statement of that batch, and the whole batch must finish within 30 seconds. An installation too large for that uses the D1 export below.

Backup schema 21 adds each account's page walkthrough progress and dismissal preference to entire-installation backups. Backups before schema 21 restore with no recorded walkthrough progress. Roster and meetings restores preserve walkthrough progress.

The earlier Community-based Modular schema 22 adds optional-module lifecycle and Operator assignment authority to entire-installation backups. Public Community v1.2.5 independently uses schema 22 for Discord delivery batches. The importer distinguishes the complete Community table manifest without Modular metadata from the Modular format; the number alone is not sufficient. Restoring a supported Community backup enables Attendance, completes module selection, and assigns Attendance to every restored Operator so existing access is preserved.

Backup schema 23 adds Attendance setup progress and retained-data cleanup state. Restoring an older supported backup upgrades Attendance setup records without reopening setup for an existing Community installation. Cleanup leases are transient authority and are deliberately not portable.

Backup schema 24 adds each Admin's developer-control visibility preference. Durable scheduler state remains runtime authority outside portable backups, so restore cannot start background work or replay elapsed scheduler passes.

Backup schema 25 adds Outreach participation data. Schema 26 adds correction and reopen records. Schema 27 adds reviewed publication state and provider-operation history.

Backup schema 28 introduces the `lancerlogin-community-modular` envelope. It records the Core and optional-module ownership contract for every included table. Schemas 31 and 32 require an exact ownership match and reject undeclared tables or columns. Released Community backups through schema 22 and supported earlier Community-based Modular archives use explicit adapters. Backups produced by incompatible Modular prototypes are rejected instead of being guessed into the Community data model.

Backup schema 30 adds Carpool-owned plans, participants, assignments, import profiles, and location cache records to entire-installation backups. Supported schema 30 and 31 backups retain those records in the current format. Earlier supported backups restore with Carpool disabled and empty.

Backup schema 32 preserves Discord delivery batch identifiers introduced in Community v1.2.5. Older supported archives default these identifiers to null. This does not resume provider work during restore; the existing review and credential-revocation safeguards still apply.

Backup schema 33 adds the Outreach public member-ID validation setting and activity associations on correction requests. Earlier supported backups restore live validation as **Off**. Current backups preserve the selected privacy mode, so review it before making a restored public form available to a new audience. Lookup throttling is temporary operational state, excluded from portable backups. Event-level corrections retain their associated activity and require Staff to select the affected entry before changing counted participation.

Backup schema 35 adds Carpool planning defaults. Earlier supported backups use the standard 4-mile preferred and 12-mile maximum radii for new plans. Saved Geoapify credentials are excluded from portable backups and removed during entire-installation restore. Configure location lookup again after recovery. Existing Carpool plans retain their own distances.

Backup schema 36 preserves the event details queued for each Outreach publication destination. Earlier supported backups default those snapshots to null and retain their existing publication timing. Restored pending operations remain paused until Staff explicitly retries; a restore does not publish or remove provider events. Invalid snapshot identities, times or all-day dates are rejected before restoration.

Backup schema 40 preserves each kiosk's configured authentication method independently from its last reported method. Migration 0073 copies the installation's effective method to existing devices without changing their reported state. Supported schemas 31-39 restore each kiosk's configured method from that backup's installation setting; older schemas use fingerprint. Current backups reject missing or invalid per-device methods before writes. Restored devices remain retired with revoked credentials and require re-pairing; newly paired devices start with fingerprint. Retained device records do not grant access.

Backup schema 31 adds the installation's configured kiosk authentication method. Earlier supported backups restore it as fingerprint, preserving the prior behavior. A retained reported method is historical diagnostic state and does not establish current device readiness. Fingerprint templates, slot mappings, badge and QR mappings, local credential transform secrets, local active-roster caches, and pending kiosk events are not included in dashboard backups. Portable restore still revokes every kiosk credential, so re-pair each device and review its owner-only local state before returning it to service.

Fingerprint sharing state is operational and non-portable. Dashboard exports exclude fingerprint cloud storage (`kiosk_fingerprint_vault_settings`, `kiosk_fingerprint_vault_templates`), reset batches and commands (`kiosk_fingerprint_reset_batches`, `kiosk_fingerprint_reset_commands`), the retired review tables (`kiosk_fingerprint_review_requests`, `kiosk_fingerprint_review_manifests`, `kiosk_fingerprint_review_slots`, `kiosk_fingerprint_retired_review_grants`) and historical peer-sync registrations and deliveries. An entire-installation restore removes cloud authority and ciphertext, clears reset and peer authority, and leaves cloud storage off. The separate `FINGERPRINT_VAULT_KEY` is a Worker secret, never a backup field; preserve it independently, since a replacement key cannot decrypt existing ciphertext. Before re-enabling cloud storage after a restore, renew the organization's biometric consent. Raw D1 exports and Pi backups may retain retired or deleted fingerprint metadata; protect them and never reuse them to authorize sharing. See [privacy](PRIVACY.md#optional-fingerprint-cloud-storage).

Scan check records are diagnostic and never part of a backup: fingerprint match scores (`kiosk_scan_matches`), which kiosk recorded each accepted scan (`kiosk_accepted_scans`) and possible wrong matches (`kiosk_possible_wrong_matches`). They describe scans of the state being replaced, so an entire-installation restore clears them, as **Delete installation** does; **Possible wrong matches** starts empty after a restore. Re-enrollment suggestions and dismissals are cleared with the roster they belong to. The minimum match score (`kiosk_fingerprint_match_settings`) is not in a backup either; a restore keeps the installation's current value, so it never lowers the score an Admin required. Roster and meetings restores leave all of these alone.

Schema 20 added saved report views and report-tab preferences to entire-installation backups. Older backups restore with an empty report library. Roster and meetings restores preserve existing reports. If a preserved report refers to a label that is absent after a category restore, the report displays an actionable warning and keeps the missing reference for editing instead of broadening its results.

Portable roster backups omit Discord role IDs. Restoring a roster keeps only existing role associations whose labels remain active, and stops any pending role sync. It does not modify Discord roles.

Backup schema 45 adds where each dated label change came from (`member_label_changes.source`: `dashboard` or `discord`) to roster and entire-installation backups, and each Discord role link's sync direction (`discord_label_role_mappings.sync_direction`: `to_discord` or `two_way`) to entire-installation backups. Label history restores exactly, including changes made from Discord. A label that synced both ways restores paused: it stays on **Two-way, needs reconciliation**, the scheduled two-way check skips it, and nothing changes in Discord or labels until an Admin opens **Review differences** on the Labels page and confirms, which records a new agreed state and turns two-way sync back on. The Admin can instead switch the label to **Dashboard to Discord**. A roster restore replaces label history, so it pauses current two-way labels the same way. The last agreed state, the list of Discord users holding the role without a roster link, and open reviews are operational and never travel in backups; a restore clears them. A backup taken while a label is paused records it as two-way, so restoring it pauses the label again. Backups before schema 45 restore every label change as from the dashboard and every role link as Dashboard to Discord, as before.

Backup schema 46 adds each kiosk's kind (`kiosks.kind`: `pi` or `web`) and member lookup (`kiosks.member_lookup`: `entry` or `search`), and each pairing code's kiosk kind and name (`pairing_codes.kiosk_kind`, `pairing_codes.kiosk_name`), to entire-installation backups. As before, a restore revokes every kiosk credential and invalidates every pairing code, so web kiosks pair again like Pi kiosks. Backups before schema 46 restore every kiosk and pairing code as a Raspberry Pi one on member ID entry.

Backup schema 47 adds member PINs to entire-installation backups: each member's salted PBKDF2-SHA256 PIN hash, when and at which kiosk it was set, and its wrong tries and lock (`member_pins`), each kiosk's **Require PIN** setting (`kiosks.require_pin`), and the PIN lockout setting (`organization_settings.pin_lockout_enabled`, `pin_lockout_attempts`, `pin_lockout_minutes`). A PIN itself is never stored, so no backup contains one. Roster backups never carry PIN hashes; a roster restore keeps the PINs of members it updates in place. Pending PIN setup requests are short-lived and bound to a kiosk's credential, so they never travel; a restore revokes kiosk credentials as before, and kiosks that pair again receive the restored hashes once Require PIN is on. The online PIN throttle's state (`member_pins.throttle_failures` and `throttle_until`) is never backed up, so a restore starts it over. Backups before schema 47 restore with no PINs, Require PIN off on every kiosk, and lockout off (5 wrong tries, 15 minutes).

Backup schema 50 adds each module's own reporting start date (operational baseline) to entire-installation backups (`module_report_baselines`); Attendance's stays in `organization_settings.attendance_reporting_starts_on`. Before schema 50 one date served every report, so restoring an older backup gives Outreach the Attendance date, as the upgrade does. A module not in the build being backed up carries no date.

Backup schema 51 adds the early arrival allowance (`organization_settings.early_scan_minutes`) to entire-installation backups. Restoring an older backup sets it to the 15-minute default, as the upgrade does for existing installations.

Backup schema 52 adds each kiosk's Discord code setting and its backup choice (`kiosks.discord_code` and `kiosks.discord_code_backup`) to entire-installation backups. Restoring an older backup leaves Discord codes off on every kiosk, with the backup choice at offline only. The one-time codes themselves last two minutes and are never backed up, and neither is a kiosk's wrong-code count.

Backup schema 53 adds the Notion connection and each module's chosen Notion databases to entire-installation backups (`notion_connection` and `notion_bindings`): the token's ciphertext and IV under the integration key, whether the connection is on, the integration's name and workspace, when Notion last accepted the token, and what the token has been seen to allow; and, for each module in the build being backed up, the database and data source an Admin chose. The token itself never appears in a backup, and neither does the pause after a Notion rate limit. Backups before schema 53 restore with no Notion connection and no chosen databases. A token restored onto an installation whose integration key cannot decrypt it shows **Saved, but can't be read** in **Settings > Integrations > Notion** until an Admin saves it again; the chosen databases are kept. While deliveries are paused after a restore, modules do not write to Notion, as for Discord.

Backup schema 54 adds the name Notion shows on each module's comments to entire-installation backups (`notion_comment_names`), for each module in the build being backed up that has one set. Backups before schema 54 restore with no names, so each module's comments carry its own name.

Backup schema 49 adds the FIRST connection's credentials to entire-installation backups (`first_credentials`): for FRC and FTC, the Events API username, the token's ciphertext and IV under the integration key, and when FIRST last accepted it. The token itself never appears in a backup. FIRST's cached team answers, seasons and recent request counts are not backed up and restore empty. Backups before schema 49 restore with no FIRST credential. A credential restored onto an installation whose integration key cannot decrypt it shows **Saved, but can't be read** in **Settings > Integrations > FIRST** until an Admin saves it again.

If you restore meetings without their original roster backup, review audience labels before using attendance reports. Label assignments, attendance rules, and the recent window travel with the roster category, while each meeting's audience selection travels with the meetings category. Older backups without labels restore meetings as **All** and do not invent member labels or attendance rules.

A meetings restore updates meetings that still exist by ID in place, so their live Google Calendar and Discord scheduled-event links survive and later syncs update the same external events instead of creating duplicates. These links are operational state of the running installation and are not part of the backup. Meetings absent from the backup are deleted with their links; their external events are left in place, and the restore response reports how many were detached as `recovery.detachedCalendarEvents`. Remove those events from the calendar or Discord server manually if they are no longer wanted.

Participation start dates that older versions stored as the UTC date a member was added are corrected once to the organization's local date by scheduled housekeeping (`apps/api/src/participation-start-correction.ts`, migration 0107). A member is corrected only when all of these hold: the stored date equals the UTC date of the member's own `created_at`; no audit entry shows an Admin changed the start date; and the correction cannot make the member's record worse. West of UTC the start moves a day earlier, so the member must have been present at every meeting that would newly count. East of UTC it moves a day later, so no counted presence may fall on the day that stops counting. A member for whom no meeting would start or stop counting is left alone. The audit entry `attendance.participation_starts_corrected` lists each corrected member's old and new date and the meetings gained or dropped, and counts the members left alone. The dashboard has no audit log page or export, so the entry is read where every audit entry is: in the `audit_log` table of an entire-installation backup, or in D1 directly. A run that corrects nobody writes no entry. The job's completion marker is never in a backup. A roster or entire-installation restore starts the job again, so it examines the restored members: dates from a backup made before the correction are assessed again, and dates from a later backup no longer match and stay as they are.

Module access grants, which let one module call another without a signed-in user, are authority rather than data. Backups leave them out, and an entire-installation restore removes them. After a restore, review **Settings > Modules > Module access** and grant again; see [module access](MODULE-PLUGINS.md#module-access).

Operational web-update locks and recovery records are deliberately outside the dashboard category backups. They prevent an old restore from erasing an active deployment claim. Worker update credentials are secrets and are never in a backup.

A dashboard restore replaces the data in one all-or-nothing database transaction, limited to 150,000 records. Cloudflare D1 also limits how long a single transaction may run (about 30 seconds) and how much memory it may use. If a large backup exceeds those limits, the transaction is rolled back, nothing changes, and the restore returns HTTP 503 with an explanation. Restore one category at a time, or use the D1 restore workflow below for very large installations.

A restore also counts against D1's daily allowance of rows written, which is 100,000 a day across the account on the Free plan. Cloudflare's [D1 pricing page](https://developers.cloudflare.com/d1/platform/pricing/) says: "When your account hits the daily read and/or write limits, you will not be able to run queries against D1", and "Free daily usage limits reset at 00:00 UTC." That is every query, reads included, so the dashboard and every kiosk stop working until then, sign-in included, not only scans.

D1 counts a written row for each record and one more for each index on its table. A restored scan (`attendance_events`) costs 6: the row and its five indexes. Migration 0106 dropped a sixth index that repeated the start of another, which took the reference installation below from 535,065 written rows to 481,065, and a scan at a kiosk from 8 to 7. The report revision triggers of migration 0037 would add one more for every row inserted or removed; a restore sets them aside for its transaction, adds one to the revision itself and puts them back unchanged, which had taken the same restore from 638,964 written rows to 535,065. Of the 481,065, 410,683 are the records and their indexes, and the rest the rows the restore removed first. Scans are about four fifths of it, so restoring one category at a time does not help: meetings and attendance is nearly all of the cost. A restore of more than roughly 15,000 records passes a Free day's allowance in its one transaction.

Before a restore estimated to write more than 80,000 rows, the restore dialog says "at least about" how many, and what passing the allowance means, and asks whether to continue. The estimate is a lower bound: the records in the file times the cost of their tables (`packages/shared/src/restore-writes.ts`, which a test keeps in step with the schema); the rows removed first come on top. Starting a restore in parts returns the same estimate as `estimatedRowsWritten`. On the Free plan, restore a large backup when the installation can be out of use until 00:00 UTC, or move the account to a paid plan first.

### Backups and restores in parts

Cloudflare limits a Worker's CPU time per request: 10 ms on Workers Free, with some tolerance for a request that occasionally runs over. Reading, checking and writing a whole backup in one request costs far more than that for a multi-season installation. Measured in local workerd for the reference installation (150 members, 12 labels, 3 kiosks, 300 meetings a season for three seasons, about 30 members scanning in and out of each meeting; 73,677 records and a 24 MB file), one season alone (28,877 records, 9.3 MB) costs about 20 ms to read, 6 ms to check and 30 ms to write, and its backup about 30 ms; three seasons are refused by the single-request restore's 10 MiB limit.

So the dashboard moves a backup in parts of about 64 KiB, one part per request, and D1 does the copying:

- **Backup.** Starting a download copies every table into staged parts in one batch, which is one snapshot exactly as before, and writes the usual audit entry. The dashboard downloads the parts and puts the same JSON file together. Rows written after the download started are not in the file.
- **Restore.** The dashboard splits the file in the browser. It sends the backup document with its large tables emptied, and the API runs every check that does not need those tables' rows, including the module, ownership, authority and lifecycle checks and the refusal of plugins the installation cannot restore. It then uploads each part. The API checks each part's SHA-256 against the value declared when the restore started, checks every row as the single request does, and stages the rows. One final request checks the document again and runs the same all-or-nothing transaction, in which D1 copies the staged rows into place.

Nothing but staging is written before that final transaction. A restore that is refused, fails, is cancelled or is abandoned at any earlier point leaves the installation exactly as it was, and so does a final transaction the database refuses. The final transaction also removes the staged parts. Everything else about a restore is unchanged: the typed confirmation, write suspension during an update, kiosk credentials and pairing codes retired, queued provider work stopped for review, sessions ended, and the same audit entry and response.

The tables uploaded in parts are the ones that grow with every meeting, scan and audited action: `meetings`, `meeting_audience_labels`, `attendance_events`, `attendance_corrections`, `member_label_changes`, `audit_log`, `integration_deliveries`, `integration_state`, the Discord absence notice, recipient, contest and anomaly report tables, and the calendar mapping and operation tables. Nothing about one of their rows depends on another row, so each part is checked alone. Every other table, and every plugin's section, stays in the backup document and is checked whole, as a plugin's backup adapter requires; a plugin section of several megabytes can still exceed the CPU allowance when the restore starts or finishes.

Measured the same way over several runs, no request of the reference installation's backup or restore used more than 9 ms. Starting a backup took 5 to 7 ms and each of its 280 parts about 1 ms (6 ms at most). Starting a restore took 6 to 9 ms, each of its 371 parts 1.5 to 2 ms (7 ms at most), and the final request 5 to 8 ms, while D1 spent 6 to 13 seconds copying the staged rows. The two requests that check the backup document, at the start and the end of a restore, are the costly ones, and their cost follows the tables that stay in the document (the roster, accounts, settings and plugin sections), not the meetings and scans. These are local measurements on one machine, without what the D1 binding costs on Cloudflare; treat them as relative to each other and to the single-request numbers above. `node --experimental-strip-types scripts/measure-backup-cpu.mjs` repeats them.

Staging is operational state in `data_transfer_sessions` and `data_transfer_chunks` (migration 0105). It is never part of a backup. Each Admin has one restore and one backup download staged at a time: starting another ends that Admin's earlier one, whose requests then answer HTTP 404 with `code: "transfer_session_missing"`, and leaves other Admins' alone, so one Admin's download cannot end the backup another is taking for an update. At most four sessions of a kind are kept in all; a fifth removes the oldest. A session nobody finished is removed two hours after it started, by the scheduled clean-up or the next backup or restore, and deleting meetings and attendance, the roster or the installation removes everything staged. A restore that completed keeps only its answer until then.

| Request | Purpose |
| --- | --- |
| POST `/admin/data/backup/sessions` | Body `{ scope, updateRequestId? }`. Stages the snapshot. Returns the session `id`, the `filename`, the backup `document` with every table empty, the `parts` (each with its `seq`, `table`, `rows` and, for a plugin's table, `module`) and the `columns` of each table that has parts. |
| GET `/admin/data/backup/sessions/<id>/parts/<seq>` | One part: a JSON array of rows, each an array of values in the order of its table's `columns`. |
| POST `/admin/data/backup/sessions/<id>/complete` | Every part was received. Removes the staged parts and, for a web update, records its backup. |
| DELETE `/admin/data/backup/sessions/<id>` | Cancels the download. |
| POST `/admin/data/restore/sessions` | Body `{ scope, confirmation, document, parts, excludeModules? }`. `document` is the backup as JSON text with the tables sent in parts emptied; `parts` lists each part's `table`, `rows` and `sha256`. Returns the session `id`, its `digest`, the numbers of the `parts` to upload, and `estimatedRowsWritten`. Refusals are those of the single request, including HTTP 409 `module-restore-refused`. |
| PUT `/admin/data/restore/sessions/<id>/parts/<seq>` | One part: a JSON array of row objects, at most 256 KiB. HTTP 409 `restore_part_mismatch` when the bytes are not the declared ones. Sending a part again is harmless. Text is staged as D1 stores a bound value, and numbers as it binds them, so both routes leave the same bytes. |
| GET `/admin/data/restore/sessions/<id>` | The numbers of the parts that have not arrived (`missing`), and whether the restore has completed (`committed`). The dashboard asks this after a dropped connection and continues with the missing parts. |
| POST `/admin/data/restore/sessions/<id>/commit` | Body `{ confirmation, digest }`. Checks the stored document against the SHA-256 taken when the restore started (HTTP 409 `restore_document_mismatch`), then replaces the data. HTTP 409 `restore_incomplete` while parts are missing. The response is the single request's. Sent again after it completed, it is answered with the same response and nothing runs twice. |
| DELETE `/admin/data/restore/sessions/<id>` | Cancels the restore and removes the staged parts. |

The single requests remain for API clients and smaller installations: GET `/admin/data/backup?scope=<category>` and POST `/admin/data/restore`, which accepts a body up to 10 MiB. The dashboard uses them only against an API without parts, and for a backup while an update suspends writes, since staging a backup is a write. The file format is the same either way, so a backup made in parts restores in one request on any release that reads its schema, and the reverse.

If the connection drops during the final request, the transaction either completed whole or changed nothing. The dashboard sends the request again, which is safe, and reports the answer. After an entire-installation restore that completed, the repeat finds the session ended, as every session is; the dashboard then says the restore completed and asks you to sign in again. Only when no answer can be had at all does it ask you to reload and check.

An entire-installation restore signs out every account. A backup never contains session state, and a restore gives every restored account a new session epoch that is higher than any earlier one, so a session that was ended before the restore (by signing out, a password reset or deactivation) cannot work again, and neither can any other session that was open. The Admin making the restore stays signed in: the response replaces their session cookie with the same session under the new epoch, with its original expiry. If the backup does not contain that Admin's account as an active one, they are signed out too and sign in with an account from the backup. Roster and meetings restores do not touch accounts or sessions.

Entire-installation restore validates table ownership, installation scope, module contracts, dependencies, lifecycle state, setup progress, Operator assignments, saved reports, and walkthrough progress before any destructive database statement runs. It then creates fresh local module authority instead of importing old epochs or leases.

Portable restore preserves encrypted Google and other integration records only when the installation encryption secrets are unchanged. It stops pending provider, Calendar, notification, anomaly, and Outreach publication work for explicit review. It also invalidates all restored pairing codes and kiosk credentials. A backup made before the browser simulator was removed (backup schema 47 and earlier) restores without its simulator session. Re-pair each physical kiosk, confirm its selected authentication method, and review provider operations after restore. Do not copy a historical queue to a new pairing or another device. Server restore cannot erase local authentication mappings; remove them from **Authentication maintenance** on each kiosk before repurposing or decommissioning it.

This portable-restore boundary differs from an ordinary in-place web update. A normal compatible update preserves the active Community kiosk credential, pairing, mappings, and queued scans. Existing Community kiosk credentials remain compatible with their pre-upgrade unbound queue. Every new or replacement pairing is pairing-bound: each new scan captures that pairing, and a queued scan from an older pairing is rejected and retained in the kiosk's local review record instead of being attached to the replacement kiosk.

### Plugin modules

Backup schema 42 adds an `externalModules` section to entire-installation backups. Meetings and roster backups are unchanged and must not contain it. Core tables, column lists, ownership metadata and historical normalization describe only Core and the first-party modules, so the rest of the file is identical whether or not plugins are installed. Every installed plugin has one entry:

| Field | Meaning |
| --- | --- |
| `id`, `label` | The plugin's module ID and display name. |
| `contractVersion` | The module contract the plugin was built against. |
| `backupVersion` | The plugin's own backup format version. |
| `source`, `commit` | The plugin's git source and pinned commit, or `null` until the installed-module catalog records them. |
| `tables` | Rows of the plugin's declared portable tables for this installation, using only its declared columns. |

Plugin lifecycle, Operator assignment and setup rows stay in the Core module tables. A plugin's non-portable tables, such as stored credentials or leases, are never exported.

Restore validates the section strictly before any write: no unknown fields, only scalar values, only declared tables and columns, rows scoped to this installation, and plugin rows counted toward the same 150,000-record dashboard limit. A plugin's section always travels whole in the backup document, also when the rest of the restore is uploaded in parts. An installed plugin then converts an older backup version, validates its rows, and neutralizes transient authority so credentials, leases and pending work do not revive. Restore clears every installed plugin's declared tables, including plugins that the backup does not contain, and writes plugin rows in the same atomic batch as Core data. An installed plugin absent from the backup starts disabled with a new generation and its default rows, as on a new installation.

Restore refuses, without changing anything, when the backup contains a plugin that is not installed, is newer than the installed plugin, or was exported under a different module contract. The response is HTTP 409 with `code: "module-restore-refused"` and lists each module with its ID, name, required backup and contract versions, installed versions, recorded source and commit, and record count. Install the listed plugin version and retry, or confirm a restore that discards those modules' data. In **Settings > Data**, the restore dialog names each module and its record count and requires a separate **Discard** checkbox before **Restore without these modules** becomes available. API clients send `excludeModules` with exactly the refused module IDs; any other list is refused.

The opt-out is unavailable while a restored module depends on a refused one. Install the missing dependency instead. Discarded modules restore as absent: they have no lifecycle, generation, Operator assignment or setup rows, and their data is not written. If a discarded module is still installed in an older version, it starts disabled and empty. The restore audit entry and the response record each discarded module with its record count.

Backups from schema 41 and earlier have no plugin section. They restore exactly as before; any plugins installed now are cleared and start fresh.

Lifecycle, assignment and setup rows of a module whose code is not in the build making the backup, such as a removed plugin, are left out of the file: it carries none of that module's data, and the build could not restore them.

### Carpool moved into a plugin

Backup schema 43 moves Carpool out of Core's section. Carpool's rows now travel in its plugin section (module backup version 2), and Core's ownership metadata lists only Attendance and Outreach. The columns are unchanged. Meetings and roster backups change only in their ownership metadata.

Backups from schema 30 through 42 were made while Carpool was first-party, and carry its tables in Core's section. Core still checks their ownership metadata exactly and then treats those rows as a Carpool module entry, backup version 1:

- With the Carpool plugin installed, the rows restore through its adapter, which applies the same historical defaults Core did (meeting links, trip scope and pin provenance, groups and rebuild recovery, trip timing, settings) and the same validation. Lifecycle, Operator assignments and setup progress restore as before, and kiosk handling is unchanged.
- Without the plugin, a backup that holds Carpool data or state (any Carpool row, Operator assignment or setup progress, or Carpool enabled, retained or deleting) is refused like any unavailable plugin. The refusal names Carpool, backup version 1 and its record count. Install the plugin and retry, or confirm a restore that discards Carpool with `excludeModules: ["carpool"]`; the discard is audited and Carpool restores as absent.
- Without the plugin, a backup in which Carpool was never used restores without a confirmation. Its disabled Carpool registration is left out, as there is nothing to discard.

A backup from schema 43 or later made without the Carpool plugin contains no Carpool data, even if Carpool data is still retained in the database. Compose the plugin before taking a backup that must include it.

### Outreach moved into a plugin

Backup schema 44 moves Outreach out of Core's section. Outreach is now the official Outreach plugin, included in installation builds by default. Its rows travel in its plugin section (module backup version 3), and Core's ownership metadata lists only Attendance. The columns are unchanged. Meetings and roster backups change only in their ownership metadata.

Backups from schema 25 through 43 were made while Outreach was first-party, and carry its tables in Core's section. Core still checks their ownership metadata exactly and then treats those rows as an Outreach module entry, backup version 2:

- With the Outreach plugin installed, the rows restore through its adapter, which applies the same historical defaults Core did (correction activities and public form privacy before schema 33, event times, publication settings and labels before schema 29, publication snapshots before schema 36) and the same validation. Pending and leased publication operations are paused for explicit retry and counted with the other paused provider operations. Lifecycle, Operator assignments, setup progress and walkthrough progress restore as before.
- Without the plugin, a backup that holds Outreach data or state (any Outreach row other than the default settings and labels every installation received, an Operator assignment or setup progress, or Outreach enabled, retained or deleting) is refused like any unavailable plugin. The refusal names Outreach Participation, backup version 2 and its record count. Install the plugin and retry, or confirm a restore that discards Outreach with `excludeModules: ["hour-tracking"]`; the discard is audited, Outreach restores as absent, and progress on its walkthrough is not restored. Saved reports on Outreach datasets are kept as saved.
- Without the plugin, a backup in which Outreach was never used restores without a confirmation. Its disabled registration and default rows are left out.

Backups before schema 25 contain no Outreach data. With the plugin installed, Outreach starts disabled, and its default settings and labels are created when it is first enabled, as on a new installation.

A backup from schema 44 or later made without the Outreach plugin contains no Outreach data, even if Outreach data is still retained in the database.

Plugin authors provide a backup adapter on their API contribution (`backup` in `apps/api/src/module-contributions.ts`). Its version must equal the manifest's `backup.version`, and its tables must be exactly the manifest's portable tables, in parent-first restore order, each with an `installation_id` column. A plugin that declares transient authority on a portable table must provide `neutralize`. Core clears non-portable tables first, then portable tables in reverse order, before Core rows are removed.

## D1 export and restore

The physical kiosk's **Authentication maintenance > Unpair kiosk** control creates a protected local archive before returning to setup. This archive contains the old installation's credential, local attendance history, mappings, roster cache and sharing state, not reader templates. It is not portable into another installation and is never restored automatically. It preserves the local PIN and Wi-Fi connections. Retire the original dashboard device separately, since local unpairing alone does not revoke the archived credential. See [KIOSK.md](KIOSK.md) for the confirmed transition and interrupted-archive recovery procedure.

For a larger or infrastructure-level recovery, work from the adopter-owned private repository checkout. Create a fresh export before an upgrade or restore. Put `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in the current shell through the organization's approved secret-handling method, not a command line or repository file.

```sh
npm run backup-d1 -- --database sample-club-data --output lancerlogin-backup.sql
```

The helper refuses to overwrite an existing backup. Store the export securely, and record the installed release and UTC export time beside it.

Restore only to the same adopter-owned installation after taking a fresh pre-restore export:

```sh
npm run restore-d1 -- --database sample-club-data --file lancerlogin-backup.sql --confirm "RESTORE sample-club-data"
```

Replace `sample-club-data` with the private installation database name. Verify members, meetings, attendance events, corrections, audit records, and settings before reopening normal writes. If `INTEGRATION_KEY` changed, rotate the affected integration. Do not restore a historical kiosk queue or a backup into another organization automatically.

A raw D1 export is infrastructure state, not a portable dashboard backup. It can contain operational leases, update locks, kiosk authority, pending provider work, fingerprint relay ciphertext/public keys and associated member/device metadata, and durable server-encrypted vault templates/authority. Its restore requires a separately reviewed recovery plan that explicitly reconciles those authorities before normal writes resume. The vault's separate root secret is outside D1; preserve it independently, since ciphertext plus that secret allows decryption. Treat Pi state backups as credential-bearing biometric-related material too: historical peer sync may retain private keys, approved peer identities, encrypted outbox messages and slot/retry metadata, and cloud storage adds immutable mapping and delivery metadata. A backup may retain information already removed from live state. Do not put either kind of backup in source, chat, or support logs.

Cloudflare documents D1 exports and its separate Time Travel recovery capability in its [D1 documentation](https://developers.cloudflare.com/d1/). Use those provider controls only with an explicit recovery plan for the intended installation.

For label assignment and rule behavior, see [Member labels and attendance policies](ATTENDANCE-POLICIES.md).
