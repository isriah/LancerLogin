## External acceptance boundary

No existing attendance installation, Cloudflare resource, Raspberry Pi, credential, database, repository, or git history was modified or reused. The community collector remains in its collector-only account. On 2026-08-31 the user explicitly approved a narrower exception allowing a coexistence deployment in the same Cloudflare account as the earlier attendance resources. A new least-privilege seven-day token and the collision-guarded Create workflow produced only `lancerlogin-test-api`, `lancerlogin-test-data`, and `lancerlogin-test-dashboard`; no custom domain, route, binding, migration, or shared data path was created. The isolated Create acceptance passed, the Pages dashboard rendered the fresh first-Admin setup, `/api/health` returned ready, and `/api/setup/status` returned unconfigured. The isolated Upgrade acceptance subsequently validated those exact resources and retained secret names, applied all migrations, and redeployed only that Worker and Pages project. At the user's request, the public deployment workflow runs and their logs/artifacts were permanently deleted on 2026-09-01; this durable record intentionally does not link to removed run pages. Live browser smoke tests confirmed the guided setup wizard, dark-mode branding access, and simulated-kiosk path. Physical Pi/R503 acceptance remains pending.

Main-branch CI runs `npm run verify:release`, including `npm run verify:migrations`, which creates an isolated local D1 database, applies every numbered migration in order, compares the applied list to the source directory, inspects the final themed-branding and kiosk-health schema, checks the biometric-storage invariant, and removes the generated state. It never uses a Cloudflare token or remote flag. A tagged release must reference the exact commit from a successful main-branch Verify run, so packaging does not repeat that full gate.

The adopter successfully upgraded the isolated private installation through v0.8.0. v0.9.0 remains intentionally undeployed until the user manually exercises the private workflow. No dashboard-triggered deployment exists. A dedicated Pi exposed a real service-port collision with the retained pre-community kiosk and confirmed R503 serial communication after conversion work; the v0.9 installer now fails safely on collisions and configures the serial link at every start. End-to-end v0.9 fingerprint attendance acceptance is still pending. A 1:1 browser implementation of the physical kiosk remains explicit future work: it must share the kiosk screen and attendance behavior, substitute browser controls only at the hardware boundary, and audit simulated events. The smaller guided-setup simulator remains available.
