# Dashboard interaction contract

The dashboard is keyboard-first: it has a skip link, labeled navigation and controls, semantic headings, live status regions, and no modal-dependent onboarding. It targets WCAG 2.2 A. Automated structural checks and browser verification cover the production React interface.

The dashboard uses real, deep-linkable pages rather than loading every category into one expandable screen. Home, Meetings, Attendance, Reports, Roster, and Kiosks have their own paths. Admin settings have separate Organization, Integrations, Privacy, Data, and Updates paths. A Pages fallback serves the app shell when a user refreshes one of those paths.

The Setup checklist is a persisted installation-level record, not per-user state. Any Admin can resume it. Until it is complete, it temporarily replaces the normal dashboard content and focuses on one task at a time. When the final attendance check is confirmed, an accessible confetti celebration and completion dialog appear; dismissing the dialog moves to dashboard Home. Completed setup is absent from primary navigation but remains reachable from Organization settings and Kiosks. Optional integrations never block completion.

Each completed item records the Admin and time that completed it. Admins can reopen a required item when a configuration needs review; optional integrations use their own status and do not affect the required checklist.

Operators can create and edit meetings, view the roster, manage attendance and reasoned corrections/excuses, export reports, and monitor kiosk status. The physical kiosk resolves the eligible meeting automatically. Operators cannot modify the roster or access organization settings, users and credentials, integrations, privacy controls, updates, or destructive configuration.

Roster is a top-level page. A CSV import is parsed into a preview table before any write, and an Admin chooses whether to add/update rows or replace the active roster. Every member has an editable participation start date, defaulted to the roster-added date; meetings before it remain preserved but are excluded from that member’s attendance obligations and reports. Replacement deactivates omitted people without deleting their historical attendance or linked dashboard credentials. Admins may explicitly link one roster member to one dashboard account and assign Admin or Operator access, or create a non-rostered Admin/Operator account. Roster membership alone never grants authentication, and unlinking a roster member does not delete the dashboard account.

Branding stores an optional bounded PNG, JPEG, or WebP logo directly in D1, never as an externally fetched URL. Organization name and subtitle apply in every appearance. Saved primary and secondary colors theme controls in light, dark, and follow-device modes; semantic success, warning, and error colors stay stable. The UI derives readable button text, trims transparent logo margins for display without changing the stored original, and can automatically add a contrasting light or dark backing. Admins may override that backing. The logo/name/subtitle header returns to Home. The unbranded default remains LancerLogin.

Home begins with a Sunday-through-Saturday, five-week calendar spanning last week, the current week, and the next three weeks. Dates before the current calendar month use a subtly darker surface without changing event colors. Meetings within their scan window show a live roster: one arrival scan is **Active · not checked out**, a completed arrival/departure pair is **Present**, and no complete pair after the organization-wide closing time is **Absent** unless a correction or excuse overrides it. Open Discord contests appear on Home for reasoned review.

Every meeting requires an end time. Meetings may be one-time, daily, weekly, biweekly, or monthly within a bounded date range. The meeting table searches all displayed attributes and supports complete occurrence or future-series edits. Attendance windows cannot overlap, including the one organization-wide late-scan allowance under Organization settings, which defaults to 30 minutes and has no per-meeting override. Kiosks has a dedicated page for pairing/replacement, history, heartbeat, reader state, queue/sync health, installed release, protected maintenance guidance, fixed recovery commands, and the separate browser simulator.

Admins receive a compact dashboard notification when semantic-version comparison finds a newer public GitHub release. The Updates settings page shows installed/latest versions and the release notes. Beginning an update first downloads an entire-installation backup and then opens the guarded private GitHub workflow, where **Latest stable** is the default dropdown choice. The dashboard never stores Cloudflare or GitHub write credentials and never dispatches a deployment itself.

Admins explicitly enable optional integrations before configuration. Enabled integrations sort above disabled integrations; disabled providers appear as condensed rows and are absent from operational controls. Enabled cards remain open while setup or verification is required. A configured card collapses and can be reopened for credential rotation or removal. Google requires an active-Admin OAuth return, Resend requires an expiring emailed code, and Discord requires a bot/server/channel check plus a signed button click. Disabled and saved-but-unverified provider credentials cannot send operational messages. Google cannot be disabled when doing so would leave no usable local Admin sign-in.
