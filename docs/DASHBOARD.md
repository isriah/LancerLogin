# Dashboard interaction contract

The dashboard is keyboard-first: it has a skip link, labeled navigation and controls, semantic headings, live status regions, and no modal-dependent onboarding. It targets WCAG 2.2 A. Automated structural checks and browser verification cover the production React interface. Dashboard meeting creation uses a focus-contained dialog that returns focus to its opener when dismissed.

New or changed dashboard presentation follows the required visual-language contract in [UI-STANDARDS.md](UI-STANDARDS.md). The contract defines the shared token vocabulary, component defaults, responsive expectations, and planning/review checklist while grandfathering unrelated legacy styling.

The dashboard uses real, deep-linkable pages rather than loading every category into one expandable screen. Dashboard, Reports, Roster, and Kiosks have their own paths, and every meeting has a canonical `/meetings/[ID]` operational detail route. Dashboard is the single meeting browser: it remembers a personal Calendar/Table choice, keeps a meeting selector and Add meeting action available in either view, and routes every selected meeting to its detail. Add meeting opens one-time, recurring, and duplicate-based creation without changing the active view or route; a successful creation refreshes the active browser and selector and announces the created count. Legacy `/meetings` bookmarks replace themselves with Dashboard's Table view, `/attendance?meetingId=[ID]` bookmarks replace themselves with the matching detail route, and bare `/attendance` returns to Dashboard. Admin settings have separate Organization, Integrations, Privacy, Data, and Updates paths. A Pages fallback serves the app shell when a user refreshes one of those paths.

The Setup checklist is a persisted installation-level record, not per-user state. Any Admin can resume it. Until it is complete, it temporarily replaces the normal dashboard content and focuses on one task at a time. When the final attendance check is confirmed, an accessible confetti celebration and completion dialog appear; dismissing the dialog moves to Dashboard. Completed setup is absent from primary navigation but remains reachable from Organization settings and Kiosks. Optional integrations never block completion.

Each completed item records the Admin and time that completed it. Admins can reopen a required item when a configuration needs review; optional integrations use their own status and do not affect the required checklist.

Operators can create and edit meetings, view the roster, manage attendance and reasoned corrections/excuses, export reports, and monitor kiosk status. The physical kiosk resolves the eligible meeting automatically. Operators cannot modify the roster or access organization settings, users and credentials, integrations, privacy controls, updates, or destructive configuration.

Reports select the configured operational attendance baseline by default and explain that it excludes earlier completed meetings from the current operational view without deleting them. Operators can choose all preserved history when they need that earlier context. When no baseline is configured, preserved history is the active reporting period and the unavailable operational option is identified explicitly. Report filters affect only the current Reports screen. Attendance percentages use each meeting's saved positive weight; the excuse-adjusted rate removes excused meeting weight from the denominator. The attendance CSV includes the saved category, weight, and weighted contributions for each row.

Roster is a top-level page. A CSV import is parsed into a preview table before any write, and an Admin chooses whether to add/update rows or replace the active roster. Every member has an editable participation start date, defaulted to the roster-added date; meetings before it remain preserved but are excluded from that member’s attendance obligations and reports. Replacement deactivates omitted people without deleting their historical attendance or linked dashboard credentials. Admins may explicitly link one roster member to one dashboard account and assign Admin or Operator access, or create a non-rostered Admin/Operator account. Roster membership alone never grants authentication, and unlinking a roster member does not delete the dashboard account.

Configuration settings include separate late-arrival and early-departure anomaly limits, both defaulted to 10 minutes. Member detail shows mean anomalous time across all preserved completed meetings from that member's participation start date. Each qualifying late check-in or early check-out contributes one value, and the displayed mean is rounded to the nearest whole minute. Reports-page dates and the operational baseline do not change this member statistic, and the anomaly settings do not change attendance outcomes or the separate late-scan allowance.

Settings → Integrations lets an Admin configure Google Calendar independently from Google sign-in. The Admin saves a separate OAuth client, authorizes one Google account, and selects one writable destination calendar. The card names the selected calendar, reports waiting or failed deliveries, and offers a manual retry. It explains that only a generic event name and meeting times leave LancerLogin. The same screen lets an Admin enable Discord anomaly reports and choose a separate private text-channel ID after Discord is verified. The selected channel must belong to the verified server and cannot be the member-facing attendance channel. Each eligible meeting produces one report after its late-scan window closes, while a meeting without qualifying anomalies produces no message. Enabling or changing the channel starts delivery from that point forward and does not backfill older meetings.

When Discord is enabled, member detail shows the paired Discord user ID or a muted **Not linked** state. The Discord identity field is absent while the integration is disabled.

Branding stores an optional bounded PNG, JPEG, or WebP logo directly in D1, never as an externally fetched URL. Organization name and subtitle apply in every appearance. Saved primary and secondary colors theme controls in light, dark, and follow-device modes; semantic success, warning, and error colors stay stable. The UI derives readable button text, trims transparent logo margins for display without changing the stored original, and can automatically add a contrasting light or dark backing. Admins may override that backing. The logo/name/subtitle header returns to Dashboard. The unbranded default remains LancerLogin.

The header exposes the personal light/dark browser preference as a compact switch. Its current state is available visually and to assistive technology, and keyboard or pointer changes persist across reloads.

Dashboard defaults to a Sunday-through-Saturday, five-week calendar spanning last week, the current week, and the next three weeks, with controls to move backward or forward by five weeks and return to today. Dates before the current calendar month use a subtly darker surface without changing event colors. Its alternate Table view retains meeting search and management controls. Each meeting detail owns its live roster: one arrival scan is **Active · not checked out**, a completed arrival/departure pair is **Present**, and no complete pair after the organization-wide closing time is **Absent** unless a correction or excuse overrides it. Meeting detail limits Discord contest review to that meeting, while the top-right contest notifier opens the complete actionable list in a keyboard-accessible popup. Every review surface places the member ID beside the member name, pairs the meeting name with its occurrence date, and refreshes the notifier after a successful resolution.

Every meeting requires an end time. Meetings may be one-time, daily, weekly, biweekly, or monthly within a bounded date range. Admins manage up to 100 active meeting-weight categories in Organization settings. Each category has a positive weight and may have a minimum-duration rule; the first matching active rule in the displayed priority order is the automatic creation choice. Meeting creators may instead select any active category or the default 1× value. Each meeting saves its category name and weight, so later category edits or retirement do not change prior results. Meeting detail shows this saved value, and recurring assignment edits use the same occurrence-only or this-and-future choice as other edits. Dashboard Table view searches all displayed attributes and keeps checkbox selection, bulk delete, and Sync all to Discord independent from row navigation. A meeting detail shows its timing, lifecycle, required/optional status, recurrence, notes, attendance close, and complete attendance workflow. Focus-contained detail dialogs edit or delete one occurrence or that occurrence and its future series, and duplicate the meeting into a new one-time meeting or series. A successful single-meeting deletion returns to Dashboard with Undo. When Google Calendar is configured, creating, editing, hiding, or restoring a meeting immediately attempts the matching one-way Calendar operation and safely leaves any failed delivery queued; it never changes whether the meeting itself was saved. When Discord is enabled and verified, the detail also exposes calendar sync through the scheduled meeting end, absence notification from the scheduled start onward, and reasoned review of that meeting's open contests; ineligible actions remain visible but disabled with timing context. Attendance can be refreshed manually and refreshes every 30 seconds only from scheduled start through the late-scan close. Attendance windows cannot overlap, including the one organization-wide late-scan allowance under Organization settings, which defaults to 30 minutes and has no per-meeting override. Kiosks has a dedicated page for pairing/replacement, history, heartbeat, reader state, queue/sync health, installed release, protected maintenance guidance, fixed recovery commands, and the separate browser simulator. When Discord is enabled and verified, the physical-health card also exposes an authorized manual refresh of its persistent Discord kiosk-status message.

Admins receive a compact dashboard notification when semantic-version comparison finds a newer public GitHub release. The Updates settings page shows installed/latest versions and the release notes. Beginning an update first downloads an entire-installation backup and then opens the guarded private GitHub workflow, where **Latest stable** is the default dropdown choice. The dashboard never stores Cloudflare or GitHub write credentials and never dispatches a deployment itself.

Admins explicitly enable optional integrations before configuration. Enabled integrations sort above disabled integrations; disabled providers appear as condensed rows and are absent from operational controls. Enabled cards remain open while setup or verification is required. A configured card collapses and can be reopened for credential rotation or removal. Google sign-in requires an active-Admin OAuth return, Google Calendar separately requires Admin authorization and one writable calendar, Resend requires an expiring emailed code, and Discord requires a bot/server/channel check plus a signed button click. Disabled and saved-but-unverified provider credentials cannot send operational messages. Google sign-in cannot be disabled when doing so would leave no usable local Admin sign-in; Google Calendar has no effect on that safeguard.

The Discord integration card also owns the Admin-only attendance-channel manager toggle and contest-window setting. Its native switch and bounded numeric control follow the shared Settings control treatment on desktop and mobile. Operators cannot view or change these settings. Enabling the mode preserves the configured channel as the sole management boundary and activates the pinned status, guidance, and tracked-notice expiry workflow after Discord is verified.
