# Temporary database unavailability (WU-141)

Dependencies: the existing Worker exception boundary and dashboard setup-status/sign-in handling. This change does not bypass account limits, change billing, retry database operations or alter provider resources.

`database-unavailable.ts` recognizes a fixed daily D1 row-read quota sentence, including the exact observed REST limits-documentation suffix. It requires structured Error provenance: a `D1_ERROR` wrapper or numeric provider code 7500, with at most six own-data-property cause links and bounded message lengths. Plain similarly worded Errors, string codes, arbitrary suffixes, untrusted plain objects, accessor fields and unknown failures are not classified. Recognition never reflects provider text, SQL, account limits, credentials or links.

The API returns HTTP 503 with fixed code `database_temporarily_unavailable` and a retry-later message. It does not attempt the telemetry diagnostic database write for this recognized condition. Unknown failures retain the existing configured-deployment generic HTTP 500 behavior. This classifier uses locally tested REST-derived wording: the exact deployed Worker binding exception shape has not yet been observed. It therefore does not establish that the hosted outage will be classified; unknown binding variants remain unknown until separately verified.

A dashboard setup-status 503 displays a temporary-unavailable screen with static wait/reload guidance instead of deployment-workflow advice. Other setup failures retain the existing fallback. A local sign-in 503 displays a service warning and does not mark username/password invalid. Neither UI reads or displays the failed response body, automatically retries nor starts setup because the service is unavailable. Initial unavailable screens cannot load adopter branding; they use the saved light/dark theme and existing centered-state tokens. No new control or styling exception is introduced.

Focused verification uses `node --test tests/database-unavailable.test.mjs` for actual Worker entrypoints with synthetic D1 failures, and `npm run test:browser -- database-unavailable.spec.ts` for actual dashboard startup/sign-in against mocked HTTP responses. Browser checks cover 1280x900/390x844, light/dark, reduced motion, no overflow, no raw provider text and unchanged unknown-error fallback. These tests do not consume hosted D1 reads or prove quota-reset timing, Worker binding wording, or the cause of different direct/proxied responses.
