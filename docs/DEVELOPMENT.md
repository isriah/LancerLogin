# Local development and verification

LancerLogin uses focused checks during implementation and one complete gate when preparing a release. All commands are local and use mocks or an isolated local D1 database; they do not contact or deploy to an adopter's Cloudflare account.

Read the guide for the surface you are changing and use its stated acceptance criteria. Keep implementation, verification, and review focused on that surface.

Use Node.js 24.22.1, the exact version in `.node-version` that every GitHub workflow pins (`tests/node-version.test.mjs` enforces this), and install dependencies with `npm ci --no-audit`. This runtime includes the [Windows shutdown fix](https://github.com/nodejs/node/pull/61999) needed for reliable Wrangler CLI checks. Older Node 24 builds can crash after the CLI correctly rejects invalid configuration; keep the test's exit-code and error assertions intact.

The lockfile uses Vite 7.3.7 and overrides Miniflare's Undici dependency to 7.30.1 for the October 2026 security fixes ([Vite advisory](https://github.com/advisories/GHSA-rq7h-c2jc-7f22), [Undici advisory](https://github.com/advisories/GHSA-4qv8-2p9j-2685)). Keep the override until the pinned Miniflare dependency itself selects a patched version, then remove it with a strict audit and affected local-runtime tests. Do not broadly refresh Wrangler or unrelated dependencies to clear an audit finding.

## During implementation

For a new bundled module, follow [module authoring](MODULE-AUTHORING.md) for registration, authorization, setup, jobs, persistence, backup and lifecycle requirements. To run Core with a plugin from a local folder, use `npm run plugins:dev -- --plugin <folder>`; see [writing a plugin](PLUGIN-AUTHORING.md#develop-locally).

New installations start with the release organization colors, primary `#B80100` and secondary `#EEB822` (`product.defaultTheme` in `packages/shared/src/product.ts`). A development Worker can set the optional `DEFAULT_THEME` var to `development` to start with the purple development colors `#7c3aed` and `#0f766e` instead, so its dashboard is easy to tell apart from a release. `npm run plugins:dev` sets it for local previews; production Worker configuration never does. The var only affects first-Admin setup and the dashboard's fallback before branding loads. Existing installations keep their stored colors.

Run the smallest command that covers the files being changed:

| Area | Command | Coverage |
| --- | --- | --- |
| Worker API and shared policy | `npm run verify:api` | API JavaScript and TypeScript tests plus API/shared typechecks |
| Dashboard | `npm run verify:dashboard` | Dashboard behavior tests plus dashboard typecheck |
| Public documentation | `npm run verify:docs` | Static documentation content and accessibility assertions |
| Raspberry Pi kiosk | `npm run verify:kiosk` | Kiosk, installer, extracted release-artifact smoke tests plus kiosk typecheck |
| GitHub/Cloudflare provisioning | `npm run verify:provisioning` | Account-neutral workflow, setup, maintenance, and template checks |

For a changed browser interaction, use `npm run test:browser -- <test-file-or--grep>` during implementation and private acceptance. Run the unfiltered suite locally only when the change affects the whole browser application or a fresh manual preflight is explicitly needed. The exact public release commit runs the unfiltered suite in CI. The wrapper gives each worktree its own transform cache and deterministic three-port range and refuses to reuse an existing fixture server.

Optional modules have checked-in verification manifests under `module-tests/`. Use `npm run verify:module -- list` to inspect every declared selection, `npm run verify:module -- fast <module-id>` for the under-one-minute logic loop, and `npm run verify:module -- acceptance <module-id>` for the ordinary module gate with relevant API, contract, browser, typecheck, and build coverage. The first-party ID is `attendance`; `hour-tracking` (also accepted as `outreach`) is the official Outreach plugin, `carpool` the Carpool plugin and `visits` the Guest Visits plugin, and each manifest names the test selection that composes it (`pluginSelection`). Composition includes Core's official modules (`scripts/official-modules.json`) by default, so `tests/fixtures/official.modules.json`, an empty selection, composes Outreach alone. Plugin browser specs need the plugin composed into the checkout: `node scripts/run-browser-tests.mjs --compose-selection tests/fixtures/official.modules.json tests-browser/outreach-workflow.spec.ts --workers=1` (or `tests/fixtures/carpool.modules.json` for Carpool, or `tests/fixtures/visits.modules.json` for Guest Visits, each of which also includes Outreach) composes it before the run and restores the plugin-free defaults afterwards. Without it, the plugin's specs report as skipped. TypeScript tests compose through `tests-ts/fixtures/outreach-plugin.ts`, `tests-ts/fixtures/carpool-plugin.ts` or `tests-ts/fixtures/visits-plugin.ts`; set `LANCERLOGIN_REQUIRE_OUTREACH_PLUGIN=1`, `LANCERLOGIN_REQUIRE_CARPOOL_PLUGIN=1` or `LANCERLOGIN_REQUIRE_VISITS_PLUGIN=1` to fail instead of skipping when a plugin repository is unavailable. Test processes share each composition through a cache in the OS temp folder (`lancerlogin-test-compositions`), keyed by the effective pins and the content of the composer and the Core files it validates against, so a run composes each set of pins once; set `LANCERLOGIN_TEST_COMPOSITION_CACHE=0` to compose afresh in every process. The pins name the public `https://github.com/isriah/lancerlogin-outreach.git`, `lancerlogin-carpool.git` and `lancerlogin-visits.git` repositories. Tests and the module and browser runners fetch a pin with `LANCERLOGIN_PLUGIN_TOKEN` when it is set (needed only for private plugin repositories); otherwise they use a local checkout of the same repository name that contains the pinned commit, found in `LANCERLOGIN_PLUGIN_CHECKOUTS` (directories separated by the platform path delimiter), `../module-plugins` or `.local/module-plugins` beside the Core checkout; otherwise they fetch the public repository anonymously. When a pin cannot be fetched, for example a private repository without a token or no network, plugin tests skip and name what is missing, except where a REQUIRE variable is set: `verify:module` sets it for every plugin its manifest composes (Core's official modules included), and the Verify `verify` job and private Quick check set all three, so there an unreachable pin fails the run. `LANCERLOGIN_OUTREACH_PLUGIN_SOURCE`/`_COMMIT` `LANCERLOGIN_CARPOOL_PLUGIN_SOURCE`/`_COMMIT` and `LANCERLOGIN_VISITS_PLUGIN_SOURCE`/`_COMMIT` replace a pin for every test and runner, which is how each plugin repository's CI verifies its own commit against a pinned Core commit. Core's Verify workflow passes the optional `LANCERLOGIN_PLUGIN_TOKEN` repository secret to its test steps for private plugin repositories. The runner fails on unknown modules, missing files or workspaces, invalid fast-mode work, and empty selections. Use direct `node scripts/run-browser-tests.mjs <files>` selection when diagnosing a browser failure. Shared contract changes still require the affected existing consumers, and the full product gate retains discovery of every test.

If a change crosses areas, run each affected scope. Migration changes also require `npm run verify:migrations`. That command verifies the complete fresh schema and rehearses a synthetic Community database from migration `0038_page_walkthroughs.sql` through the current append-only chain. The rehearsal checks preserved data, settings, reports, walkthroughs, provider grants, and legacy kiosk queue state without contacting providers or a physical Pi.

### Quick check

`npm run check:quick` is the edit-loop check. It compares the checkout with its base (the merge base with `--base REF`, `LANCERLOGIN_CHECK_BASE`, `git config lancerlogin.checkBase`, the branch's upstream or `origin/HEAD`, in that order) and includes staged, unstaged and untracked files. It typechecks the workspaces those files belong to, with shared contracts and root build files typechecking every workspace, and runs the JavaScript and TypeScript tests that name a changed file in their text, reach it through their static closure, or declare it, plus any changed test. The closure follows `import`, `export … from`, literal `import()` and JSON imports from every file, and, in `tests/`, `tests-ts/`, `scripts/` and `private/`, string literals that name a repository file (scripts under `scripts/` are followed as spawned; other named files are leaves). It never infers a folder, so a test or helper that reads files it can't name, such as a `readdirSync` of migrations or a `cpSync` of plugin fixtures, declares them with a `// quick-check: covers <glob>` line, which every test importing that helper inherits; `tests/check-quick.test.mjs` fails when a literal directory read in test code is undeclared or a declared glob matches no file. Root `package.json`, `package-lock.json` and `tsconfig.json` keep their own rule: every typecheck and the small default set, which also runs when nothing maps. A plugin pin or composition change (`scripts/official-modules.json`, `scripts/known-modules.json`, `tests/fixtures/*.modules.json`, `module-tests/*.json`, `scripts/compose-modules.mjs`, `scripts/test-plugin-sources.mjs`) also runs `verify:module -- fast <id>` for each affected plugin, which fails rather than skips when the plugin can't be fetched, and runs `module-composition`. It prints each selection with its reason, notes changed files that nothing selects, and exits nonzero on any failure. Physical kiosk suites never run there, and a few other suites slower than ten seconds run only when they are the changed file. Add `--list` to preview, `--list --why <path>` to see the chain by which each test reaches a file, or `--all` to typecheck everything and run every fast test. The private Quick check workflow passes `--selection text`, which keeps only the text match (no closures, headers or module gates) to save Actions minutes; the local check and the pre-push hook use the full selection. It is a development aid, not a gate: it sees no computed path that nobody declared, no remote plugin code beyond the pin, and runs no browser tests. Exit status 1 means a check failed and 2 means it could not start.

To run it before every push, opt in with `npm run hooks:install`, which sets `core.hooksPath` to the tracked `.githooks` directory for this repository; `npm run hooks:uninstall` removes it. The pre-push hook blocks the push only when a check fails, and `git push --no-verify` bypasses it once. It does nothing when `CI` is set or `node_modules` is missing, and pushes with a note when the check cannot start. Nothing installs it automatically.

### Web development gate

Minor development changes and private checkpoints need only the affected checks above, plus focused browser coverage for changed interactions. A dashboard style, report, integration or documentation change does not require physical kiosk testing unless it affects kiosk behavior or a shared contract.

For a combined web candidate, use `npm run verify:dev`. It validates local migrations, typechecks the API, dashboard and shared package, runs all JavaScript and TypeScript tests except `tests/kiosk-runtime.test.mjs` and `tests/kiosk-artifacts.test.mjs`, builds the API/dashboard and validates templates. API pairing, attendance, security, web kiosk and recovery coverage remains included. It does not run browser tests; select the relevant browser files separately. Preview the test selection with `npm run test:web -- --list`.

Run `npm run verify:kiosk` as well when changing kiosk runtime, installation, packaging, kiosk dependencies or contracts consumed by the kiosk, including pairing, scan delivery, offline queues and maintenance responses. Assess shared code and dependency changes for their consumers. The web gate selects a fixed scope, not an automatic changed-file analysis.

Before publication, retain the affected private checks and compare the exported product content with the accepted source. Do not repeat `verify:release` or the unfiltered browser suite solely because an unchanged candidate was exported. The exact public trusted-branch commit whose message starts with `Release v` runs the one complete release gate, including all source tests, the unfiltered browser suite, strict audit and Linux kiosk artifact checks.

### Documentation changes

Classify a documentation surface as current guidance, reference, historical evidence, or generated output before changing it. Use the released interface labels, keep private installation details out of public material, and run `npm run verify:docs` after changing maintained documentation. Add focused reference, command, boundary, or asset checks when the static documentation test does not cover a meaningful risk.

Static site and Markdown changes need a rendered review at the affected desktop and mobile sizes. Check headings, keyboard focus, links, captions, alternative text, and clipped content. A web kiosk, the virtual kiosk, source inspection, or a local mock is not physical kiosk acceptance. Do not run a release gate, deployment, update, or destructive recovery command merely to verify prose.

### Dashboard visual changes

Web-update API checks use isolated real SQLite for unique-lock/audit/idempotency and retryable disk-queue replay. Provisioning checks include canonical migration hashes, official release/resource/credential guards, actual Pages identity and explicit recovery. `npm run rehearse:web-upgrade` runs an eleven-case provider-free synthetic bridge/V1/failure matrix. It is not fresh-adopter or live provider/Pi acceptance. Review compatibility-manifest ownership and secure rehearsal requirements in [WEB-UPDATES.md](WEB-UPDATES.md); workflow changes also require actionlint.

Reuse shared UI tokens and controls; verify keyboard focus, themes, desktop and mobile layouts and behavior. For each new panel, enumerate its action buttons and file chooser, use the shared `ui-button` roles or an established scoped control, and add focused browser assertions for the rendered styles in light and dark themes. Include controls revealed by previews or role changes. Do not expand a focused change into a retrofit of unrelated styling.

## Virtual kiosk

`npm run kiosk:virtual` runs the real kiosk service on this computer with fake hardware, paired to a local preview. The first run creates a local Admin (`virtual-admin`, password in `.provision/virtual-kiosk/admin.json`), the synthetic members Test Student A, B and C, and Test meetings A and B, then pairs **Virtual kiosk 1**. It prints a control panel link that shows the kiosk screen beside buttons to pair, unpair, restart or reboot the kiosk, and to make the Worker unreachable so scans queue offline. Options: `--kiosks 2` for up to four kiosks, `--reset` to start over, `--no-dashboard`, and `--port-base` (default 8790). State is kept in `.provision/virtual-kiosk` between runs.

The kiosk service gets its hardware from `apps/kiosk/src/kiosk-platform.mjs`; the virtual kiosk replaces those hooks before it loads the service, and a Pi uses the defaults. Each virtual kiosk has a virtual R503 fingerprint reader (`scripts/virtual-kiosk/virtual-r503.mjs`) that answers the kiosk driver's real command packets. In the panel, tap a member's finger 1 or 2 on the reader, tap an unknown finger, or set faults: a faint, messy or unusable next read, no match, a weak match score, a slow reader or an unplugged one. Enroll fingers from the dashboard's **Manage kiosk** page or the kiosk's maintenance screen, as on a Pi. The reader keeps its stored fingers in `.provision/virtual-kiosk/readers` across restarts and unpairing. It doesn't transfer templates, so fingerprint sharing between kiosks isn't covered. The panel also sends the six dashboard kiosk commands as the **Manage kiosk** page does, chooses whether the next update installs or fails, and whether the next boot has network time (without it, the kiosk asks for the date and time). A virtual kiosk reports release 2.0.0, so the dashboard offers it updates, and reports the requested release after an update installs; it keeps running this checkout. Each kiosk has its own network: Ethernet, the synthetic Wi-Fi networks **Virtual Lab** (password `virtual-lab-1`) and **Virtual Guest**, or none. Join Wi-Fi from the kiosk's own settings with the settings PIN `246810`, or set the network in the panel. Without a network, the kiosk can't reach the Worker. After updating from an earlier virtual kiosk, run it once with `--reset`: each kiosk now reaches the Worker through its own port. `npm run test:kiosk-virtual` runs the scenarios in `tests-virtual-kiosk/` against a fresh virtual kiosk. The release gate runs them too, as the **Virtual kiosk browser** job in a dispatched **Verify**. Real hardware still needs a spare kiosk: the sensor, serial timing, the display, boot and the update service.

## Release preparation

Use the affected verification commands, focused browser files and product review to accept the private candidate. Before export, run `npm run verify:release` on the candidate. Do not run the browser groups locally for release preparation: the public release gate runs all three (core, plugin and integration). If that gate fails, fix the candidate and export it again.

Once `verify:release` passes, export the candidate and start the public release gate at once, and run the [local update rehearsal](#local-update-rehearsal) (and, when it applies, an upgrade of a development installation) while the gate runs. The gate and the rehearsal check different things and neither waits for the other. Export again only when the rehearsal or the development upgrade finds a problem; a clean result needs no second export. A development-installation upgrade adds coverage only when the release changes migrations, the web updater, provisioning or plugin composition. Tell from the diff between the previous release tag and the candidate: when this prints nothing, skip it.

```sh
git diff --name-only <previous release tag> <candidate> -- apps/api/migrations apps/api/src/module-migrations.ts apps/api/wrangler.jsonc \
  apps/api/src/web-updates.ts 'apps/dashboard/src/web-update*' 'scripts/*web-upgrade*' 'scripts/*web-update*' .github/workflows/upgrade-web.yml .github/workflows/refresh-web-update-credential.yml \
  'scripts/*provision*' 'scripts/*cloudflare*' scripts/prepare-pages-proxy.mjs scripts/ensure-fingerprint-vault-key.mjs scripts/d1-maintenance.mjs scripts/database-identity.mjs .github/workflows/provision-template.yml \
  scripts/compose-modules.mjs scripts/check-module-composition.mjs scripts/official-modules.json scripts/known-modules.json scripts/resolve-plugin-releases.mjs packages/module-sdk ':(glob)**/generated/**'
```

A change to the `wrangler` version in `package.json` also counts. When unsure, run the upgrade.

The GitHub **Verify** workflow uses two scopes. Pull requests and `main` or `modular` pushes run `verify:dev`, adding `verify:kiosk` only when kiosk code, packaging, shared contracts or root dependencies changed. Only a manual run runs the complete release gate: dispatch it on the exact release commit before tagging. Fast-forwarding the trusted branch to that commit afterwards runs the scoped checks, not the complete gate a second time. `verify:release-ci` executes migration verification, every workspace typecheck and build, all web tests and the kiosk runtime suite. The root-owned Linux kiosk artifact test runs separately so it is not repeated inside that command.

The complete gate runs the browser suite in three groups, assigned per spec file by feature area in `tests-browser/groups.json` (`scripts/browser-groups.mjs`):

- **Core** (four **Core browser shard** jobs, plugin-free): every Core spec, including the integration specs.
- **Plugin** (one **Plugin browser shard** job): only the specs that need the official Outreach or Carpool plugin and skip entirely without it, with both plugins composed from `tests/fixtures/carpool.modules.json`.
- **Integration** (one **Integration browser shard** job): the Core specs whose behaviour changes when plugins exist (module navigation and slots, Settings > Modules and plugin management, module setup, backup and restore, shell and startup, and any Core file with individual plugin-dependent tests), run again composed.

This runs each test once plugin-free and only the plugin-sensitive ones composed: about 710 browser tests instead of about 1,220 when the whole suite ran in both modes. `npm run test:browser -- --group <core|plugin|integration> [--compose-selection <file>] [--part i/n]` runs a group locally; the runner refuses the core group with composition and the plugin and integration groups without it. `--part` splits a group into whole spec files balanced by the approximate CI seconds recorded for each file in the manifest. Playwright's own `--shard` splits by test count in file order, which put most slow specs in one shard. `tests/browser-groups.test.mjs` fails when a spec file is not assigned, when a spec that skips entirely without a plugin is outside the plugin group, or when a spec with individual plugin-dependent tests is not an integration spec, so add every new spec to the manifest. When a spec's run time changes a lot, update its `seconds` so the parts stay even; the parts currently take about six minutes each on a CI runner. `node scripts/browser-groups.mjs --refresh-seconds <report.json> [...]` sets each reported file's `seconds` from Playwright JSON reports (the sum of its tests' first attempts); give it the reports of every shard from one CI run, not a local run, since a local machine weighs specs differently.

Composition fetches public pins anonymously, sends the `LANCERLOGIN_PLUGIN_TOKEN` repository secret only when it is set (needed only for private plugin repositories), and fails the shard, rather than skipping its specs, when a pinned plugin cannot be fetched. The `browser-smoke` check passes only when every shard of all three groups passes. In CI each test gets one retry; every shard writes a Playwright JSON report, lists the tests that passed only on their retry in its job summary, and uploads the report as a `browser-report-<group>-<part>` artifact. The shards do not share a prebuilt dashboard. In CI, Playwright builds the dashboard for production in each shard's own checkout as its server starts (`scripts/serve-dashboard-build.mjs`: `vite build` with the shard's mock API address, without the `tsc` and composition checks that Verify runs, after any plugin composition) and serves it with `vite preview`; the spec files themselves read the composed module registry from that checkout. The build takes seconds and depends on the shard's ports and plugins, so a separate build job would add a job and an artifact without removing work. A production build drops dev-only behaviour such as React StrictMode's double mount, so Core shard 4 also runs `dashboard-smoke.spec.ts` and `ui-foundations.spec.ts` on the Vite dev server. Locally the dev server stays the default; add `--server build` to `npm run test:browser` to test the build the way CI does. Every spec runs in UTC with the `en-US` locale unless it sets its own `timezoneId`. Each shard restores the Playwright browser from a cache keyed to the locked Playwright version and installs only the system dependencies on a cache hit. GitHub shares caches only from the default branch, so the separate **Keep Playwright browser cached** workflow refreshes that cache on the default branch twice a week; it is not part of Verify and adds no required release job. The test step has its own 15-minute limit inside a 30-minute job, so slow runner setup cannot cancel tests that are still passing. It also runs the strict dependency audit. Verification and browser jobs install with `npm ci --no-audit`; security findings come from the one explicit audit job rather than duplicate implicit audits. Dependency-manifest changes and scheduled monitoring can still run that audit before a release. No tag may be created until the exact public release commit's complete Verify run passes.

The tag workflow does not repeat the full gate. It requires exactly these eleven successful **Verify** jobs for the exact tagged commit: `actionlint`, `verify`, `dependency-audit`, `browser-smoke`, **Core browser shard** 1/4 to 4/4, **Plugin browser shard 1/1**, **Integration browser shard 1/1** and **Virtual kiosk browser** (`requiredJobs` in `scripts/release-publication.mjs`). The run must be a maintainer-dispatched run on that same commit. A complete run from a push to the selected trusted source branch also counts, which only releases before v2.0.0-beta.16 have, since pushes no longer run the complete gate. A dispatched run counts only after the commit is confirmed to be on the trusted branch; it runs that commit's own workflow, so the release does not need a second identical run after the branch is fast-forwarded. The tag workflow also checks the version and patch-notes file, and packages both kiosk archives with the same utility tested by `verify:kiosk` and `verify:all`. It uploads a source-bound release bundle and publishes nothing. A manual run from `main` can package an existing verified tag without moving it.

A maintainer runs `node scripts/release-publication.mjs publish TAG RUN_ID` from the reviewed publication-tools checkout to check the bundle, then adds `--publish` to explicitly assemble and publish the immutable release. The command uses the existing GitHub CLI login, independently rechecks full CI, the tag, bundle digest, six asset hashes, notes, immutability and Latest policy, and never replaces a published release. It also refuses, in the check too, when nothing under `docs-site/` or `docs/` (excluding `docs/releases/`) changed since the previous published release in the same line (stable or beta, falling back to the newest older release of either line), so every release reviews its documentation; when none needed to change, add `--docs-unchanged "<reason>"` (at most 300 characters), and the JSON output records the reason. The immutability preflight needs Administration-read access, which the built-in Actions token cannot provide. Do not store an extra credential in Actions or remove the preflight. See [update tracks](UPDATE-TRACKS.md).

### Local update rehearsal

`npm run rehearse:update -- --from <ref> --to <ref>` upgrades a synthetic installation from one release to a candidate on this computer. Use it for every release candidate and whenever web updates, migrations, provisioning or plugin composition change. A release tag such as `v2.0.0-beta.12`, or any `public:<ref>`, is fetched from the public repository; other refs (`origin/main`, a commit) resolve in the development repository. While a candidate still carries the previous version, add `--target-tag v2.0.0-beta.13` so the migration policy sees a forward update. `--selection <file>` replaces the default plugin selection (`tests/fixtures/carpool.modules.json`, Carpool pinned to its released commit), `--report <file>` chooses where the Markdown and JSON reports go, and `--keep` keeps the temporary folder for inspection.

The rehearsal exports both trees with `git archive` into a new temporary folder, installs each with `npm ci --no-audit`, and composes the official modules and the selection with each tree's own composer. It builds FROM's Worker with `wrangler deploy --dry-run`, applies FROM's migrations to a local D1 database with `wrangler d1 migrations apply --local`, runs the Worker in Miniflare and seeds data through the API: the first Admin, a roster, meetings and attendance, module enablement and setup, Outreach labels, teams, activities and entries, a Carpool plan with participants and a paired synthetic kiosk. It then snapshots every table and runs TO's own `executeWebUpgrade` with a local adapter: TO's migration policy, first-party module check, composition and extracted-module guard, the API and dashboard builds in CI mode (so the composition build guard runs), a checkpoint copy of the database, the local migrations, the fingerprint storage key step, the API Worker and the generated Pages `_worker.js` in Miniflare, and TO's post-deployment health predicate. Before that it proves the refusal path: a selection without Carpool must stop with `module_migration_required` and leave the database unchanged. Afterwards it checks preserved rows and key records, the plugin catalog and migration ledger, Outreach and Carpool endpoints, sessions and sign-in, the kiosk credential, roster and roster revision, and the Pages proxy including the `//host` escape check, then runs TO's no-cloud updater tests.

Nothing leaves the computer except anonymous fetches of the pinned public plugin commits. Wrangler runs with an empty home, no credentials and a loopback-only Cloudflare API origin, and both Workers refuse and record every outbound request. The rehearsal does not cover Cloudflare deployment, D1 time travel, secrets, propagation, the GitHub dispatch and deployment repository, maintenance-mode write suspension, browser rendering or physical kiosks; the report lists these. Links inside the temporary folder (npm workspace junctions) are unlinked before it is removed. The command exits nonzero when any check fails.

## Kiosk artifact verification

`node scripts/package-kiosk.mjs <new-output-directory>` builds both ARM64 and ARMv7 archives, the versioned installer, and their SHA-256 files. The output directory must not already exist. The shared packager copies every runtime `.mjs` file, then verifies checksums and extracts each archive into an operating-system temporary directory outside the checkout. A child Node process loads the extracted service and serves its real health and screen assets using isolated empty state with hardware and background polling disabled. The test suite also removes `update-command.mjs` from an extracted archive and requires startup to fail even though that file remains in the checkout.

The packager writes portable ustar archives with explicit header modes: `0755` for every code directory (including the archive root) and shell helper, and `0644` for runtime modules and service/policy files. Every host validates these archive modes before extraction, even when the checksum is valid. POSIX hosts additionally validate the extracted modes. The installer normalizes the code tree before and after extraction, rejects unexpected links, and leaves `/var/lib/lancerlogin` as private `0700` state. The same checks apply to fresh installs and the official update helper's installer path.

Windows runs the import/HTTP tests but cannot establish Linux permission safety. The complete GitHub Verify gate additionally runs `sudo "$(command -v node)" --test tests/kiosk-artifacts.test.mjs` on Linux. Its root-owned extracted artifacts must start after the child drops to the non-root `nobody` UID/GID, explicitly re-enters the runtime directory, and asserts the code belongs to a different account. State is a separate private temporary directory owned by that account. A `0700` root must actually fail with `EACCES`; the installer's repair must restore startup. The tag workflow requires `sudo "$(command -v node)" scripts/package-kiosk.mjs <new-output-directory> --require-unprivileged` on the exact archives it publishes. This option fails unless running on Linux as root and must not be removed to bypass a failed release gate.

Source-tree tests alone are insufficient evidence for kiosk releases. Keep new runtime assets in the shared packaging path and extend artifact checks when adding a new asset type, runtime subdirectory, dependency, or entry point. These checks do not establish physical UART/R503, systemd, Chromium, or installed-Pi behavior; check those on a physical kiosk after upgrading it.
