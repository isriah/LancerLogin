# Discord attachment feasibility (WU-143)

Dependencies: the approved development Discord application/server, active paired synthetic member, verified shared Discord/Google Drive connections and explicitly selected private development Drive root. This module-independent spike is enabled only at `https://lancerlogin-v2-example-dashboard.pages.dev`. It is unavailable at any other configured origin even if its command remains registered. No additional provider resource, permission, public upload flow or P4 domain is introduced.

## Exact synthetic inputs

Use the checked-in files in `experiments/discord-attachment-spike/`: `LancerLogin synthetic attachment.png` (32x32 geometric image) and `LancerLogin synthetic attachment.pdf` (one geometric page, padded to approximately 600 KiB). `manifest.json` and the API manifest pin their exact MIME, length and SHA-256. No personal content belongs in this experiment. The modal accepts one file, with a 1 MiB streamed ceiling; exact fixture matching rejects all other bytes, including corrupt, encrypted and unsupported documents. A rejected file requires using the provided fixture.

This verifies transport and private persistence of known synthetic bytes. It does not parse arbitrary hostile PDFs/images or establish final P4 intake limits. General content validation and its compute placement remain a P4/runtime dependency. The ceiling is a proposed spike limit; hosted evidence measures the actual fixture size, not every size up to that ceiling. No parser dependency is added to the API.

## Interaction and transfer

Command reconciliation adds `/attachment-proof` only for the exact development origin, preserving pairing, attendance, Hours and unrelated commands. A current paired active member in the configured guild/application receives a modal with a Label (18) containing File Upload (19). The five-minute opaque modal belongs to that member and the original provider IV, shared Google generation/IV and root revision. The signed modal submission resolves exactly one selected attachment ID from its own resolved map. Submission immediately defers privately; no file download precedes that acknowledgement.

The downloader accepts only HTTPS `cdn.discordapp.com/attachments/<snowflake>/<selected-id>/<filename>` with no userinfo, port, fragment, redirects or encoded path separators. It validates the signed URL's hex issue/expiry fields and 64-hex signature shape, then fetches without bot authorization. Size metadata, Content-Length when present, streamed length and exact fixture digest must agree. Download/body reads have six-second bounds and a 1 MiB ceiling. The original CDN URL, interaction webhook token and source filename are never stored or logged. The background transfer has a 25-second local budget; late work cannot pass its database fence. Provider URLs and bodies are never emitted as errors.

Before creating a Drive file, the selected root must still be an owned, untrashed folder with exactly owner-only permissions. Google allocates one fresh file ID; the operation records that ID, expected digest/size/MIME and pending state before its one multipart create. The only parent is the selected root. There is no update/overwrite endpoint, permission mutation or automatic retry. A successful readback must confirm exact ID, operation marker, MIME, size, SHA-256, parent and owner-only file permissions before `saved`. Current pairing, Discord verification/enablement/IV, Google IV and root revision fence dispatch and final persistence. Changing a grant can safely require a new attempt. Drive permission reads and creation are not atomic against external owner edits; keep the synthetic root exclusively controlled during acceptance.

Private follow-up failure cannot rewrite an already saved result. Duplicate modal delivery does not redownload or create another file. The receipt ID is returned privately for coordinator readback; no evidence gallery is exposed.

## Readback and recovery

Current Admins can GET `/admin/integrations/discord/attachment-proofs/:id`. POST the same path plus `/reconcile` with `{ "confirmation": "VERIFY SYNTHETIC ATTACHMENT" }` to perform read-only provider verification of a pending receipt. It never repeats the create. Status returns only the opaque proof/file IDs, state and fixed content metadata. A saved status is the historical verification result, not a fresh guarantee that an owner has not subsequently changed permissions or content; GET and a reconcile of an already saved receipt make no provider calls. Hosted acceptance must independently verify current privacy.

Migration 0039 stores at most 16 receipts and excludes them from portable installation JSON backups, like the existing Drive experiment. Before any destructive recovery, the maintainer must retain an exact private inventory of proof IDs and allocated Drive IDs. Installation deletion/restore is atomically blocked while a pre-dispatch transfer is active or any receipt is pending, including after its lease expires. An expired processing row cannot pass the pending-state CAS and start a create after restore. An uncertain create remains pending with its known destination identity; a successful matching readback clears that guard by marking it saved.

A pending file returning 404, provider rotation or lost access may require explicit coordinator investigation outside this spike. There is deliberately no automatic absent-file resolution, receipt deletion, provider cleanup or retry. Such a pending receipt can block installation recovery indefinitely until reviewed; do not relabel it failed merely to bypass the guard. Abort is not proof that Google stopped processing a request. Completed receipts may cascade away only after the maintainer inventory is secured. SQL recovery never deletes Drive files or reverses provider effects; full raw D1 replay preserves transient rows, whereas portable application restore clears their authority.

## Verification and hosted acceptance

Local tests use signed interactions, real local D1, synthetic CDN/Drive fakes, exact fixtures, streamed bounds, private replies, replay, provider rotation, inactive members, wrong parents/permissions, ambiguous creation and installation deletion guards. The canonical recovery graph pins 39 migrations and retains the new transient receipt in raw replay. These are local/mock results.

Coordinator hosted steps: reconcile commands in the approved server; with the paired synthetic member run `/attachment-proof` and submit each provided fixture separately; record acknowledgement and completion latency; read each receipt and independently confirm its private Drive file and matching bytes/hash; verify no public permission. Retain the exact IDs privately. Deliberately interrupted creation is a separate controlled acceptance step: inspect/reconcile the same receipt, never submit a replacement create. No external cleanup or restore is authorized by this implementation.

References: [Discord File Upload](https://docs.discord.com/developers/components/reference#file-upload), [three-second acknowledgement and fifteen-minute interaction tokens](https://docs.discord.com/developers/interactions/receiving-and-responding), [signed attachment CDN URLs](https://docs.discord.com/developers/reference#signed-attachment-cdn-urls). Provider documentation establishes the interaction shape; only hosted tests establish this deployment's acceptance.

## Fixed failure diagnostics (WU-144)

Dependencies: WU-143 receipt state machine and existing installation audit table. No migration or provider contract change is introduced. Current Admin GET adds nullable `diagnostic: {stage, category}`. Evidence uses one receipt-keyed audit row with NULL actor and fixed metadata only; it never stores source names, CDN URLs, payloads, Discord identities, credentials, provider bodies or exception text. The write is fenced to the original receipt, submission and Discord provider IV, including when current provider authority has changed. Missing/restored receipts cannot receive late evidence.

Stages distinguish component shape, selection, resolved map, filename, MIME, size, URL, CDN fetch/status/body, fixture digest, authority, Google access, private root/permissions, ID allocation, pending persistence, upload and final verification/persistence. Categories are fixed `started`, `failed`, `deadline_elapsed`, or `complete` with validated stage pairs. Local body timer expiry, native timeout exceptions and the overall deadline can establish `deadline_elapsed`; no arbitrary error strings are interpreted. The started marker is best effort, and missing terminal evidence does not prove CPU exhaustion: abrupt runtime termination, unavailable D1 and interrupted execution require independent runtime evidence. Diagnostic failure never converts a verified save into failure or authorizes a retry. A later successful pending reconciliation does not erase the historical original-upload diagnostic.

The pre-WU-144 failed receipt cannot acquire a retroactive cause. On September 11, the official [Discord File Upload submitted example](https://docs.discord.com/developers/components/reference#file-upload) confirmed Label `component`, File Upload `values`, and `data.resolved.attachments` match the parser. Signed local tests include Discord's component IDs and ephemeral attachment metadata. No concrete shape mismatch was found, and no MIME/URL/fixture allowlist was relaxed. Source filenames are now bounded nonempty strings instead of exact display-name matches, so a browser download suffix does not reject identical approved bytes. Names are neither retained nor used for Drive creation; the verified manifest supplies that fixed name. Renamed content still must match the exact approved digest. Local actual-D1/provider-mock verification remains distinct from a successful hosted retry.
