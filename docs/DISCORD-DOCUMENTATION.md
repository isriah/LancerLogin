# Private Discord activity notes

Dependencies: WU157 member-note service and provenance, shared signed Discord routing/replies, and migration 0046 transient drafts. `/activity-note` is implemented for the Documentation module. Deployment and external command registration remain separate explicitly authorized operations; this candidate makes no live Discord acceptance claim.

Current active paired members select an active impact-relevant activity in an ephemeral catalog, 25 choices per page. No Hours reporting window applies. The catalog shows only activity title/date and never saved notes, private descriptions, roster records or summaries. Both Hours and Documentation modules, Notes, and the verified Discord connection must remain enabled. Saved application/guild and signed guild-member identity are mandatory. DMs and another actor's controls cannot use the draft.

The private modal uses two labelled paragraph fields, each capped at 4000 characters. The continuation follows the first field **exactly**, without an implicit space or newline. Both raw values are retained and concatenated without trimming or truncation; the shared 8000 UTF-16-unit/nonblank/control-character rules apply to the combined note. Emoji may count as two units. Confirmation shows the selected activity and character count, not the complete private note. Members can edit before confirmation; submission neither records hours nor publishes the note.

Activity and section revisions are checked during modal opening, draft edits and final admission. New draft mutations also fence active pairing and the captured provider IV/current verification. The first confirmation freezes its interaction ID and exact payload atomically. Concurrent confirmations reuse that body/key; later buttons recover only the original acknowledgement. Receipt replay precedes pairing lookup within the shared domain service, so unlinking does not erase an already accepted result. Adapter module/provider gates still apply. Uncertain submissions cannot be edited or assigned a replacement key. After draft expiration, ask Staff to check before sending another copy.

Every reply is ephemeral with implicit mentions disabled. Modal opening performs bounded read-only work within the existing 2500ms deadline. Other interactions defer immediately and edit only their private webhook response. Tokens are never persisted; webhook transport carries no bot authorization and uses the existing 14-minute reply deadline. Failed delivery does not reverse a committed note. Reuse an earlier confirmation button to recover during draft lifetime.

Migration 0046 adds `discord_documentation_drafts`, with authenticated encrypted payloads bound to installation, draft, guild, Discord identity and provider IV. Proposed bounds reuse Hours defaults: 20-minute lifetime, four live drafts per member and 256 per installation. Expired rows are cleaned on subsequent interaction. No token or clear note enters the table or audit metadata. Portable schema 26 remains unchanged: drafts are excluded, installation restore cascades their deletion, and raw recovery includes the table. Durable member notes and receipts use the existing portable contract. The synthetic raw recovery model now pins 46 migrations / 92 tables.

Command composition contributes the exact implemented definition alongside core/Hours commands; reconciliation retains unrelated commands and uses individual managed mutations plus authoritative readback. Disabling a module does not delete commands. Stale commands fail closed. `/attachment-proof` remains a separate synthetic development experiment and grants no Documentation intake authority. Member file intake is implemented separately by WU167 below.

Focused verification uses `node --test tests/documentation-discord-d1.test.mjs tests/member-documentation-d1.test.mjs tests/hour-discord-d1.test.mjs`, `npm run verify:api`, `npm run verify:migrations` and the application recovery suites. All provider HTTP in tests is mocked, with generated signing keys and synthetic D1 data. Hosted latency, private delivery and registration require later approved development acceptance.

## Private activity files (WU167)

Dependencies: WU162 durable original-byte intake, WU165 schema48/backup28, and the existing signed private Discord transport. `/activity-file` selects an active impact-relevant activity using the same bounded private catalog pattern. Files works with Notes disabled and outside the Hours reporting window. Members cannot choose initiatives or read other submissions. Current pairing, verified configured application/guild/provider IV, module flags, Files and selected activity/section revisions fence admission and every shared upload phase.

The modal accepts exactly one File Upload19 inside Label18, up to 4 MiB. Only the selected attachment ID resolved inside the signed interaction is accepted. Filename is validated but not retained; the stored title is Activity file. The response defers ephemerally before downloading. HTTPS signed Discord CDN attachment URLs require the exact selected ID, allowed host/path and unexpired signature fields. Fetch denies redirects and sends no bot header; body length and bounded streamed bytes must agree. The download has a six-second cancellation signal and five-second body bound. Actual-byte SHA256 is frozen before admission; the feasibility experiment's 1 MiB limit and fixture allowlist are not reused.

Migration0049 adds encrypted, 20-minute private file drafts (four per member, 256 per installation), excluded from portable backup28. AES-GCM payloads bind installation/draft/guild/actor/provider IV. Temporary signed CDN authority is encrypted only while transfer needs it; completed chunk intake removes it. Draft cleanup expires remaining authority. Webhook tokens never enter storage. Raw recovery49 includes opaque transient rows and copy inventory; portable restore clears drafts and preserves durable Discord attribution and upload ownership. Database restore does not restore Drive binaries.

First modal submission freezes one interaction ID. Later modal deliveries and Continue / check upload controls reuse its exact metadata, digest, member and operation. A draft lease serializes continuations, while the shared upload lease fences compute and provider work. At most four bounded chunks are dispatched within a 20-second dispatch budget, or one bounded shared phase is attempted per interaction. No background polling loop is created. The private continuation can survive interrupted delivery; platform termination may leave a lease to expire before the same operation resumes. An uncertain result never chooses another file identity or repeats provider creation. After expiry, Staff must inspect the existing upload inventory; do not submit another copy. Expired CDN authority can prevent completion of an unfinished byte transfer.

Only verified shared-service `saved` yields a private saved confirmation. Hours and notes remain independent. Provider registration, hosted latency, runtime capacity and real member transfer remain development acceptance work; local tests use synthetic bytes and provider fakes. Local checks cover actual signed routing, missing signatures, wrong actors/guilds/application, Notes independence, revoked contributor/Files gates, replay, lost provider acknowledgement, byte identity, private delivery, redirect/size rejection and portable restore. Official [component reference](https://docs.discord.com/developers/components/reference#file-upload) and [signed CDN URL reference](https://docs.discord.com/developers/reference#signed-attachment-cdn-urls) were rechecked September11.
