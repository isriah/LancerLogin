# Durable original-file intake (WU162)

Dependencies: shared verified Google connection/storage (WU151), member provenance (WU157/160), private document computation and exact-original readback (WU161). This backend preserves one actual original in Drive and creates a real file artifact only after verification. The upload interface is described below; Discord file intake and native Drive copy remain separate work. P5 packet/publication consumers are deferred by the user.

## Admission and transport

Staff POST `/admin/documentation/uploads` accepts title (1-200), caption (0-4000), MIME, byteLength, SHA-256, sectionRevision, activities/initiatives with current revisions, and an idempotencyKey (16-128 opaque characters). Plain-text limits are UTF-16 units. Public POST `/public/documentation/uploads` additionally accepts the exact entered memberId; it resolves the current member internally. Members require exactly one active impact-relevant activity and cannot select initiatives. The exported service accepts a server-owned public/staff/Discord attribution; no public JSON can choose internal attribution. Existing link artifacts retain their fields and behavior.

A successful admission returns reference, state, nextChunk, chunkSize, maxBytes, expiresAt, saved and a ticket. The ticket is derived using a purpose-bound server HMAC and stored only as a hash. It expires after 30 minutes (or the original staff session expiry, sooner), without renewal. A matching admission retry recovers the same operation and ticket; changed metadata conflicts. A ticket authorizes only that operation and never substitutes for current contributor, module, Files section, activity, root or provider authority. Keep it out of URLs/logs/persistent browser storage.

The public operation prefix `/:reference` supports GET minimal status, PUT `/chunks/:index`, POST `/seal`, POST `/advance`. POST advancement accepts `{}`; no replacement metadata. Use the `x-lancerlogin-upload-ticket` header. Chunks are sequential 256 KiB with a shorter final chunk; an identical repeat is safe, changed bytes fail. The dedicated Pages assertion purpose accepts bounded binary PUT without changing existing Hours/notes assertion protocols. Wrong origins, changed paths/bodies and cross-purpose signatures cannot provide trusted ingress. Untrusted ingress uses the existing restrictive admission bucket. Admissions additionally cap each contributor at 20 operations and the installation at 500 per rolling day. These are technical defaults, not product promises of unrestricted capacity.

The provisional limit is one file up to 4 MiB, matching the local private-compute contract. Hosted capacity remains to be accepted. Files unsupported for embedding can be explicitly linked-only originals; validation is not an antivirus certification. Invalid supported inputs fail visibly. The generated validation preview never replaces original bytes.

## Advancement and independent outcomes

States are uploading, validating, ready, preserving, reconciling, saved, failed and expired. Each request performs one bounded phase or provider chunk. The operation holds immutable source, contributor, metadata, context, declared original commitments, compute identity, original destination and ownership. A 60-second compare-and-set lease serializes advancement. A lost acknowledgement is resolved using the same operation, compute job, reserved Drive ID and encrypted resumable session.

Completed compute metadata and exact original chunks are checked against manifest, snapshot, original and chunk commitments. Whole-original verification reads at most four chunks concurrently, at most 4 MiB total, under a shared 30-second deadline; cancellation aborts outstanding reads. No parser runs in the API. State commits require the same live lease. A rejected input never becomes an artifact.

Drive preservation revalidates the owned private root and permissions, preallocates a file ID, and durably records dispatch before starting its resumable session. Only provider-acknowledged offsets are retained; partial acknowledgements resume the remaining bytes. Timeouts never trigger a second create. A completed file must match its exact ID, operation marker, MIME, size, parent, owner-only permissions and SHA-256. If Drive omits its optional SHA-256 field, bounded exact-ID media readback must match the whole digest. Redirects are not followed. Only then does one atomic batch create the artifact, original revision, context memberships and audit and mark the operation saved. Follow-up/read response failure cannot undo saved state.

Hours and notes are separate outcomes. Their accepted records are never rolled back because a file fails. Members cannot browse files, roster identities, other submissions or the staff operation inventory.

## Curation and recovery

File artifacts use the existing artifact/header/history tables and review workflow, adding kind=file, immutable file metadata and nullable user/member provenance. Metadata editing cannot replace the original URL/bytes. Member authors are real members, not fake staff users. Existing claims retain actual historical artifact revision FKs through migration0047. Explicit staff review remains separate from preservation and publication.

Current staff GET `/admin/documentation/uploads?after=...&limit=...` provides a bounded operation inventory (limit1-50). POST `/:reference/reconcile` verifies the original organizational generation and freshly selected original root; it cannot retarget ownership. It may refresh connection IV/root verification revision. Ownership verification and contribution eligibility remain distinct: if the contributor or original context gates no longer hold, verified ownership remains reconciling with an eligibility-required reason rather than silently admitting the contribution. Restore the required eligibility or retain the operation for explicit coordinator handling. An uncertain ID returning404 is not proof that the remote write never happened. There is no automatic deletion, absence clearance or replacement create. An expired compute job/session may leave a manual reconciliation requirement.

Portable backup27 includes durable operation/file inventory and original provenance. It excludes ticket and resumable credentials and live leases. Restore expires undispatched incomplete operations and leaves dispatched incomplete operations reconciling; it never resumes provider authority. Shared root verification must be performed again. Atomic installation guards reject live/uncertain writes and backups omitting or changing known file ownership. A database restore does not restore or delete Drive binaries. Attendance-only restore leaves this domain intact. Raw recovery now pins47 migrations; local graph evidence is not a hosted recovery drill.

Local evidence and limitations are recorded in the candidate handoff. No provider calls, deployment, resources or live-Pi changes are authorized by this unit.

## Public Files catalog (WU164)

GET `/public/documentation/uploads/context` returns `{available:boolean,sectionRevision?:number}`. GET `/public/documentation/uploads/activities?after=...&limit=...` returns `{activities:[{id,title,serviceDate,mode,revision}],next,sectionRevision}` with an ID cursor, default limit25 and maximum50. Only active, impact-relevant activities in the current installation appear, independently of Hours entry windows. No roster, descriptions, submitted content or provider details are returned.

Both reads reuse upload transport assertions, public read admission and no-store responses. Current Hours/Documentation module and Files-section settings gate these reads; Notes and Summary settings do not. Disabled context returns `{available:false}` and disabled catalog returns403. Duplicate/unknown parameters and invalid pages return400. Missing section configuration uses revision0 and enabled Files, matching admission defaults. Catalog reads make no provider calls: availability is not a promise of verified storage readiness. Upload admission still checks current activity/section revisions, contributor and private root/provider authority.
WU163 adds compatible file/member artifact reads and the upload interface described below. Existing link-only responses remain compatible.

## Public and staff interface (WU163)

The public `/submit-documentation` page has separate note and file forms. File eligibility uses `/public/documentation/uploads/context` and `/activities`, independently of the Notes switch. A selected file is bounded to 4 MiB, SHA-256 hashed, and transferred in 256 KiB chunks through the existing backend. Member IDs, original bytes, immutable admission body and ticket remain in page memory only. Note and Hours outcomes never depend on this form.

The File uploads staff view provides the same transfer workflow, optional activity selection and a paginated operation inventory. Staff can explicitly reconcile an existing operation against its original verified root; actual denied access clears private state. A transient permission refresh preserves the selected file and frozen recovery identity while pausing advancement; resuming requires an explicit check or retry. Unknown responses stop advancement. An explicit check reads the existing reference; retrying an uncertain admission resends exactly its original body, without a new key. Expiry or unresolved provider effects directs the contributor to staff instead of silently creating a replacement. Closing the page loses its local recovery information.

Artifacts accepts real file/member DTOs and history, displays source attribution without inventing a staff author, and links to the immutable private original. Metadata edits omit URL for file records. Explicit saved-revision review, rejection, archive and association behavior remains shared with links. Review is distinct from private preservation.

The interface reuses native file/select/input controls, existing ui-card/hours-stack layout and semantic typography, control, focus and brand tokens. No UI-standard exception or new styling tokens. Focused local browser verification covers success with Notes disabled, exact immutable admission retry, lost chunk response, staff reconciliation and file curation, plus representative 390/1280 light/dark custom-brand views. Hosted upload capacity/provider acceptance remains separate. Native Drive copy, Discord file intake and deferred P5 remain outside this interface unit.
