The provisioning workflow refuses public repositories, a private template copy checks out an explicit public release tag, and authenticated Admin update metadata points back to that installation's private workflow without exposing it through `/health`.

- Guarded adopter-owned Cloudflare provisioning verifies an account-owned token against the selected `CLOUDFLARE_ACCOUNT_ID`, refuses Create collisions, supports explicit Resume including interrupted secret setup, generates installation secrets, migrates D1, and deploys Worker/Pages. The first live Create run passed against the user-approved `lancerlogin-test` target; no account identifier or credential is stored in the repository.

## Verification boundary

All current automated tests, workspace typechecks, sanitizer checks, dependency audit, migration verification, production builds, Chromium smoke tests, and actionlint must pass before the v0.9.0 tag. Provider calls use mocked responses in tests. The R503 protocol uses an injected mock transport. The user explicitly requested that this release not update the live isolated test deployment automatically; the guarded private-repository Upgrade workflow remains the manual acceptance path. Physical Pi/sensor acceptance is in progress but is not claimed. The expanded full-screen kiosk simulator is intentionally deferred while the existing setup simulator remains available. When implemented, it must reuse the physical kiosk screen, state transitions, and attendance logic 1:1, replacing only hardware input with browser adapters and marking resulting audit events as simulator-originated. `docs/COMPLETION-AUDIT.md` is the durable requirement-to-evidence matrix.

## Live adopter test boundary

On 2026-08-31 the user explicitly revised the deployment boundary to allow a coexistence test in the same Cloudflare account as an earlier attendance deployment, while continuing to prohibit any modification, binding, route, database access, credential reuse, or dependency involving the earlier resources. A fresh seven-day account-owned token was created with only Workers Scripts Write, D1 Write, Pages Write, and Account Settings Read and stored as encrypted secrets in the GitHub `production` environment. Pre- and post-deployment inventories showed the legacy Worker, Pages project, and D1 database unchanged alongside the three newly named LancerLogin resources. No custom domain, DNS record, Worker route, shared binding, or migration path was configured.

The first two upgrade trials failed closed during read-only resource discovery because Wrangler changed Pages-list and secret-list command interfaces. Neither trial reached migrations or deployment. The workflow now uses Cloudflare's authenticated Pages API and Wrangler's supported secret-list format; the subsequent guarded upgrade succeeded only after confirming all three exact `lancerlogin-test-*` resources and both retained Worker secret names.
