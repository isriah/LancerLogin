# Hour event provider publication (WU-124)

Dependencies: centralized verified Google/Discord connections, Hours catalogs/accounting and current staff grants, and the durable platform scheduler. WU-124 supplies the backend; WU-127 adds the saved-event Staff publication panel. Neither creates provider resources. Development provider acceptance follows integration; local synthetic responses do not establish successful Google or Discord publication.

## Product behavior and technical defaults

Each event activity has independent Google Calendar and Discord publication switches, initially off. Creating an activity, recording hours, linking Attendance, or changing impact relevance does not publish. Hour records and Attendance mappings are independent of this outbox. Provider failure never reverses an Hour record.

Publication requires current `hours.manage` authority and an explicit reviewed snapshot. The snapshot contains only title, description, location and optional explicit start/end instants; service date and time zone come from the current activity. It does not copy private activity edits automatically. Editing the activity marks the review outdated. Google permits an all-day event; Discord requires explicit future times and a location. Both instants must fall within the activity date. These are technical validation defaults implementing the settled independent opt-in decision; no time is invented.

Archive or turning a switch off queues deletion of that provider's owned event. Archive and saved hours do not wait for remote delivery. Module disablement pauses delivery and retains all mappings; pending upserts require renewed review after re-enabling. Provider disablement/rotation similarly invalidates pending review. Restoring an enabled snapshot never silently resumes its pending publication.

## HTTP contract

All endpoints are under `/admin/hours/activities/:id/publications`, apply only to event-mode activities, and reload current staff authority. Responses omit credentials and interaction data.

- `GET` returns activity ID/revision/archive state and one row per provider, including enabled, intent revision, generation, needsReview, reviewedActivityRevision, reviewed snapshot, current target readiness, and bounded operation history.
- `PUT /google` or `/discord` accepts `{revision, activityRevision, enabled:true, targetKey, snapshot:{title,description,location,startsAt,endsAt}}`. `targetKey` is the opaque digest returned by GET for the verified connection/destination. Stale content, authority, destination or revisions fail atomically. Explicit disabling accepts only `{revision,activityRevision,enabled:false}`.
- `POST /:provider/retry` accepts `{generation,action,revision}`. It increments the operation revision, changes the reviewing actor, and rejects a live lease or a concurrent retry atomically. It cannot replace the destination, clear an uncertain-create checkpoint, or bypass an outdated content review.

Provider target is `{ready:false}` or `{ready:true,key,destination,applicationId}`. Each operation exposes generation, original destination/applicationId, eventId, abandoned, action (`upsert`/`delete`), revision, status (`pending`/`processing`/`failed`/`complete`/`review`), phase (`ready`/`create_dispatched`/`known`), fixed safe error and attempts. `needsReview` is the authoritative outdated-review indicator; enabled does not mean delivered. A disabled intent can still have queued cleanup. A not-ready target can coexist with preserved old destination operations. Limits are twenty immutable generations per event/provider and at most eighty operation rows.

## Delivery and ownership

Migration 0038 adds namespaced intents, immutable destination generations and leased operations. Staff review and intent/outbox changes share one D1 transaction and audit. Activity edits/archive, module disablement and central Google rotation also update publication rows through triggers. D1 mutation metadata counts those side effects; success therefore uses the direct conditional audit insertion, or an adjacent transactional SQL `changes()` result for token refresh, rather than treating total affected rows as the direct-write count. Current staff grant, module, activity revision, provider identity and lease are checked when claiming and immediately before every provider mutation, including after token retrieval. Requests already sent cannot be recalled. The Google capability metadata, token closure and server-only IV come from one captured encrypted row, so a scope refresh or replacement between reads cannot admit stale publication settings against a newer IV. Public response fields remain explicitly selected and omit that signature.

Each five-minute `hours.google-calendar` or `hours.discord-calendar` durable family processes one operation with a sixty-second lease. Eligibility and execution share the existing 32-statement/12-provider-request admission budget. Discord publication disables transport-level retries; the durable outbox owns retry so it reacquires current authority. Transient errors back off, with manual review after repeated failure. Scheduler `ok` means the bounded pass completed; operation status determines delivery success. Legacy Attendance cron does not deliver Hours publication; durable mode is required.

Google uses a deterministic ID plus a private namespace marker. Existing events require the expected marker and a valid ETag; PATCH/DELETE sends If-Match. Discord uses a namespace marker and verified bot creator identity, with a bounded server event inventory. Duplicate or foreign ownership matches require manual review. Discord creation is checkpointed before dispatch: a lost response is reconciled to a unique visible owned event, and an uncertain create with no visible match never triggers another blind POST. These rules follow [Google event resources](https://developers.google.com/workspace/calendar/api/v3/reference/events), [private extended properties](https://developers.google.com/workspace/calendar/api/guides/extended-properties), and [Discord scheduled events](https://docs.discord.com/developers/resources/guild-scheduled-event).

A late successful create retains its original generation identity even if the intent was disabled during the request, and requeues owned cleanup. Old destination operations cannot retarget to a newly configured account/calendar/server. If current access cannot prove the original destination and ownership, staff must review that provider resource manually. No exactly-once remote delivery claim is made across arbitrary external failures.

## Backup and restore boundary

Installation JSON backup schema 20 includes all three domain tables in the existing snapshot batch. Earlier backup versions supply empty publication tables. Validation checks activity/provider/user references and marker/generation graphs before deletion. Restored leases are cleared, enabled intents need review, and incomplete operations become review-required. Attendance-only backup/restore leaves these tables untouched.

An atomic installation-delete trigger rejects active publication leases or an uncertain `create_dispatched` checkpoint, including a claim raced against restore preparation. This preserves late-response identity. Installation restore additionally inserts an assertion row into the normally empty `hours_publication_restore_guard` table in the same transaction. The deletion trigger requires every current generation to retain identical pinned identity/marker and any current mapped provider ID in the backup, unless its owned deletion completed and its mapped event ID is empty. The assertion row is removed before commit and is not application backup data. An older backup therefore cannot erase known cleanup authority. Resolve uncertain operations, finish cleanup, or use a current backup before retrying a 409. Restore never deletes remote assets itself. Explicit installation deletion likewise makes no remote-cleanup promise; turn publications off and complete owned cleanup before discarding the installation.

This protection covers the API's installation restore/deletion path. Raw D1 SQL exports include the schema triggers, but infrastructure replacement outside the API still requires scheduler shutdown, reconciliation and a current ownership backup. Full updater maintenance/recovery orchestration is a later dependency; this work does not claim it implemented.

## Staff publication review (WU-127)

Open **Publication for [event title]** beside a saved event in Hour Tracking catalogs. Google Calendar and Discord start off independently. New public fields are blank; only an existing reviewed public snapshot is reused. Enter public content, review the visible calendar/server and application, then explicitly save. Changing any public draft field clears its review acknowledgement. Google supports all-day publication; Discord requires a future start, explicit civil-time occurrences where clocks repeat, and a location. Changed activity dates/zones clear saved public timing rather than silently shifting it.

Saved intent, delivery and owned cleanup are separate states. Turning a switch off requires its explicit save and preserves cleanup history. Historical generations show their original destinations and IDs as text. The UI offers manual retry only for eligible failed/review operations; mismatched destinations and uncertain creation require provider ownership review. The server still fences connection identity and leases, and may reject a retry whose authority changed.

A stale, malformed or uncertain result locks both provider forms until an explicit GET reload. Access refresh also requires a new read before saving. Saving or reloading discards unsaved public drafts in both provider forms, as stated in the panel. No automatic client writes, retries or destination changes occur. Archived events can be turned off but cannot be published.

Run `npm run verify:dashboard` and `npm run test:browser -- tests-browser/hours-publication.spec.ts tests-browser/hours-catalogs.spec.ts --workers=2`. The publication tests use synthetic API responses and local Chromium: independent switches, exact revision/target payloads, all-day and repeated civil times, past/gap rejection, malformed/conflicting responses, access refresh/revocation, old cleanup, uncertain creation, keyboard focus, 44px activation targets, and 1280x900/390x844 light/dark/custom-brand/reduced-motion layouts. This establishes local UI behavior, not successful development Google/Discord delivery.
