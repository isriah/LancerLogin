# Integrations

All integrations are optional and explicitly enabled, saved, verified, rotated, disabled, or removed by Admins in the dashboard. New and unconfigured providers default off; upgrades preserve providers with saved credentials as enabled. Disabled providers retain encrypted credentials but expose no configuration form and cannot power sign-in, delivery, Discord interactions, calendar sync, pairing, or status workflows. Saved credentials remain encrypted and are never returned to the browser. An enabled saved provider remains **Verification required** until its real end-to-end proof succeeds. Enabled integrations are listed first; disabled integrations use condensed rows. Each enabled integration card contains a beginner-oriented setup guide, exact installation-specific callback value, official provider-console link, required access, and safe rotation/removal instructions.

- Google OAuth provides optional dashboard sign-in using only the `openid`, `email`, and `profile` scopes. In Google Auth Platform, configure Branding, Audience, Data Access, and one Web application client, then register the adopter's exact Pages callback, `https://<slug>-dashboard.pages.dev/api/auth/google/callback`. The public [Google OAuth setup guide](https://isriah.github.io/LancerLogin/setup.html#google-oauth) explains Internal and External audiences, Testing and In production publishing, and Google's separate verification choices. When Google is selected during first-Admin setup, its client ID and secret are collected and encrypted in that setup form so Google-only installations can perform their first sign-in. A valid Google response for an active Admin verifies the integration in LancerLogin. Admins can later rotate or remove it in Integrations.
- Resend sends one missed-meeting notice per member/meeting by default and individual attendance reports. The dashboard guide walks through domain verification, creating a sending-only API key, and choosing a From address on the verified domain. Verification sends a real six-digit code to an Admin-selected address. The code expires in ten minutes, and only its SHA-256 hash is stored in D1.
- Discord supports Operator/Admin member linking, member self-pairing with `/pair`, private self-service attendance reports with `/attendance-report`, automatic absence notices after the organization-wide scan cutoff, signed member-submitted contests, calendar event create-or-update mapping, and one persistent kiosk-status message. Admins can opt into attendance-channel manager mode from the Discord integration card. That mode keeps the tracked kiosk-status message pinned, maintains one tracked attendance-help guide after it with a **View my attendance report** button, and deletes each tracked absence message after the contest window; it never rewrites, reorders, unpins, or deletes untracked channel content. Admins may also enable one anomaly report after each meeting closes, using a separate staff-only text channel in the verified server. Those reports contain qualifying raw-scan late/early values, never mention users, skip meetings without anomalies, do not backfill meetings from before enablement, and use tracked provider-enforced nonces for retry safety. The command and button use the same report path: both bind the signed requester to one active linked roster member, use the operational reporting baseline and participation start date, include optional meetings and canonical correction/excuse outcomes, and return only an ephemeral bounded response. The button additionally binds the click to the configured server and channel and to the current tracked guide message. Once Discord is enabled and verified, a meeting detail permits manual calendar sync through its scheduled end and manual absence notification from its scheduled start onward; it also limits contest review to that meeting while the global notifier retains access to every open contest. The Kiosks physical-health card lets an Admin or Operator manually refresh the persistent status message. The five-minute schedule sends each meeting notice once, records exactly who received it, and retries failed delivery. Re-sent notices retain their own recipient records, so an earlier message remains valid while the member is still absent and linked. Each message expires after the configurable Discord contest window, which defaults to 24 hours and is managed beside channel-manager mode in Settings → Integrations. Only a linked recipient pressing the signed message button can open a contest; attendance does not change until an Admin or Operator records a review note and approves it. Controlled mentions prevent unrelated pings. Heartbeats update kiosk state and the same five-minute schedule marks stale kiosks offline. Discord failures never block kiosk or attendance delivery.
- While Discord is enabled, Admins and Operators can see a member's paired Discord user ID—or a muted unlinked state—on that member's detail page. Disabling Discord hides this identity without changing the pairing.

Discord setup needs the bot token, application public key, application ID, server ID, and attendance channel ID. Set the Discord application Interactions Endpoint URL to the exact URL displayed by **Settings → Integrations**. Register `/pair` and `/attendance-report` as guild-scoped chat-input commands in that configured server through Discord's HTTP application-command endpoint; the public operations guide contains the exact payloads. Verification checks the bot and server, sends a message to the selected attendance channel, and requires a signed user button click. Channel-manager mode additionally requires Pin Messages so LancerLogin can pin its tracked status message; it deletes only messages authored and tracked by its own bot. Anomaly reports require a second guild text channel whose Discord permissions limit access to the intended attendance staff; LancerLogin verifies the channel belongs to the configured server but cannot define its staff membership. The public key verifies that proof and every later command, contest submission, or component interaction before attendance data is read or D1 is changed.

Rotating a provider clears its earlier verification. Saving, rotating, disabling, or removing Discord also disables anomaly reports until an Admin verifies Discord and deliberately enables the private channel again; this prevents delivery to a channel that was approved for older credentials or a different server. Saved but unverified Resend and Discord credentials cannot power operational attendance workflows. Existing credentials upgraded from backup schema 1–3 also require fresh verification.

Google cannot be disabled or removed unless an active Admin has a usable local password. Disabling Google on a dual-sign-in installation switches the installation to local sign-in; enabling it again restores both methods. This prevents an Admin from removing the installation's only usable sign-in path.

The Worker contains production HTTPS clients for these provider APIs. Automated tests replace outbound requests with provider fakes, so CI never sends email, Discord messages, calendar events, or OAuth credentials. Delivery keys, update mappings, controlled mentions, Admin-only configuration, and audit records enforce the workflow boundaries.
