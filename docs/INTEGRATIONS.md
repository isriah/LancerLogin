# Integrations

This guide is for Administrators. All integrations are optional and configured in **Settings > Integrations**. Enable a provider before entering credentials. Saved values remain encrypted and are never returned to the browser. A saved provider cannot send messages or sync data until its verification succeeds.

## Google sign-in

Google sign-in is separate from Google Calendar. In [Google Auth Platform](https://console.cloud.google.com/auth/overview), create a Web application client and copy the exact redirect URI that the setup card shows into **Authorized redirect URIs**. This is the address the API uses. Do not use a desktop client or invent the callback URL. Redirect URIs must use https. Only a `localhost` or `127.0.0.1` preview may use http.

For sign-in, request only `openid`, `email`, and `profile`. Google Auth Platform currently organizes the configuration as Branding, Audience, Clients, Data Access, and Verification Center. Select an Internal audience only if every intended dashboard user belongs to the project's Google Cloud organization. Otherwise use External and review Google's current publishing and verification requirements. For an External audience in Testing, add each Admin and Operator Google account under **Audience > Test users**. Otherwise Google shows "Access blocked".

Choose **Verify with Google** and sign in with a Google account that belongs to an active Admin. The Google email must match that Admin's LancerLogin email. If the installation was created with **Username and password**, first add the Admin's Google email in **Settings > Access**. Admins can add or change any user's Google email there. If verification fails, the Google sign-in card shows a message that explains the problem.

An active Admin must be able to use a local password before Google sign-in can be removed. This avoids removing the installation's only usable Admin sign-in route.

## Google Calendar

Google Calendar uses its own OAuth client, separate from Google sign-in. Calendar needs more access than sign-in, so it is best to keep it in its own Google Cloud project.

### Connect Google Calendar

1. In the [Google Cloud console](https://console.cloud.google.com/), use a separate project for Calendar. If you use the sign-in project instead, add the two Calendar scopes under **Data Access**: `https://www.googleapis.com/auth/calendar.calendarlist.readonly` and `https://www.googleapis.com/auth/calendar.events`.
2. Enable the [Google Calendar API](https://console.cloud.google.com/apis/library/calendar-json.googleapis.com) in that project.
3. In **Google Auth Platform > Clients**, create a **Web application** client. Add the **Authorized redirect URI** that the Google Calendar card shows. It has the form `https://<slug>-dashboard.pages.dev/api/admin/integrations/google-calendar/callback`.
4. For an External audience in Testing, add the Google account that will authorize Calendar under **Audience > Test users**.
5. In **Settings > Integrations > Google Calendar**, enter the client ID and client secret and choose **Save credentials**.
6. Choose **Authorize Google Calendar**. Sign in with the account that owns or can edit the calendar, and approve both permissions.
7. Choose **Load writable calendars**, pick the destination calendar, and choose **Use this calendar**.

If authorization fails, the card shows a message that explains the problem. In Testing, Google ends the authorization after 7 days. For ongoing sync, publish the app (**In production**) or use an Internal audience. When Google refuses the authorization, or it passes the end date Google gave it, the card shows **Re-authorization required** and warns that authorization needs renewing. Choose **Re-authorize Google Calendar**. When Google gives no end date, as for a published app, or for an authorization saved before LancerLogin recorded the end date, the card can only show that authorization ended after the next delivery fails.

### Calendar delivery

Google Calendar and Discord scheduled events use the dashboard meeting title and notes as the event description, together with meeting start and end times. Clearing notes clears the Google event description on the next sync. Restrict provider destinations to the intended audience. LancerLogin does not add roster, attendance, attendees, or reminders to Google events.

Discord allows a server 100 scheduled events, so LancerLogin creates Discord events only for meetings that start within the next 60 days. Later meetings wait and are added automatically as they come within range; a meeting that already has a Discord event keeps it in sync.

While an Admin has stopped the background scheduler (**Settings > Background scheduler**, which Admins see with Debug mode on), nothing is sent to Google Calendar, Discord or email, including first attempts after a change. The work stays queued and goes out when the Stop ends, automatically after 24 hours or sooner when the scheduler is started again.

Meeting delivery is asynchronous. Saving, editing, deleting or restoring a meeting, a whole series or a bulk selection only queues the calendar change, in the same database write as the meeting change, so the two are saved together or not at all. The background scheduler then sends the queue: within seconds on an installation with the scheduler's Durable Object, otherwise five Google Calendar and three Discord events on each five-minute pass, so there a 300-meeting **Sync all** takes about five hours for Google. Deletes go first, then the soonest meeting first, whenever each was queued; an operation that failed and is waiting to retry never holds the others back. Where the fallback delivers, or a long queue is waiting, **Sync now** and **Sync all** say how many events are waiting. The dashboard therefore reports a change as queued, not as sent. Several edits made before delivery go out as one update, and a meeting created and deleted before delivery never appears on the calendar. Deleting a meeting whose Google event was never created queues no delete: its waiting create, or one Google refused, is dropped instead. A create that failed with an error LancerLogin retries (Google may have made the event anyway) is followed by a delete, which counts as done if Google has no such event. A provider failure does not undo a meeting change.

**Sync now** on a meeting queues that one meeting in the same way. A meeting that has already started and has no Discord event is skipped, because Discord cannot schedule an event in the past. A meeting that has a Discord event and is edited so that it has already ended has that event deleted.

Nothing is queued for an integration that is switched off or not verified, and its record of which events exist is left as it is. Work that was already queued when it was switched off is marked as needing another attempt within five minutes, with that reason. Turning the integration back on, or verifying it again, queues what **Sync all meetings** queues: every current and upcoming meeting and the removal of events for meetings deleted in the meantime, so edits made while it was off reach the calendar without further action. **Sync all meetings** does the same on request and also retries removals that were set aside. A Discord event waiting for the 60-day horizon keeps waiting while Discord is off; it is not marked as failed.

Disabling the Attendance module does not wait for queued calendar work, only for an event or email that is being sent at that moment (try again shortly). Queued changes are kept with the module's retained data and go out if Attendance is enabled again; events of meetings already deleted are recorded for removal and removed then too. While Attendance is disabled nothing is sent, so those events stay on the calendar and the Discord server. They are removed if Attendance is enabled again within the 7 days its data is kept; after that they have to be deleted by hand. Disabling does not remove the events of current and upcoming meetings either; if Attendance is not enabled again within the 7 days its data is kept, LancerLogin stops tracking them and they have to be deleted by hand. The confirmation in **Settings > Modules** says how many events of each connected provider are waiting to be removed and how many of current and upcoming meetings stay, and reads as before when there are none.

The integration card reports waiting or failed work and offers **Retry failed delivery** and **Sync all meetings**. When Discord refuses a request in a way every other request would meet too, LancerLogin holds the Discord queue instead of sending each event to be refused. A reset bot token, or a server Discord no longer finds for the bot (Unknown Guild), holds everything for 15 minutes; a rate limit holds everything for as long as Discord asks, between one minute and an hour. A missing permission, which is also what Discord usually answers once the bot has been removed from the server, holds for 15 minutes the kind of work it was refused for: creating and updating events, or removing them. The event that was refused waits with the rest and is the first to be tried when the hold ends; it is not given up. An event is treated as already gone only when Discord says that the event is unknown, never when it says the server is. The card counts the refused event as needing another attempt and shows Discord's reason. When the hold ends the queue is tried again by itself, and **Retry failed delivery** on the Discord card ends it at once and reports how many events it made due. The same hold applies when the saved Discord credentials cannot be read: the events count as waiting, and the card shows **Saved, but can't be read** until the credentials are saved again (see [Safe changes](#safe-changes)). Sync all queues every meeting that is not deleted and has not ended, in one request with no limit; meetings that have ended are left as they are. It also repairs what an interrupted request may have left behind: a deleted meeting whose event was never removed has the removal queued, and a restored meeting that lost its event gets a new one. 
Delivered calendar operations are removed from the queue 30 days after delivery. Removing the connection clears LancerLogin's authorization and mappings; it does not promise to remove events already delivered to Google.

Deleting **Meetings and attendance** in **Settings > Data** removes the meetings from LancerLogin at once and leaves their Google Calendar and Discord events for the scheduler to delete afterwards. Restoring a meetings backup does the same for the meetings it removes. If an integration is switched off or unverified at the time, its events are deleted once it is enabled and verified again; if the connection is removed and never set up again, those events stay on the calendar. A removal recorded for a Google calendar other than the one now configured is dropped and noted in the audit log. One recorded for a Discord server other than the one now configured is tried on that server with the bot now saved, and dropped with an audit entry if Discord refuses it there (see [Safe changes](#safe-changes)). An event that is already gone counts as removed. Any other refusal, a missing permission included, is retried ten times, 15 minutes after the first and doubling to a day at most: about three days when the provider answers each attempt. On Discord, a refusal that starts a hold also keeps back the removals that were not sent, without counting an attempt against them, so with many removals waiting behind a refusal that lasts they are tried one per hold and take correspondingly longer. After its tenth attempt the removal is set aside: the audit log records it, the integration card counts it as needing another attempt with the provider's reason, and **Retry failed delivery** or **Sync all meetings** on either card makes it due again. Retry only makes failed work due; the scheduler sends it, like everything else. Disconnecting a provider sets its waiting removals aside at once with one audit entry, since its events can no longer be reached; they stop counting as waiting and count as needing another attempt. Restoring a whole-installation backup discards removals that were still waiting, so those events stay on the calendar.

## Resend

Enable Resend, use a verified sending domain, create a **Sending access** API key restricted to that domain, and choose a plain From address on that domain with no display name. Verification sends a six-digit code to the Administrator-selected address. The code expires after ten minutes. The `onboarding@resend.dev` test sender delivers only to the email address of your own Resend account. If verification fails, the card shows Resend's own reason. Correct the stated domain, sender, or code issue before trying again.

## FIRST

The **FIRST** card holds one connection to FIRST's team data that any module can use, for example Guest Visits filling in a team's name from its number. Only the team number is sent to FIRST. It has no enable switch: each program is on once it has what it needs.

- **FRC and FTC** use FIRST's Events APIs. Request a username and token from the [FRC Events API registration](https://frc-events.firstinspires.org/services/API) or the [FTC Events API registration](https://ftc-events.firstinspires.org/services/API), enter them in that program's row and choose **Save**. LancerLogin checks them with FIRST before saving and stores the token encrypted; it is never shown again. To change the username, enter the token again. **Remove** forgets the credential and FIRST's saved answers for that program.
- **FLL** (Challenge and Explore) uses FIRST's public team search and needs no username or token, so it shows **Available** without setup. FIRST reuses team numbers across programs and seasons, so LancerLogin keeps only that program's entries for the exact number and shows the team from the latest season.
- **Test a team** looks up one number in one program and shows FIRST's answer. **Clear cached answers** makes the next lookups ask FIRST again.

LancerLogin keeps FIRST's answers for a while: a team for seven days and "no such team" for one day. Guest lookups on public pages are limited per visitor and for the whole installation each minute, so a busy page cannot use up the tokens. Entire-installation backups carry the saved usernames and encrypted tokens. A credential restored onto an installation with a different encryption key shows **Saved, but can't be read**; enter the token again and save.

## Notion

The **Notion** card holds one Notion connection that any module can use, for example a plugin that adds rows to a team's ordering database. Modules never see the token, and each module can use only the databases you choose for it on this card.

Set it up once:

1. In Notion, open [integration settings](https://www.notion.so/profile/integrations) and create an **internal** integration in the team's workspace.
2. Give it the capabilities the modules you use need. Notion lists five:
   - **Read content**
   - **Insert content**
   - **Update content**
   - **Insert comments**
   - **Read user information**, with or without email addresses
3. Copy the integration's token, paste it into **Integration token** on the Notion card and choose **Save**. LancerLogin checks the token with Notion before saving and stores it encrypted; it is never shown again.
4. In Notion, open each database a module uses, choose **Connections** from its menu and add the integration. A database the integration was not added to cannot be chosen.
5. Under **Databases** on the card, paste each database's link and choose **Save database**. Each module that uses Notion lists the databases it needs and why. If a database has more than one data source, choose which one.

What the card shows:

- **Connection.** The integration's name and workspace, and when Notion last accepted the token. The switch turns the connection off without forgetting the token; modules then stop using Notion. **Check** asks Notion again. **Remove** forgets the token and keeps the databases you chose, so a new token picks up where the old one stopped. If someone else changed the connection after you opened the page, your change is not saved; the card shows what is saved now so you can decide again.
- **What the token allows.** Notion has no way to list an integration's capabilities, so each of the five shows what LancerLogin has seen: **Working** after a module used it, **Refused by Notion** after Notion refused it, and **Not used yet** until either. Saving or checking the token tests **Read user information**; choosing a database tests **Read content**. To fix a refusal, change the capability in the integration's settings in Notion.
- **Databases.** One row for each database an installed module declared, with **Chosen** or **Not chosen**. **Clear** takes a database away from its module.

Comments a module adds in Notion appear under that module's name, such as **Part Requests**. Notion adds the connection it came through after the name. A module that comments can offer **Name shown on comments** on its own settings page to use another name for its comments; leave it blank to use the module's name. Removing the token or a chosen database keeps that name, and deleting the module's data removes it.

When Notion asks LancerLogin to slow down, every module waits until the time Notion names, and the card says when calls resume. Entire-installation backups carry the encrypted token, the chosen databases and each module's comment name. A token restored onto an installation with a different encryption key shows **Saved, but can't be read**; enter the token again and save.

## Discord

Discord can provide member linking, attendance notices, calendar delivery, contest handling, and a persistent kiosk-status message. Enable it, then provide the bot token, application public key, application ID, server ID, and attendance-channel ID requested by the card, and choose **Save credentials**. After saving, copy the exact Interactions Endpoint URL that LancerLogin shows into the Discord application settings. See [Create the Discord bot](#create-the-discord-bot) for the full order.

### Create the Discord bot

Follow these steps in order. Discord checks the Interactions Endpoint URL when you save it, and LancerLogin can answer only after its credentials are saved.

1. Open the [Discord Developer Portal](https://discord.com/developers/applications), choose **New Application**, and name it.
2. On the **Bot** page, choose **Reset Token** and copy the bot token into LancerLogin. Treat the token like a password. For optional label role sync, turn on the privileged **Server Members Intent** on the same page.
3. On the **General Information** page, copy the **Application ID** and **Public Key** into LancerLogin.
4. On the **Installation** page, enable **Guild Install** and select the **bot** scope. Grant **View Channels**, **Send Messages**, **Read Message History**, **Pin Messages**, **Create Public Threads**, **Manage Threads**, **Create Events**, **Manage Events**, and **Manage Roles**. The bot needs **Create Events** to create scheduled events. Use the install link to add the bot to your server. For role sync, place the bot's role above the roles it will manage. Members need **Send Messages in Threads** in the attendance channel to ask questions in absence-notice threads.
5. In Discord, turn on **Developer Mode** in **User Settings > Advanced**. Right-click the server and choose **Copy Server ID**. Right-click the attendance channel and choose **Copy Channel ID**. The attendance channel must be a text channel. Paste both into LancerLogin.
6. In LancerLogin, choose **Save credentials**. All five values are required to save.
7. Copy the Interactions Endpoint URL that LancerLogin now shows under **Verify the connection**. This is the exact address the API uses. It has the form `https://<slug>-dashboard.pages.dev/api/discord/interactions`. Paste it into **Interactions Endpoint URL** on Discord's **General Information** page and choose **Save Changes**.
8. Choose **Send Discord verification**, then press the button in the message the bot posts.

If Discord says the interactions endpoint URL could not be verified, confirm that you chose **Save credentials** first. Then check that the saved public key is from the same Discord application: copy it again from **General Information** and use **Replace saved credentials**.

### After setup

Verification checks the saved application and server, reconciles Core's `/pair`, `/attendance-report`, `/code`, and `/label` commands plus the commands each installed plugin declares (Outreach adds `/outreach-submit`, `/outreach-correction` and `/outreach-report`), sends a message to the selected attendance channel, and requires the signed button proof. After an update, a verified connection checks these commands automatically on the next five-minute maintenance pass and adds or updates only commands that changed. **Settings > Integrations > Discord** shows whether command setup is pending, current, or failed. **Reconcile Discord commands** repairs them immediately without replacing credentials or clearing existing mappings. Command setup does not associate labels or sync member roles. Outreach commands remain unavailable unless Outreach is enabled and ready. `/code` gives a linked member a one-time kiosk code; see **Discord codes** in [KIOSK.md](KIOSK.md).

Linked members can use `/outreach-submit` to record participation in an eligible dated Outreach activity and `/outreach-correction` to request Staff review. `/outreach-report` privately shows a linked member their own Outreach participation summary. Responses are private and include receipt references. An exact Discord interaction retry is idempotent, and a correction never changes totals until Staff accepts it. Outreach Event publication is off by default. Staff can Publish or Resend a scheduled Event from its activity, or an Admin can turn on automatic publication of future scheduled Events separately for Discord and Google Calendar in **Settings > Outreach > General**, where **Publish upcoming Events** queues the active Events that have not ended yet to each destination that is on. Manual publication queues every configured Google Calendar and Discord destination, and each provider result is reported independently. Team Support and Other Service activities are never published.

Discord role sync is optional. Turn on the privileged **Server Members Intent** for the bot and grant **Manage Roles**, then place the bot's role above each role it will manage. In **Settings > Modules > Attendance > Labels**, an Admin links a label to a role by choosing it in the label's **Discord role** column. The list shows every server role and explains why the bot cannot manage some of them, such as a role above the bot's highest role or one managed by an integration. Role and label names do not need to match. **Create labels from Discord roles** creates a label named after each chosen role, or reuses an unlinked active label with that name, and links them. Each label links to at most one role and each role to at most one label.

An Admin can also link from Discord. Pair a roster member linked to an active LancerLogin Admin account; that Admin can run `/label @ROLE` in the configured server. An active label must have the same name as the role, ignoring letter case. Confirming the private prompt saves the link. Linking either way does not change role assignments.

On the **Labels** page, preview **Sync to Discord** for one label, or **Sync all linked roles** for every active linked label at once, before confirming. The preview lists additions, removals, and labeled members who are unpaired, absent from the server, or inactive. A sync removes the mapped role from every server member who is not an active, paired roster member with the current label, including unpaired accounts. It changes no other roles. For a label left on **Dashboard to Discord** (the default), sync is manual: label and pairing changes take effect in Discord only after another sync. An icon next to each linked role shows its sync state: in sync, label changes since the last sync, syncing, failed, or never synced. Hover over it, focus it, or tap it for details, including when it last synced. A sync that a two-way check started shows as syncing too, with its progress. A sync that makes no progress for over 15 minutes shows **Sync stuck**, and the row's button becomes **View sync**; updating LancerLogin in **Settings > Updates** fixes a known cause. Pairing changes are not tracked in that status. Applying label changes in Roster offers a link back to review role sync. When a sync fails for some members, the row's button becomes **Retry failed**, which retries only the failed changes still needed. Each row's **More** menu holds **Rename**, **View last sync** (**View sync** while one runs), **Unlink role**, and **Retire label**. Unlinking an association leaves existing Discord roles in place. Retiring a label keeps its role link; an Admin removes it with **Unlink role** beside the label under **Retired labels**. If the page cannot check a running sync's progress several times in a row, it stops checking and shows the error with **Check again**; the sync itself may still be running. Operators can view mappings, sync status, and the last sync.

#### Two-way labels

Each linked label has a direction: **Dashboard to Discord** or **Two-way**. A two-way label is checked every 5 minutes with no preview: a role added or removed in Discord changes the member's label (recorded in their label history as a change from Discord, dated that day), and a label change in the dashboard reaches Discord. When both sides changed since the last check, the dashboard wins. Its row shows **Every 5 min** instead of a **Sync to Discord** button, and **Sync all linked roles** skips two-way labels.

- **Turning it on.** Choosing **Two-way** opens **Turn on two-way sync**, which lists everyone who has the label but not the role, or the role but not the label. Choose the correct side for each person, or for everyone, then choose **Confirm and turn on two-way sync**. Nothing changes until you confirm. A label that affects attendance asks you to confirm that you understand the warning first. Role changes you chose are queued and made by the background scheduler, starting within seconds; the label shows **Syncing** until they finish.
- **Who is checked.** Only roster members whose Discord account is linked (`/pair`) are synced. People who hold the role but are not linked to anyone on the roster are left alone. Admins see them under **Discord users not on the roster** in the **Discord roles** card on the **Labels** page, as of each label's last check (the **Checked** time shown for the label); this collapsible section appears once Discord is verified and a label syncs two-way, with no Debug mode needed. Link them in Roster to sync their label.
- **Newly linked members: nothing is removed.** The first time a member is checked after their Discord account is linked, there is no earlier agreed state, so neither side is taken away. A member who already holds the role in Discord but does not have the label **gets the label**, recorded in their label history as a change from Discord dated that day, so meeting audiences and attendance policies that use the label apply to them from then. A member who has the label gets the role. Later changes follow the rules above. If a newly linked member should not have the label, remove the role in Discord before they link, or remove the label or the role afterwards.
- **Trust.** Anyone who can assign the role in Discord can now change the label, and with it meeting audiences and attendance policies. Use two-way only for roles managed by people you would let edit labels.
- **Failures and restores.** A failed check shows **Two-way check failed** and is retried every 5 minutes. After an entire-installation restore a two-way label is paused as **Two-way, needs reconciliation**; choose **Review differences** to turn it back on, or **Switch to Dashboard to Discord**.

Each absence notice opens one public thread for questions under its first message. Long recipient lists are split into multiple messages within Discord's content and mention limits, and every message includes the **Contest absence** button. The bot needs **Create Public Threads** and **Manage Threads** permissions, and members need **Send Messages in Threads** permission in the attendance channel. The button requests a private review. After rejection, a linked member can submit again within the same notice window; repeated clicks on an open request do not create duplicates. Earlier rejection reasons and reviewer details are retained. Turn on **Block re-contests after rejection** in the Discord settings to prevent this. The bot removes every tracked message in the notice and its question thread after the configured contest window on its next five-minute maintenance pass, even when the optional attendance-channel manager is off. Without **Manage Threads**, Discord refuses to delete the thread, so maintenance keeps retrying. Changing a meeting's times, required setting or audience while its notice is still within the contest window removes that notice right away. A fresh notice is posted when the edited meeting's attendance closes. A notice Discord refuses is retried with growing delays (a minute at first, up to an hour) and given up after 16 attempts; **Send Discord absence notice** on the meeting still sends it. A notice interrupted part-way is taken up again after ten minutes without mentioning anyone twice. Anomaly reports are retried the same way, and a meeting's first notice or report always goes out before any retry. If Discord refuses the removal, maintenance keeps retrying and no new notice is posted. A member who is still checked in cannot contest before attendance closes. The optional manager maintains the pinned kiosk status and attendance guide. The optional anomaly report requires a different text channel in the verified server. Administrators must restrict that channel to intended attendance staff. If that channel is private, add the bot to it with **View Channel**, **Send Messages**, and **Read Message History**. Provider failures never block kiosk scans or an attendance record.

Sync upcoming meetings before their start time. A meeting already in progress without a Discord event is skipped with an explanation; existing active events retain their provider start time when updated. Ended meetings are skipped.

The Kiosks page verifies the tracked status message before reporting it current and provides **View Discord status message** after syncing. If the message was deleted, sync recreates it. Enable the attendance-channel manager to keep it pinned.

The status message is kept current by the background scheduler, not by each kiosk heartbeat. It changes within seconds when a kiosk comes back online or reports a different reader state or release, and within five minutes on an installation without the scheduler's Durable Object. A kiosk that stops reporting shows as offline at the next five-minute check, about two to seven minutes after its last heartbeat. A status message deleted in Discord, or unpinned while the channel manager is on, is restored within an hour, or at once from the Kiosks page.

## Safe changes

Saving, rotating, disabling, or removing a provider clears its verification where appropriate. Disabled and unverified providers do not send operational messages or synchronize meetings. Review the card's status after every change and retry only the action it identifies. Do not paste credentials into source, logs, screenshots, or chat.

Replacing the saved Discord credentials keeps the calendar events LancerLogin has created when the new credentials are for the same server, for example after a bot token reset: the events, and any changes still waiting to be sent, stay as they are, nothing is sent until you verify again, and verifying updates the events that are there instead of creating new ones. When the new credentials are for a different server, the events on the previous server no longer belong to this connection. LancerLogin records each one that may still be there (events of meetings that have not ended, and removals that were still waiting), tells you how many when you save, and after you verify the new server removes them from the previous server if the bot now saved can still reach it. An event it cannot remove there, because the bot is not in that server or lacks permission, is left on Discord and recorded in the audit log (`calendar.event_removal_abandoned`, with the event and server IDs); delete it in Discord yourself. A refusal on the previous server never holds up the new server's events. LancerLogin also remembers which meeting each of those events belonged to. If you save credentials for the previous server again, for example after correcting a mistyped server ID or undoing a move, its events that are still waiting to be removed are linked to their meetings again: verifying updates them where they are, and none is deleted or created a second time, including the event of a meeting in progress. An event that was already removed there is created again. Saved credentials that can't be read name no server, so replacing them always keeps the calendar as for the same server; if the new credentials are in fact for a different server, each meeting's event is created on it, and the events on the old server are left there for you to delete, with only the audit entry of the save (`kept_server_unknown`) to show for it. If two Admins save Discord credentials at the same moment, the second is told that the credentials changed and nothing is changed by it; reload and save again. Removing the Discord integration leaves its events on the server, because nothing can reach Discord once the credentials are gone, but LancerLogin still remembers them. If you set Discord up again for the same server, each event is linked to its meeting again and verifying updates it where it is; nothing is deleted or created a second time. If you set it up for a different server, that is a change of server: the save tells you how many events are on the previous one, and they are removed there after you verify if the new bot can reach it. The one exception is a connection whose saved credentials could not be read when it was removed, on an installation that never saved Discord credentials with this release or a later one: nothing names its server, so its events are forgotten as before. If Discord deletes an event of a meeting that is already in progress, LancerLogin cannot create another for it (Discord only schedules events that start in the future); the meeting then has no event, and LancerLogin records why instead of keeping the ID of the event that is gone.

A card that shows **Saved, but can't be read** holds credentials this installation can no longer decrypt: its encryption key (`INTEGRATION_KEY`) was replaced, the data was restored onto an installation with another key, or the stored value is damaged. The Integrations page still loads, nothing that uses those credentials runs, and every action that needs them answers that they can't be read instead of failing. Choose **Replace credentials**, enter them again and save, then verify the provider as after any other change. Nothing about the old value is shown or logged.
