# Optional password computation runtime (WU-131)

Dependencies: current account authorization, local recovery and the existing salted scrypt format. This is a technical runtime option, not a change to confirmed authentication choices or password cost. No namespace is created by this implementation.

## Evidence and limits

The exact JavaScript password implementation uses scrypt N=32768, r=8, p=1, 32-byte output and random 16-byte salt. A bounded synthetic Node benchmark at d1a106c measured three verifications at 109/110/109 ms process CPU, versus 16 ms total for 100 session issue/verify pairs. Cold unknown-user timing equalization performed two scrypt operations and measured 218 ms CPU. These are local process measurements, not Cloudflare invocation CPU measurements.

The maintainer's read-only development API metrics for the 07:18-07:25 failure window reported four `exceededResources` invocations (CPU p50=10000 microseconds, p99=133919 microseconds) and ten successes (CPU p99=227779 microseconds). This supports a resource mismatch; that aggregate outcome does not independently distinguish CPU from memory exhaustion. Previous successful sign-ins do not establish sustainable headroom.

[Worker limits](https://developers.cloudflare.com/workers/platform/limits/#cpu-time) specify 10 ms CPU for Free HTTP requests, exclude network/database waiting, and describe occasional isolate overrun flexibility followed by enforcement for consistent overruns. Error 1102 can represent CPU or memory exhaustion. [SQLite Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/) specify a default 30-second invocation CPU budget and availability on Workers Free. Moving the same computation to this runtime needs actual deployment verification; local workerd does not prove hosted CPU acceptance. No password-cost reduction or paid-plan change is part of this work.

## Optional binding contract

- Absent `PASSWORD_COMPUTATION_MODE`, or explicit `inline`, preserves the existing standard deployment behavior and hash implementation.
- Explicit `PASSWORD_COMPUTATION_MODE=durable` requires the private `PASSWORD_COMPUTATION` binding to the exported `PasswordComputation` class, a separately approved SQLite namespace, and the existing `SESSION_KEY`. The API always selects the fixed `primary` object. Invalid mode, missing binding/key, timeout or unavailable service returns a generic 503. It never falls back to HTTP scrypt in configured mode.
- No public API route forwards to the object. Its sole protocol is POST `https://password.internal/compute`, signed internally using SESSION_KEY HMAC with a distinct password-computation domain, exact body digest, unique request ID, installation and five-second expiry. Session signatures cannot authorize this protocol. Purposes are fixed: local-login verification, first-admin creation, user-create, password-reset. Public setup-code and current Admin authorization remain in their original API handlers before signing a request; current database mutation guards remain authoritative.
- The object accepts only exact versioned DTOs. Hash requests cannot choose cost, salt, output length or another algorithm. Verification accepts the canonical format generated by the unchanged current hasher. Corrupt/noncanonical stored hashes fail closed in durable mode; there is no reinterpretation or automatic migration. Every correctly generated existing hash remains compatible, including passwords longer than 1024 bytes.
- Bounds preserve passwords representable in the existing 262144-byte API JSON request: decoded password at most 262144 UTF-8 bytes and internal JSON at most 264192 bytes, including escaping and fixed metadata. Both inbound and response streams are bounded and time-limited. Internal responses are at most 512 bytes and must match the request ID, operation and fixed result type. Errors contain no request or provider text.

## Concurrency, timeout and data handling

One computation runs per isolate, with at most two waiting requests. Queue deadlines expire without starting that computation; excess admission returns 503. This permits short overlapping legitimate sign-ins while bounding the approximately 32 MiB scrypt working allocation. The gate also covers additional object IDs if trusted internal code obtains them. It is not an account-wide rate limiter, and separate isolates still have separate limits. Existing API wrong-password lockout behavior is retained.

The caller has a five-second end-to-end deadline, aborts its binding request on expiry and never repeats it. A computation already executing may finish after cancellation, but the object performs no account/session/database mutations and rejects expired output. Late results cannot resume the timed-out caller's account mutation. Users may explicitly try again after a transient 503; no automatic retry is added.

In durable mode, local sign-in rereads the active account after computation and rejects a changed password hash or role before issuing a session or updating login counters. It also respects a newly applied lockout. The existing inline deployment path is unchanged. Actual local D1 race tests replace a password, deactivate the account or change its role between computation and response; all reject without a session or counter reset.

The object never uses durable storage, alarms or logging. Real passwords/hashes exist only in bounded request/computation/response memory; JavaScript strings cannot guarantee immediate zeroization. Only the synthetic timing-equalizer hash is cached in memory. The replay map retains at most 128 request IDs and expiries through the bounded replay horizon (at most seven seconds in v2), without passwords or hashes; it is intentionally not persistent across isolate replacement. The private binding, purpose-bound signature and short expiry are the primary admission boundary.

## Verification and deployment boundary

Run `node --test tests/password-computation.test.mjs` and `npm run verify:api`. Tests cover unchanged inline behavior, existing hash interoperability, larger/escaped passwords, exact DTOs, purpose/tamper/expiry/replay rejection, bounded streams and concurrency, timeout/failure without fallback, and actual local workerd/SQLite Durable Object/D1 first-Admin creation, Staff create/reset, wrong/unknown/locked sign-in and empty object storage/alarm state.

Resource creation and configuration remain coordinator work after explicit approval of the exact development namespace. Standard deployment templates are unchanged. Do not reuse the scheduler/PDF object or enable durable mode without its binding. The optional object remains a local candidate until the exact deployed bundle, binding and modes are verified, then a bounded synthetic development sign-in and account lifecycle exercise succeeds with safe aggregate invocation evidence.

Existing Worker invocation metrics can be inspected read-only for script/version, time window, CPU/wall aggregates and outcomes without logging login bodies, cookies, usernames or authorization headers. Prefer these metrics before considering another sign-in attempt. Hosted verification must distinguish `exceededCpu`, `exceededMemory`, and ambiguous `exceededResources`, and preserve Google access while proving local recovery reliability.

The optional development provisioning workflow is specified in [DEVELOPMENT-BOOTSTRAP.md](DEVELOPMENT-BOOTSTRAP.md#optional-development-password-computation-wu-132). It requires an existing pinned scheduler, separate exact-resource approval, an ordered SQLite class migration, and independent provider-derived namespace capture. No provisioning or hosted password acceptance is implied by the local runtime tests.

## Fixed private failure diagnostics (WU-134)

The private object returns an empty error body and an allowlisted `x-ll-password-error` category. The API consumes this header and logs only the fixed `password-computation failure` label plus a fixed category: request preparation, binding fetch, response validation, deadline, an allowlisted internal stage, or unclassified internal failure. Arbitrary header values, exception text, bodies, identifiers, timestamps, passwords, hashes and keys are never logged or forwarded. Public callers continue to receive the same generic 503, without the private diagnostic header. The object itself does not log.

Independent-clock tests reproduce the existing strict future-envelope rejection when the receiver clock is behind the caller. This demonstrates protocol sensitivity, not a confirmed hosted failure cause. WU-134 left freshness checks, five-second deadlines, scrypt cost and inline defaults unchanged; the subsequent WU-136 protocol below adds bounded clock tolerance. Local sequential computation tests exercise gate reuse; existing actual workerd/SQLite object tests cover repeated account operations. Hosted diagnosis requires the exact deployed version and fixed failure category before choosing any behavioral fix.

## Bounded cross-runtime clock tolerance (WU-136)

Dependencies: private diagnostics identified the hosted `internal-envelope-time` rejection. Protocol v2 signs both `issuedAt` and `expiresAt`, requires an exact safe-integer 5000 ms lifetime, and rejects v1. The receiver permits at most 1000 ms of clock difference: issuance cannot exceed receiver time plus 1000 ms, and expiry must exceed receiver time minus 1000 ms. This one-second tolerance is an approved conservative technical default, not measured clock drift; successful hosted verification is still required.

Receiver queue/computation expiry is the earlier of receipt time plus 5000 ms and signed expiry plus 1000 ms. The caller retains its original five-second timer and signed expiry check before any account operation. Thus a tolerated stale envelope can consume bounded private work but cannot authorize a late caller. Replay IDs remain through signed expiry plus 1000 ms, even when the local work budget ends earlier; retention is at most seven seconds with an unchanged 128-entry cap. Scrypt cost, inline defaults, generic public errors and no-fallback behavior remain unchanged.
