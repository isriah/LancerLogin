# Admin scheduler controls (WU-096)

Dependencies: WU-092 scheduler API and separate WU-095 development deployment approval. These controls do not provision infrastructure or establish successful provider delivery.

Settings → Configuration exposes Background scheduler only to Admins through the existing protected route. Loading the section performs one status request; Reload scheduler status is explicit and there is no polling. An unavailable or malformed response does not become a stopped/default writable configuration. The UI accepts the seven current core jobs plus at most 57 additional jobs, bounded ID text, supported outcomes and valid integer JavaScript timestamps. Unknown job labels render as escaped React text. Missing core jobs fail closed.

Start and Stop send only an empty JSON object to the existing fixed action endpoints. A synchronous pending guard and disabled controls prevent overlapping requests. The prior snapshot remains visibly labeled Last loaded while a request runs. The UI reads status after a successful mutation and announces success only when that snapshot agrees with the requested state. Mutation failure, failed readback or a contradictory snapshot requires an explicit Reload before any further action. An uncertain request is never automatically retried. A reload can recover current access/state without repeating the action.

Stopping waits for the current pass and cannot retract provider work already sent. Job-pass outcomes do not imply delivery; a normal navigation link opens Integrations for authoritative provider status. Telemetry retains its independent consent. Times use the browser's locale and timezone; stopped jobs show retained next-pass timestamps rather than suggesting that a stopped scheduler will run them.

UI review reuses existing page hierarchy, primary/quiet controls, semantic status colors, surface/text/border tokens, spacing and radii. One Configuration h1 remains. Multiline job detail rows intentionally wrap; action rows remain vertically centered. Screenshots at 1280×900 and 390×844, light/dark, and representative custom branding were inspected. Link contrast was corrected during review; keyboard focus, 44px button heights and horizontal containment are covered. No UI-standard exception is required.

Verification: `npm run verify:dashboard` and `npm run test:browser -- tests-browser/scheduler-controls.spec.ts tests-browser/module-controls.spec.ts --workers=2`. Scheduler browser cases cover unavailable/access-loss/error/malformed responses, start/stop readback, mismatch and failed readback, explicit reload, no duplicate writes, escaped unknown labels, Admin route isolation, keyboard operation and responsive themes. Existing Module tests scope their alert assertions to their Modules section because the independent scheduler can also report unavailable status; the assertions retain their original behavior.

All browser verification uses local synthetic fixtures and blocks non-loopback requests. Hosted Admin control acceptance, provider processing, alarms after browser closure/redeployment and CPU limits remain separate development-deployment checks described in PLATFORM-SCHEDULER.md. These tests do not prove those outcomes.
