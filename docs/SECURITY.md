# Security model

LancerLogin is designed for a private adopter-owned deployment. Public source, releases, and documentation are separate from each installation's private repository, Cloudflare account, credentials, backups, and attendance data.

## Access and sessions

Administrators manage authenticated accounts in **Settings > Access**. Roster membership never grants an account. Local passwords use a unique-salt, memory-hard scrypt hash and are not recoverable. The browser runs scrypt (N=32768, r=8, p=1) and sends only the result; the Worker stores and compares a SHA-256 of it, so it never receives the password and sign-in costs it well under a millisecond of CPU. Because the Worker never sees the password, the 12-character minimum is enforced by the dashboard and the reset tool. Accounts whose password was last set before this change are checked once with server-side scrypt at their next sign-in and then stored the new way; until then, the salt lookup before sign-in reveals that such an account exists. Failed local sign-ins are counted atomically per account; the fifth failure blocks new sign-ins to the account for 15 minutes. A lock does not end existing sessions, so wrong guesses cannot sign the owner out. Local sign-in, first-Admin setup and kiosk pairing are also throttled per client network address within a ten-minute window. The dashboard's Pages proxy reaches the Worker through a service binding, which keeps the visitor's address; if a project lacks the binding, the proxy falls back to a fetch that Cloudflare gives one shared address, so all dashboard visitors share each limit until the next successful update adds it. The throttle stores only a keyed hash of the route and address with a window start and count, and the scheduled pass deletes these rows after a day. Sessions are signed, expiry-bound, Secure, HTTP-only, and SameSite=Strict; every protected request rechecks the active account, current role and session epoch. Signing out, an Administrator password reset or deactivation revokes every existing session of that account. An entire-installation restore revokes every existing session of every account and can never bring a revoked session back; only the Admin making the restore keeps their session, under a new epoch, and only when the backup holds their account as an active one (see [backup and restore](BACKUP-RESTORE.md#dashboard-backups)). Google sign-in and Google Calendar authorization state values are signed with a purpose-specific key, so they can never act as a session. Unexpected server errors return only a correlation ID; the detail stays in Worker logs.

Google OAuth uses signed, expiring state and validates issuer, audience, verified email, account activity, and explicit enablement. Google cannot be disabled when no active Administrator can sign in with a local password.

## Data and integrations

Integration credentials are encrypted with an installation-specific Worker secret and never returned in API responses. Saved but unverified or disabled integrations cannot send operational messages. Verification, credential changes, access changes, exports, and attendance changes are audited.

Google Calendar sends meeting titles, notes as event descriptions, and meeting times. Restrict the connected calendar to the intended audience. Discord signed interactions are verified before processing. Discord operations are limited to the configured server, LancerLogin-tracked message or event identifiers, and roles explicitly associated with active member labels. An Admin associates a role either in the dashboard or with a confirmed `/label` command from a paired Admin account; either way the bot must already be able to manage that role, and association changes no assignments. A manual role sync enumerates that server's members and changes only its selected mapped role after an Admin reviews a full preview. The adopter must restrict any staff-only Discord channel it chooses. LancerLogin does not moderate or delete unrelated Discord content. A label set to **Two-way** is also read every five minutes: a role added or removed in Discord changes that member's label, which can change their meeting audiences and attendance policies, so anyone who can assign that role in Discord can change it. Turn on two-way sync only for roles whose managers you would trust to edit labels. The optional FIRST connection sends FIRST only a team number, with the program and season and, for FRC and FTC, the saved Events API username and token.

Notion uses one integration token held by Core; modules never receive it. Each module can use only the Notion databases an Admin chose for it and the operations its manifest declared, and Core checks that a page belongs to the chosen database before changing it. This guards against mistakes, not against a malicious plugin. A plugin is trusted code: one that read Core's connection table with its own database access could decrypt the token with the credential service, as it could the FIRST credentials. Review a plugin's source before installing it. Give the Notion integration only the capabilities your modules need, and add it only to the databases they use.

CSV export prefixes formula-like values as text before quoting. This prevents roster or meeting data from being interpreted as a spreadsheet formula.

## Kiosk identity boundary

Fingerprint, RFID badge, NFC badge, member ID, and QR code input all resolve to a member ID on the kiosk before the shared attendance pipeline runs; a Discord kiosk code is the exception, resolved to its member by the Worker. This section describes the Raspberry Pi kiosk; [web kiosks](#web-kiosks-and-member-pins) differ as described below. Fingerprint templates remain in the R503 unless Admin-enabled cloud storage is enabled. RFID, NFC, and QR readers are treated as bounded keyboard-wedge inputs: the kiosk transforms each value with HMAC-SHA256 and an owner-only local secret, then stores only the keyed digest and member mapping. Raw badge and QR values, local digests, and the local transform secret are excluded from Worker requests, D1, logs, fixtures, and portable dashboard backups.

Member ID entry is explicit touch or keyboard input and succeeds only for a member in the kiosk's current active-roster cache. Stored badge and QR mappings also fail closed when the mapped member is no longer active. Local authentication maintenance is loopback-only and requires the rate-limited local settings PIN. Five wrong PINs lock entry for 30 seconds, doubling with each further lockout up to one hour until a correct PIN; the counter is stored in the owner-only PIN file, so a service restart does not reset it. The local service accepts only a Host header that names the kiosk itself (loopback, its hostname or `.local` name, or one of its current addresses, on its own port), which defeats DNS rebinding from a page opened in a desktop browser on the Pi. Before pairing, another device on the LAN can pair the kiosk only with a six-digit setup code shown on the kiosk's own screen; wrong codes rotate it and pause LAN pairing. LAN clients see only `ok`, `paired` and setup state from `/health`. Separately, an Administrator can authorize a kiosk-scoped dashboard fingerprint enrollment session lasting at most five minutes. It grants no general maintenance unlock, requires physical name confirmation, uses verified free slots only and rechecks current server authority before confirmation and reader storage. Cancellation, expiry, changed pairing, disabled Attendance or lost administrator authority prevents further enrollment. Unknown credentials do not fall back to another method. Only an Administrator can change a selected active kiosk's configured method. Both configuration endpoints deliver that device's own method, and a heartbeat updates only its reported state. Changing one kiosk or the retained historical installation setting cannot change another kiosk's selection.

Disabling Attendance or retiring a kiosk revokes server-side authority, but it cannot erase an R503 template or a local badge or QR mapping from a disconnected Pi. The dashboard's remote kiosk commands are fixed and narrow. The only one that erases data, **Erase unlinked fingerprints** (`erase_unlinked_fingerprints`), requires Admin confirmation and erases only reader templates that no member mapping references; there is no remote command that wipes mappings, the queue, pairing or the Pi. Before repurposing or decommissioning a kiosk, unlock **Authentication maintenance** on that device, remove local mappings and wipe its card.

### Web kiosks and member PINs

A web kiosk pairs with a single-use, 8-character code that expires after ten minutes, and receives the same kind of kiosk credential as a Pi; D1 stores only hashes of the code and the credential. The differences are in where the credential lives and what protects it:

- **The credential is in the browser.** A web kiosk keeps its credential in the browser's IndexedDB storage for the dashboard origin. Anyone who can use that browser profile, or run code in it, can read the credential and act as the kiosk. On a Pi the credential is in owner-only files of a dedicated service account.
- **The settings PIN is a local screen lock.** The 6 to 12 digit settings PIN is chosen and checked on the device, to keep members out of the kiosk's maintenance menu. The server never sees it, and it does not protect the credential or the cached roster.
- **A paired kiosk's credential is trusted for PIN handling.** With **Require PIN** on, the Worker accepts a scan the kiosk says it checked offline (`pinCheck: "offline"`) without a PIN, even if the member has been locked since, and it lets the kiosk set a member's first PIN and reset any member's PIN from its maintenance menu (`/kiosk/pins`), without a dashboard sign-in. PIN sets and resets are audited with the kiosk's name. Someone holding a kiosk credential can therefore record a visit for any active member and replace PINs.
- **Offline PIN checks use cached hashes.** A kiosk with **Require PIN** receives each member's salted PBKDF2-SHA256 hash to check PINs offline. A 4 to 6 digit PIN has at most a million values, so a copied hash can be guessed quickly whatever the hashing. Online checks are throttled per member (after five wrong PINs: 30 seconds, one minute, then five minutes between tries) and can lock with **Kiosk PIN lockout**. Each online try is counted toward both before its PIN is checked, so tries sent at the same time get no more checks than tries made one after another, and never more than the lockout's configured number before the lock. Offline checks are only counted and reported on reconnect.

For these reasons, pair web kiosks only on devices the team controls, keep them out of shared or personal browser profiles, and retire a lost or borrowed device on **Kiosks** at once: retiring revokes the credential, so the copy on the device stops working. A member PIN or member ID proves much less than a fingerprint; use a fingerprint kiosk where one member signing in for another matters.

Discord kiosk codes are single-use, expire after two minutes, and are stored only as SHA-256 hashes. A code is claimed online by the Worker and names the member itself, so it needs no PIN; wrong codes are throttled per kiosk (after five in a row: 30 seconds, one minute, then five minutes). A code is consumed when it is claimed, even if the scan is then refused.

Peer-to-peer fingerprint sharing is retired; its endpoints reject transfers and cloud storage is the only synchronization path. See [privacy](PRIVACY.md#retired-peer-fingerprint-sharing).

### Optional server-managed fingerprint storage

Cloud storage is off by default. An Admin must explicitly confirm its biometric-storage boundary. Enabling it authorizes automatic upload of identity-verified mapped enrollments and automatic download to every currently authorized paired R503 kiosk. Existing source kiosks need not remain online after upload. There is no additional local peer-approval requirement for this option.

The Worker receives a template over authenticated HTTPS, encrypts it for durable storage, and can decrypt it for an authorized kiosk. This is not end-to-end encryption against the server. A separate 32-byte `FINGERPRINT_VAULT_KEY` root secret derives distinct AES-256-GCM and HMAC-SHA256 keys using HKDF-SHA256. Each ciphertext uses a fresh 12-byte nonce. Authenticated context binds the installation, vault generation, key identity, immutable roster row, fingerprint identity and keyed digest, source pairing, enrollment and creation time. D1 contains ciphertext and operational metadata, never plaintext templates or the root secret. Browser/Admin routes expose settings and counts only, not templates or a valid-ID catalog.

Uploads require both the external member ID and immutable roster ID. New online enrollments retain this identity in protected local mappings, and downloaded copies preserve it. Older or offline mappings without a verified immutable identity require re-enrollment before sharing. Retired review approvals cannot supply that authority, and their cloud copies are revoked without removing independent fresh enrollments. Neither current ID equality nor a recycled external ID silently authorizes old-template backfill. Unknown reader slots are never read for backfill. A download may reuse only an authenticated byte-identical occupied slot already bound to that same immutable member; otherwise it uses a verified free slot and never overwrites.

Every cloud operation checks Attendance enablement, active immutable member binding, vault generation/key identity and the current kiosk credential/pairing. The Worker rechecks authority after encryption or decryption. Retiring or replacing a source kiosk revokes its future requests but does not erase an otherwise valid member's retained fingerprints. Member deactivation or ID change clears that member's cloud templates. Storage disablement, Attendance disablement or portable installation restore removes vault authority and cloud ciphertext. Completed local journals prevent a removed mapping being silently recreated. Existing local copies remain and require individual device review.

The runtime processes at most two source captures and eight missing templates per poll. Compatible clients fetch a revision-bound complete catalog (up to 10,000 entries) when it changes and batch only missing templates; stale revisions or authority changes reject the response. Older clients retain paginated manifests. The runtime bounds HTTPS requests and replies, and uses the shared sensor lock and owner-only metadata journal for idempotent recovery. Plaintext exists briefly in Worker and kiosk memory, not intentionally in D1, files or logs. A compromised server, authorized kiosk, owner-level Pi account or memory dump can expose it. Missing or changed keys fail closed; preserve ciphertext and recover the original separate key. An Admin can still disable storage to delete cloud copies when the key is unavailable. See [PRIVACY.md](PRIVACY.md) and [BACKUP-RESTORE.md](BACKUP-RESTORE.md).

### Fingerprint re-enrollment and mapping reset

Legacy mappings cannot acquire immutable identity from a current external-ID lookup alone. Staff must re-enroll the member while the kiosk is online, using PIN-protected Authentication maintenance or a dashboard enrollment session with physical name confirmation and a verified free slot. There is no mapped-slot approval screen, biometric proof snapshot or member-lookup approval route. Retired approval identifiers remain denied so removing old provenance fields cannot revive their cloud authority. Historical review data is not a portable source of trust.

Updating software does not automatically clear local mappings or reader templates. A deliberate reset can start re-enrollment from clean associations. Preserve protected kiosk state first and wait for every active kiosk's reset acknowledgement. Reader templates remain and require deliberate replacement of known slots; unknown occupied slots are never automatically overwritten.

An audited mappings-only reset atomically removes cloud authority and live ciphertext, rotates/disables peer relay authority, clears queued transfers, and queues commands for each current active pairing. Fingerprint uploads and transfers remain blocked for a pending pairing until its durable local acknowledgement. Command polling stays available while sharing is off. Local reset quiesces sharing and clears only fingerprint identity associations under the sensor lock; it does not erase reader templates, attendance queues, roster, pairing or other authentication mappings. It also leaves completed import journal records in place, so **Erase unlinked fingerprints** afterwards skips the slots those records name; see [privacy](PRIVACY.md#fingerprint-re-enrollment-and-reset). Offline kiosks can still use old local mappings until reconnect, so the dashboard reports per-pair pending status rather than instantaneous global removal.

## Plugins

A plugin is fully trusted code with the same access as LancerLogin itself: it runs in the installation's Worker and dashboard and its build runs in the deployment workflow. Plugin changes from the dashboard need an Admin, fresh authentication, a trust confirmation and an audited commit, and they deploy only through the backup-first update flow. Cross-module access without a signed-in user requires an explicit Admin grant. See [module plugins](MODULE-PLUGINS.md#trust).

## Updates and recovery

Kiosk unpairing is a loopback-only, same-origin, PIN-authorized and explicitly confirmed local operation. It drains in-flight installation work and blocks when attendance is pending. A durable owner-only journal archives installation-bound files before the service restarts, preventing cached credentials, roster, mappings, queue history and fingerprint trust from carrying into a new pairing. Interrupted archival blocks scanning and pairing until locally authorized recovery finishes; malformed or unsafe filesystem state fails closed. The local PIN and NetworkManager connections are retained, and no reader template is erased. This is not remote credential revocation: retire the old dashboard device separately and protect the archive as credential-bearing biometric-related material. Archives are deleted when the kiosk is paired again and 30 days after unpairing; an unfinished archive transaction is never deleted.

Web updates require current Administrator authorization, an exact dashboard origin, a pinned official release allowed by the server-owned track, an entire-installation backup, and a durable request. Stable is the default; Beta requires explicit audited consent. The browser cannot choose deployment resources, tags or commits. Refreshing status never redispatches. Recovery retains a deployment lock until explicit review confirms the next action and API/Pages health.

Tracks never install or downgrade software. Started web updates and recent pending kiosk updates lock the track. Beta preparation requires the reviewed private controller; a kiosk needs its installed channel-aware root helper. Execution independently checks release flags, complete assets, exact tag/commit and immutable beta metadata. See [UPDATE-TRACKS.md](UPDATE-TRACKS.md).

Physical kiosk updates are separate from web updates. A kiosk installs only a server-pinned, immutable official release whose installer and archives match GitHub's recorded asset digests, and rolls back automatically when the new release fails its health check. Dashboard state is not proof of a physical update; confirm the release the kiosk reports. See [KIOSK.md](KIOSK.md#update-a-physical-kiosk) and [WEB-UPDATES.md](WEB-UPDATES.md).
