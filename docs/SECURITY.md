# Security model

Discord channel-manager operations are confined to the configured attendance channel and persisted LancerLogin-owned message identifiers. The scheduler may create or update those tracked messages, pin the tracked status message, and delete a tracked absence notice after its recorded expiry. The attendance-report button accepts only signed interactions from the configured server and channel on the current tracked attendance-help message, then returns the requesting linked member's report ephemerally. It never discovers messages for bulk moderation and never edits, unpins, reorders, or deletes unrelated channel content. All managed content disables implicit mentions; absence notices explicitly allow only the linked recipient IDs selected from attendance data.

Discord anomaly reports are confined to a separate Admin-configured text channel in the same verified server. The configuration refuses the member-facing attendance channel, and the report payload disables all mentions. LancerLogin verifies server and channel type, but the adopter must restrict Discord channel visibility to authorized attendance staff. Saving, rotating, disabling, or removing Discord disables report delivery until an Admin approves the private channel again. Per-meeting delivery records and Discord's enforced nonce prevent retry duplication; LancerLogin never edits or deletes anomaly-report messages or other channel content.

Discord calendar delivery is confined to the verified server and to scheduled-event identifiers returned for LancerLogin's own tracked meeting mappings. Durable operations contain meeting IDs, generations, provider event IDs, retry state, short-lived processing leases, and safe error text; event title and notes are read from the authoritative meeting only at delivery time. Each provider event carries an opaque, generation-specific LancerLogin reference in its location so an ambiguous successful create can be reconciled without exposing meeting content in the retry queue or creating a duplicate. Delete and restore operations never enumerate or remove untracked server events. Disabling or losing verification pauses the queue, and removing or rotating the integration clears only Discord calendar mappings and operations plus their compatibility state—not unrelated tracked Discord messages.

Local sign-in passwords are never recovered. LancerLogin stores a unique-salt, memory-hard scrypt hash (N=32768, r=8, p=1) and verifies it with constant-time comparison. Unknown usernames receive the same scrypt verification work as known users. Five consecutive failed passwords lock that account for fifteen minutes without storing an IP address; a successful sign-in or the local recovery tool clears the failure state. A forgotten local credential is reset only from the interactive local recovery tool using the adopter's scoped D1 authorization; it cannot be emailed or displayed.

Google OAuth is selectable at first setup and is verified server-side in the Worker with signed, expiring state plus issuer, audience, verified-email, active-user, and explicit-enablement checks. Either method or both may be enabled, but Google cannot be disabled when no active Admin has a usable local password. Integration settings use an installation-specific 32-byte Worker secret and AES-256-GCM with a fresh IV per save. Dashboard responses return only enabled/saved/verified state and timestamps, never saved values. Resend and Discord challenges expire after ten minutes and store only SHA-256 hashes; Discord proof also binds the configured server and provider message ID. Rotation clears verification, and disabled or unverified provider credentials cannot drive operational email or Discord workflows. Enablement, save, verification, rotation, and removal controls use the Admin-only integration capability.

The central Google client is encrypted once per active connection, with a separate encrypted candidate during replacement. Organizational Calendar/Drive grants cannot be written by staff login. Single-use purpose/session/generation-bound state, PKCE, current Admin SQL predicates and explicit verified promotion protect reconnection; local Admin recovery remains required. Revocation and reported scope loss fence stale proof reuse. Active/candidate encrypted envelopes are slot-bound and backup validation happens before destructive restoration. See [GOOGLE-CONNECTION.md](GOOGLE-CONNECTION.md) for the complete contract and current local-verification limits. Calendar delivery retains its fixed opaque identity, generic summary and timing-only payload; no roster, notes or attendance are sent.

For local sign-in, the Worker issues a signed, expiry-bound session containing only user ID and role. Signatures are HMAC-SHA-256 with an installation secret; tampered and expired sessions are rejected before authorization. Every protected request also reloads the active user and current role from D1, so deactivation or demotion takes effect immediately instead of waiting for the eight-hour session expiry. The generated Pages `_worker.js` forwards `/api/*` to the Worker, so the browser keeps Secure, HTTP-only, SameSite=Strict cookies on one first-party Pages origin instead of depending on third-party Worker cookies. Every JSON mutation requires `application/json`, forcing hostile cross-origin browser requests through a CORS preflight; untrusted origins receive no permission. This also protects the unconfigured first-Admin bootstrap, where no session exists yet. Google uses the same Pages `/api/auth/google/callback` origin. A Google-only installation refuses removal of its only configured sign-in integration.

Attendance CSV cells beginning with spreadsheet formula markers are prefixed as text before RFC-style quoting. This prevents organization-controlled meeting or roster text from becoming an executable formula when an export is opened in spreadsheet software.

Meeting-weight definitions are installation-scoped and Admin-only to manage. Admins and Operators may select an active category while creating or editing a meeting. Each meeting stores a bounded positive weight and category-label snapshot; later category edits and retirement cannot rewrite historical attendance. Category lifecycle, ordering, and explicit meeting assignment changes are audited. Backups restore category definitions before meetings so saved references remain valid.

The optional community telemetry collector is isolated from adopter resources. It rejects fields outside the documented five-field allowlist, rejects IP-shaped location text, HMAC-hashes opaque install IDs with a collector-only secret, stores one daily row, and applies edge/global admission limits. Observability is disabled in its generated configuration. Its summary endpoint requires a separate long bearer token and returns aggregates only; metro groups require five distinct installations.

## Committee Staff identity

The modular development application adds a true `staff` user role. It has no attendance, roster, kiosk, or installation-administration capability. Admin and Operator attendance privileges remain unchanged. Staff can sign in using local credentials or an explicitly registered Google email; module access additionally requires the installation module and an explicit current grant. A role change never writes module grants. Every protected request reloads active identity; a signed token claiming Admin cannot override a stored Staff role. The browser reloads identity and module access when focus returns.

Account creation and updates check the acting active Admin inside the SQL mutation, including after asynchronous password hashing. Updates additionally preserve the last active Admin. Only a successful mutation writes its audit row. Installation restores reject unknown user roles and a configured backup lacking an active Admin before constructing destructive statements.
