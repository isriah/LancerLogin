# D1 export candidate transport

WU176 adds a portable Fetch transport for an opaque application D1 SQL export. It returns an **unverified backup candidate**, not a recoverable-backup assertion or an `engine.backup` adapter. It executes no SQL, restores no database, changes no table selection and makes no application writes. The provider export itself is an operation requiring maintenance coordination: Cloudflare documents temporary database unavailability and cancellation when polling stops. See the [official D1 export API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/export/).

## Composition

`createDatabaseExportTransport({ pins, token, store, fetch })` accepts the existing encrypted `createArtifactStore`, a server-only provider token, and optional injected Fetch. `pins` has exactly `installationId`, `accountId`, `applicationDatabaseId`, `updaterDatabaseId`, and `exportStorageHost`. Application and updater database UUIDs must differ. Resources are fixed at construction; no caller can supply SQL, tables, a download URL or replacement resource.

The storage hostname is an exact trusted-bootstrap pin within `*.r2.cloudflarestorage.com`. Provisioning must obtain and review the hostname from an authoritative Cloudflare export response; this milestone does not discover or provision it. If the actual provider uses another hostname shape, deployment remains blocked pending an explicit reviewed transport change. No wildcard destination is used at download time and no browser override exists. Only a provider-returned HTTPS URL matching that hostname, without credentials, fragments or nondefault ports, is accepted. Provider requests and downloads reject redirects. The Cloudflare bearer is sent solely to the fixed `api.cloudflare.com` export endpoint; storage downloads receive no Authorization or Cookie headers.

## Durable protocol

- `begin(operationUuid)` atomically claims an encrypted operation before one initial fixed POST `{ output_format: 'polling' }`. If its acknowledgment or bookmark persistence is lost, repeated begin and advance do not restart an export. The operation remains unknown for operator reconciliation.
- `advance(operationUuid)` makes at most one export poll using the exact persisted `current_bookmark`, or one download of the exact persisted signed URL. Poll responses must preserve `at_bookmark`. Provider errors become a fixed failed outcome. Transport ambiguity returns only unknown; provider messages and private URLs are never returned or logged.
- Completed exports enter staging. Original bytes are capped at 16 MiB, digested before the first chunk, and written through the existing authenticated encrypted chunk store, at most eight chunks per advance. Every resumed download must match the frozen SHA-256 and byte length. Lost chunk acknowledgments are resolved through immutable chunk readback; they cannot replace earlier bytes.
- A separate advance seals complete stored chunks through full encrypted readback, without another download. This also recovers a lost final-chunk acknowledgment after URL expiry. Advance then returns `{ outcome: 'backup-candidate', candidate: { operationId, bytes, sha256, verified: false } }`. `read(operationUuid)` is a trusted server-only API returning original bytes and candidate metadata after checking the seal and digest again. It must not be exposed through public status endpoints.

Operation metadata, bookmark and temporary signed URL are encrypted by the existing installation-bound operation codec. Original SQL chunks use the existing per-artifact authenticated encryption and digest checks. The signed URL is removed from operation state on completion. The transport adds no schema: it uses updater-state migration 0002, never the application database. It does not read or return secret configuration.

Each network response has a 20-second Fetch/read deadline; provider JSON is capped at 64 KiB and SQL at 16 MiB, including streaming enforcement. A full-size test counts all D1 statements plus HTTP requests and requires each staging advance to fit 50 subrequests. Repeated bounded whole-file downloads trade bandwidth for simple digest verification and restartability; signed URL expiry can stop incomplete staging. The maintainer must schedule polling promptly and serialize each operation. No internal polling loop or automatic restart exists.

## Verification and remaining gates

Run `node --test tests/updater-database-export.test.mjs`. Four synthetic tests use actual SQLite-backed updater storage and checkpoint encryption: maximum-size original-byte recovery after factory restart with full request budgets; lost initial/poll acknowledgment; hostname/redirect/token/oversize/database pins; and lost chunk acknowledgment plus changed-download rejection. No live database, credentials or provider requests are used.

This proves export transport and durable original-byte retention only. It does not prove SQL authorization, schema or migration-ledger consistency, a validated restore, external-provider publication safety, secret recoverability, or write quiescence. Even matching before/after schema ledgers would detect only some drift and cannot prove a write fence. A real maintenance/write fence, complete current-schema restore validation and recovery semantics, retention/custody, provider permissions and independent bootstrap remain prerequisites before exposing any candidate as a verified backup or allowing migration/restore progression.
