# Foreground updater progress (WU189)

The independent recovery page now advances a selected job automatically after **Continue automatically** or an acknowledged explicit recovery/preparation-retry action. One controller owns status reads, advances and manual actions. It sends at most one request at a time, using existing POST, CSRF and nonce protections. Automatic progress is bound to the acknowledged job ID; a different job, failed job or completed reopening stops it. A succeeded/recovered code job still advances while maintenance remains closed or reopening.

Hiding the page cancels only future timers. Showing it reads status before resuming the same armed job. Manual Pause cancels automatic intent, including a recovery request whose acknowledgment has not yet arrived; that acknowledgment still updates status and settles the saved request without restarting progress. The controller never aborts or releases an underlying operation. A stalled request remains the sole owned flight until it settles. Reloading or signing in does not arm a job automatically.

An uncertain response schedules status readback before another same-job advance. This is safe because the engine's durable operation state determines whether that advance continues or reconciles; the browser never clears ambiguity or selects a replacement operation. Repeated unchanged reconciliation backs off from 2 seconds to at most 30 seconds and pauses after five unchanged results. Three consecutive request failures also pause. Confirmed bounded running advances use a 250 ms gap; status readback retains a one-second gap. Status GET never advances work. Idle/unarmed pages no longer issue an unconditional five-second status poll; Refresh status remains available.

The existing recovery session retains its 15-minute absolute expiry. The server's `expiresAt` shows a warning during the final 60 seconds. At the indicated expiry, the client conservatively stops new advances, retains and observes any underlying flight, shows the sign-in form and keeps the recorded job visible. A server 401 remains authoritative even when client/server clocks disagree. No local clock calculation extends authorization. The warning is informational and stable rather than an every-second screen-reader countdown. Credentials are entered explicitly; signing in refreshes status but never arms automatic progress. Continue must be selected again. Recovery credentials and session authority are not saved in browser storage. Existing frozen recovery/admission request IDs remain intact after uncertain responses; autoarming requires the exact acknowledged lineage. There is no unattended server scheduler or guarantee that progress continues with the page closed. Seamless Admin-session handoff remains separate work.

The runtime passes its pinned recovery origin into the app-authenticated updater service. The service validates an exact HTTPS origin and returns only its fixed `/recovery` URL in status and start responses. The dashboard renders a native navigation link with `noopener noreferrer` and retains the normalized URL in sessionStorage scoped to the current dashboard origin, allowing navigation after maintenance makes app-authenticated reads fail or the page reloads. Cached navigation accepts no userinfo, query, fragment or alternate path; it carries no credentials or automatic execution intent. This is a navigation hint, not authorization. Application Admin routes remain protected by their existing appD1 checks and maintenance admission.

The dashboard bridge uses the existing settings notice, quiet-button, typography, spacing, border, focus and control-height tokens. One inline-flex alignment rule makes the native link a 44px control without introducing color/spacing literals. Desktop and mobile light/dark screenshots with representative custom adopter colors were inspected at 1280×900 and 390×844. Heading hierarchy, visible keyboard focus, link semantics and lack of page overflow passed. Existing lengthy mobile settings navigation and legacy recovery-panel spacing remain outside this change; no UI-standard exception was introduced. The standalone recovery page keeps its existing independent styles and 44px native controls.
