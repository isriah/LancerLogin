# Durable maintenance orchestration

Current implementation through WU198 also supports archived intermediate-schema recovery and optional guarded database restore when trusted runtime adapters supply the complete fence policy. Continuation holds carry exact operation identity; restoration retains the same closed epoch through prior-code deployment, fresh health and reopening. See [runtime restore](UPDATER-RUNTIME-RESTORE.md). The WU183 description below is historical: its schema49-only and unconditionally restore-disabled statements describe the original milestone, not the current optional composition.

WU183 design: construct the raw updater engine and maintenance control capability privately, expose an engine-compatible authenticated facade, and expose only application-execution methods for the existing lifecycle integration. Restrict initial admission to the known schema-49 migration chain and same-schema releases.

Updater-state migration 0007 records the job/epoch/phase owner and durable updater execution holds. Admission binds a job, closes application admission once and returns without waiting for its own application permit. Separate advances reconcile closure and drain existing permits. Only a closed matching owner may advance the engine. Live holds cover engine calls; a crashed execution remains an orphan hold and cannot be expired or force-cleared.

Adapter `withClosedEpoch` authority is derived from the private engine's current durable job/operation, its verified release and installed ledger, matching maintenance owner and a live local execution hold. It records the operation identity before invoking adapter work. Holds and pending engine operations block reopening across ambiguous outcomes. Backup authority comes from the encrypted engine checkpoint, never a caller boolean.

Reopening requires a succeeded or recovered job without pending operations/holds and a constructor-provided independent current-health reader. The exact job/epoch/installation and independently selected release identity must match. Failed jobs remain closed for an explicit preparation retry or compatible code recovery; failure never automatically reopens admission. Recovery admission freezes its original request, verifies failed-job/checkpoint lineage and hands the same closed epoch to the new recovery job through a guarded core method; handoff retries reconcile both durable records.

No API/UI/binding configuration is changed. Existing separately authenticated recovery remains the control path once application admission closes; seamless in-app control is still a gap. Schema-46 capture/restore and general incompatible upgrades remain unsupported. Actual backup/replay and provider-health implementations are required composition dependencies, not supplied by fixture success.

## Constructor and composition contract

`createMaintenanceOrchestration({ database, installationId, store, verifier, cipher, readDashboard, createAdapters, readHealthEvidence, capability, executionCapability })` returns the existing engine service methods plus `executionCore`. Give the facade to both authenticated updater services, and the restricted execution core to the existing application maintenance transport. Never retain or route around it with another raw engine instance. The core exposes execution/proof methods only; its maintenance capability is private.

`createAdapters({ withClosedEpoch })` must provide the real staging, checkpoint, validated-backup, code deployment and health adapters. Protected adapter operations call `withClosedEpoch({ installationId, operationId, manifestSha256? }, callback)` during their engine invocation. The callback receives frozen installation/job/operation/epoch, current installed schema/ledger, selected signed manifest digest, and checkpoint-derived `backupVerified`. Closure persists after the callback, through pending/ambiguous operations and terminal health. An in-memory callback alone is insufficient: the durable owner and execution hold are also required. The initial schema-49-only admission intentionally has no migration steps; broader catalog-backed upgrades need a later explicit composition change.

`readHealthEvidence(expected)` must independently read current provider/API/schema/asset health for the supplied installed release and return the exact expected tuple plus `verified: true`. Fixture receipts are not production evidence. Recovery restores code only; `recoveryQuiescence` is forcibly false and database restore remains disabled. Recovery handoff validates backup and compatibility before saving its immutable request; a lost acknowledgment resumes the same request and closed epoch. Invalid preparation retries are rejected before persisting their phase.

Apply updater-state migrations through 0007 to the independent updater database. `database` uses primary-start sessions where supported; a binding without sessions must be primary-only. The injected engine store must also supply consistent primary reads. No expiry or public force-clear exists for application permits or updater holds. A process crash during dispatch can leave an orphan hold requiring a future separately reviewed readback resolution procedure. Hold tombstones are retained; bounded retention/compaction is a future operational concern.

Each advance performs at most one drain transition or engine step, with a fixed number of owner/hold/core reads and CAS statements around the existing adapter's bounded work. This is not a whole-provider query budget assertion: concrete adapter/store costs must be included during bootstrap composition. No hosted runtime, general schema-46 backup, restore validity, or seamless in-app control continuity is claimed.

## Verification

`node --test tests/updater-orchestration.test.mjs` runs five local SQLite/actual-engine cases with synthetic signing keys and synthetic backend receipts. It covers own-request drain without deadlock, close and recovery-handoff lost acknowledgments, concurrent single dispatch, wrong-operation rejection and encrypted backup authority, failed-health closure, failed-job recovery lineage, persistent orphan holds, and invalid retry/recovery requests that leave the owner usable. No hosted calls or production credentials are used.
