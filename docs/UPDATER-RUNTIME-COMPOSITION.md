# Schema49 updater runtime composition (WU185)

Current implementation through WU200: schema46→49 upgrades and consecutive verified backups are composed; completed validation generations can be reused. The runtime exposes application, maintenance, recovery and exact-admission controls. Optional trusted fence policy enables guarded application restore through prior-code health and reopening. The Worker entrypoint/build exists and updater-state migrations through0008 are required. Private initialization now requires adoption input and live signed-release/schema/provider preflight; see [bootstrap preflight](UPDATER-BOOTSTRAP-PREFLIGHT.md). Hosted provisioning, actual initial installation/adoption, platform acceptance and independently supervised updater replacement remain separate. See [runtime restore](UPDATER-RUNTIME-RESTORE.md), [Worker entrypoints](UPDATER-WORKER-ENTRYPOINT.md), [validation generations](UPDATER-VALIDATION-GENERATIONS.md) and the current plan.md handoff.

The original WU185 contract below records its initial scope; its single-use/schema49/three-surface/restore-disabled limits are superseded by those later contracts.

`createUpdaterRuntime` in `apps/updater/runtime.mjs` joins the signed GitHub source, encrypted updater stores, real Cloudflare code transport, replay-validated backup, postdeployment health, maintenance orchestration and existing authenticated services. It is a constructor-driven runtime factory, not a deployed Worker entrypoint or resource provisioner. Updater-state migrations through 0007 must already exist.

The constructor takes exact pins for installation, Cloudflare account/Worker/Pages/production branch, three D1 resource IDs, Worker settings/nonsecret bindings, API/dashboard/recovery origins; application-release verification trust; three actual bindings; and updater-only secrets. The application, updater and single-use validation bindings must be different objects, and their configured IDs must differ. Trusted bootstrap must establish that those handles actually resolve to the pinned resources: object identity cannot detect two distinct wrappers around one database. No public request may supply bindings, trust roots or resource overrides. All updater stores and services use first-primary sessions where supported; a binding without sessions must be primary-only.

The runtime keeps the engine, internal capabilities, signing trust, provider tokens and encryption key private. It returns three separate fetch surfaces: `application` (existing app HMAC service), `maintenance` (distinct private lifecycle HMAC service), and `recovery` (independent credential/session service). Keep the first two on their intended private bindings; this unit does not publish them on an arbitrary public router. The recovery service enforces its pinned origin. Application DB-auth routes remain subject to maintenance; seamless in-app control while closed is not introduced here.

`initialize(bootstrapCapability, {releaseId,manifestBytes,signatureBytes,updaterVersion,artifacts})` is a trusted local bootstrap method, never an HTTP route. Artifacts is a name-to-Uint8Array Map of the signed installed release. Each call stages one bounded artifact chunk or completes one step. Its persisted identity, artifact operation IDs and cursor survive interruption. All signed artifacts are retained, including the prior dashboard archive needed by code capture. Initialization verifies schema49 and the complete release-owned ledger. If the engine's initialize acknowledgment is lost, retry accepts only the exact initial release/version/schema/sequence/ledger and empty job/checkpoint state. Completed bootstrap retries return without resetting jobs or antirollback state. Initial provider resources and deployment metadata must already match the supplied signed release; the later checkpoint capture verifies actual prior code and Pages marker. This method does not deploy initial application code or create credentials.

The runtime retains verified raw signed releases and exact GitHub asset identities in encrypted updater storage. Artifact downloads resume those identities. Code resolvers reverify retained bytes into each transport's opaque verifier ownership. A definitive API/Pages receipt is persisted before updating the runtime's deployment pointer and completing its engine operation. Failed-update code recovery resolves the last definitively deployed API release through that receipt, even after the failed job is replaced. Application-reported versions never select deployment authority.

Backup and health join the same private continuation/reconciliation dispatcher as code operations. Only schema49 same-schema upgrades and compatible code recovery are composed. The validation D1 is permanently single-use, so this factory cannot complete a second backup without a separately reviewed validation-resource lifecycle. No reset, cleanup or resource creation is provided. `recoveryQuiescence` remains false; database restore, broader schema migration composition, and separately typed updater selfdeployment remain unsupported.

Reopening uses a new durable health operation for the terminal job and closed epoch. It scans actual provider code, API/proxy health, ledger and public signed assets rather than reusing the engine's prior completed health operation. Ordinary bounded progress returns pending; a private orchestration signal preserves the reopening phase and closed core while returning normal service status. Definitive invalid health still fails closed and rotates the durable health operation, so the next retry starts a full fresh scan. A transient read-only network failure resumes safely. Only exact successful evidence can reopen admission. Cached completion is retained validation for that operation, not an unbounded monitoring promise.

Provider settings capture preserves secret inventories and existing secrets during code replacement. It does not recover secret values that provider APIs cannot read. Bootstrap must maintain separate secret custody for resource deletion/replacement recovery. No hosted CPU, D1 row quota, single-use target lifecycle or deployed compatibility acceptance is claimed.

Focused verification: `node --test tests/updater-runtime.test.mjs`. The test uses real SQLite application/updater/validation databases with schema49 and foreign keys, real signing/verifying/capture/replay/code/health/service modules, and a synthetic Fetch provider that consumes actual upload bytes and exposes resulting deployment state. It drives a target code deployment, failed target health, independent recovery login and prior-code redeployment, then fresh reopening health. It also exercises reconstruction, lost initialization acknowledgment, binding alias rejection, capability rejection, service authentication, sequence preservation, normal pending status and full rescan after a failed reopening scan. No provider success adapter is substituted and no hosted requests occur. Existing focused orchestration checks cover the modified pending-evidence branch alongside this integration test.
