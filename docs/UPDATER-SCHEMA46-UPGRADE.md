# Reviewed schema46 to schema49 runtime path (WU187)

The runtime now composes the compiled schema46 snapshot catalog, verified backup adapter and migration transport for the reviewed 46→47→48→49 chain. The existing schema49 same-schema path remains supported. Runtime/bootstrap resource, credential and provider prerequisites from WU185 still apply; nothing is deployed or provisioned by this unit.

Trusted bootstrap accepts only the compiled schema46 or schema49 ledger and signed release with that exact target schema. New application updates still require target49 and the complete reviewed migration chain. The original signed release must already advertise API schema compatibility through49, and both releases must satisfy the unchanged engine frontend/API and installed-version compatibility checks. This unit does not bypass maintenance-required or restore-required decisions.

Backup selects schema46 or49 only from the current authoritative closed-epoch state. Its durable identity, capture manifest and isolated replay receipt bind the chosen catalog and schema. The original checkpoint remains schema46 after migration: engine migration completion changes only the installed schema/ledger, leaving prior installed state, prior signed release, verified backup and recovery metadata intact.

Schema47 and48 are continuation states, not general initialization states. Orchestration accepts their exact reviewed ledger prefix only when the current signed update targets49, the encrypted checkpoint belongs to that job and retains a verified schema46 backup, and its backup job/epoch matches the closed maintenance owner. An invalid original backup blocks further migration. Recovery from an intermediate47/48 state is not composed here; those states are restricted to this active update continuation. The migration adapter additionally enforces current operation, signed artifact, from-schema ledger, closed epoch and checkpoint-derived verified-backup authority.

Runtime migration dispatch re-verifies the retained signed release into the migration transport's own opaque handle. Both initial dispatch and read-only reconciliation load the exact staged, digest-verified SQL artifact; application requests cannot supply SQL or choose a migration outside the current engine step. The accepted migration transport atomically applies each reviewed script with its native ledger guard. Lost acknowledgment reads the exact resulting ordered ledger and never replays a dispatched migration. Unresolved outcomes keep maintenance closed.

Focused verification: `node --test tests/updater-runtime.test.mjs tests/updater-orchestration.test.mjs tests/updater-migrations.test.mjs tests/updater-backup.test.mjs`. Runtime fixtures use real local SQLite and the actual source/verifier/capture/replay/migration/code/health/service modules with synthetic Fetch responses. The populated46 fixture loses the47 acknowledgment after commit, reconstructs the runtime, reaches47/48/49 with exactly three migration batches, retains its member row, rebuilt documentation artifact/revisions and historical claim-artifact pin, and opens only after target49 health and a fresh reopening scan. It decrypts the final checkpoint to verify the original46 ledger and verified46 backup; the isolated validation database remains46 with the original member, artifact/revisions and historical pin. A changed checkpoint backup schema at47 is rejected before another migration. The existing49 recovery/health scenario still passes.

This is a narrow reviewed migration composition. Application restore, general catalog/schema selection, validation-target reset/reuse, updater selfdeployment and hosted CPU/D1-budget acceptance remain outstanding. A single-use validation database still supports only one backup. No claim of secret-value recovery is added.
