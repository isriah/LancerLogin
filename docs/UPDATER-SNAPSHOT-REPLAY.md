# Isolated typed snapshot replay (WU182)

`createSnapshotReplay` in `apps/updater/src/snapshot-replay.mjs` validates a completed WU181 snapshot by rebuilding schema49 and comparing the resulting database. It does not restore the application database, promote the capture to a verified backup, or enable recovery. The result is a separate `typed-replay-v1` validation receipt bound to the capture commitment and validation database identity.

The trusted constructor receives installation, application D1, updater D1 and validation D1 pins, a private object capability, the encrypted updater artifact store, and the WU181 capture accessor. The three database identities must differ. Deployment composition must bind the actual database handle to the pinned validation resource; the module cannot discover a binding's resource ID. Only trusted orchestration may call `advance(capability, {operationId, snapshotId})`. No input accepts SQL, resource overrides or cleanup commands.

The target must initially contain no application objects. Cloudflare internal metadata is excluded. The first atomic batch creates fixed `_ll_snapshot_owner` and `_ll_snapshot_steps` tables and claims this target permanently for one operation and manifest. This unit provides no target reuse, reset, expiry or force clear. The validation target must be independently isolated from application writers for the complete replay and comparison period; the step guard fences this adapter's mutations, not unrelated privileged database clients.

Before each bounded mutation batch, the encrypted updater store records its pending step. The target batch checks the exact owner, manifest and expected step with a constraint-enforced receipt insert, applies at most eight catalog DDL or parameterized row statements, and advances its counter atomically. A timeout or lost acknowledgment leaves that pending step. Subsequent calls only read its exact target receipt. Missing receipt remains unknown and cannot cause redispatch. A lost initial claim acknowledgment likewise requires the exact singleton owner. A crashed or unacknowledged pre-dispatch step may therefore require abandoning the validation target; conservative availability is intentional.

Replay uses only release-owned schema SQL. The generated replay plan rejects cycles, self references and unknown parents. It creates tables, then the two composite-parent unique indexes (`members_installation_identity`, `users_installation_identity`), then rows in acyclic foreign-key order. D1 foreign keys remain enabled. It replaces automatically generated `sqlite_sequence` rows with the captured sequence, then creates the remaining indexes and triggers. Future catalogs require regenerating and reviewing this plan; unsupported catalogs fail instead of disabling integrity enforcement.

Captured rowids and INTEGER values bind as canonical decimal strings with `CAST(? AS INTEGER)`. REAL values use the codec's round-trip decimal representation with an explicit REAL cast. TEXT and BLOB bind original byte arrays with the corresponding cast, preserving embedded NUL and empty blobs. NULL remains SQL NULL. A mutation batch contains at most eight rows, at most approximately 256 KiB of decoded row data, and each statement stays below D1's 100-parameter limit. Artifact pages remain encrypted and chunked in updater D1.

`capture.describe` authenticates the completed encrypted manifest, pins, ordered page descriptors and total commitment. `capture.readPage` checks sealed chunk storage, page digest, exact canonical typed encoding and descriptor identity on each read. Validation reads every table, including empty tables and the query after the last expected page, and compares exact canonical page bytes. Final checks compare all catalog schema objects except the two exact validation metadata tables, native migration names, foreign keys, integrity, and the final owner/step. The sequence is included in the ordinary exact page comparison. Read-only comparison progress is resumable; mutations never run during that phase.

The integrity query is D1-supported `PRAGMA quick_check(1)`, combined with the explicit foreign-key and exact schema/data checks above. Actual Miniflare D1 rejects SQLite `PRAGMA integrity_check(1)` as unauthorized. This unit does not claim the full SQLite integrity-check algorithm.

Focused verification: `node --test tests/updater-snapshot-replay.test.mjs tests/updater-snapshot.test.mjs`. Tests use actual local Miniflare D1 for full schema49 and real SQLite-backed encrypted updater storage. They exercise populated composite foreign keys, operational rows, extreme rowids/int64, REAL, TEXT/BLOB/NULL, sequence restoration, lost acknowledgment without redispatch, unknown absent receipt, wrong owner, extra rows and manifest tampering. Per-advance accounting includes target statements and capture accessor/artifact/operation store reads and writes. This is local correctness and bounded-query evidence, not hosted CPU, storage or account quota acceptance. Resource provisioning, candidate/validation receipt composition into a verified backup, actual application restore, and maintenance/recovery authority composition remain separate work.

WU188 supersedes the initial single-use restriction with checked completed-generation reuse; see [UPDATER-VALIDATION-GENERATIONS.md](UPDATER-VALIDATION-GENERATIONS.md). Incomplete targets still cannot be reset or force-cleared. New replay targets also contain the exact generation metadata table and its SQLite primary-key index.
