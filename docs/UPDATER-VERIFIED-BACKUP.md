# Verified backup adapter (WU184)

`createVerifiedBackup` composes WU181 typed capture and WU182 isolated replay. Its `backup`, `continueOperation` and `reconcile` methods satisfy the engine adapter result contract. Route only the backup kind to these methods when composing the shared continuation/reconciliation dispatcher. No engine, service or deployment configuration is enabled by this unit.

The constructor owns pinned installation/application/updater/validation database identities, actual application and validation bindings, encrypted updater storage, and WU183's trusted `withClosedEpoch`. The current durable job/operation, selected release digest, closed epoch and exact schema49 signed migration ledger must match at every call, including completed receipt readback. Browser roles, supplied installed state or caller resource overrides grant no authority. Bootstrap must bind the handles to these identities and retain the validation target's independent isolation.

One encrypted `backup:<operationId>` record binds capture, validation and completion. The same operation ID identifies the snapshot and replay throughout reconstruction. Each invocation performs one bounded capture or replay step. Capture completion alone is never verified. The adapter checks the sealed capture manifest and the exact `typed-replay-v1` receipt, including every pinned resource, operation/snapshot ID, manifest commitment, catalog, schema and migration-chain commitment, before retaining its final receipt.

The engine-facing receipt contains `backupId` (operation UUID), `sha256` (capture manifest commitment), `schema:49`, and `verified:true`, plus retained authority identity and validation receipt. Here verified means independently replay-validated typed backup. It does not mean the application database has been restored or that restore transport exists. The original capture API still returns an unverified candidate.

Adapter and replay reconciliation perform no backup/replay claim, CAS, error-persistence or validation mutation. The trusted orchestration authority callback still performs its existing execution-hold accounting. A completed exact receipt returns applied; safe durable progress returns pending. The new replay read-only accessor proves exact target owner and step receipt before authorizing continuation. An absent receipt after dispatch stays unknown, with no replay, expiry or force clear. Before replay's durable claim exists, its absence proves no validation dispatch has begun. Capture-stage reconciliation permits only the existing idempotent updater-owned capture continuation; it cannot clear a validation-stage ambiguity. Lost final adapter acknowledgment reads the retained receipt without another target operation. Completed readback verifies retained validation identity; it is not a fresh target rescan.

The validation resource remains permanently single-use. There is no resource creation, reset, reuse or cleanup API. Failed validation is conservatively unresolved through this adapter, so orchestration remains closed. A later reviewed recovery/resource lifecycle must handle abandoned targets; this unit adds no bypass. Application restore, general schema upgrades, verified-backup consumption by a restorer, and hosted quota/CPU acceptance remain outstanding.

Focused local command: `node --test tests/updater-backup.test.mjs`. It runs actual schema49 capture and replay against Miniflare D1 with real encrypted SQLite updater storage, reconstructs the adapter every step, loses the target claim acknowledgment, checks receipt/epoch/job/release mismatches, proves read-only reconciliation does not write, and verifies absent claims never redispatch. Query accounting covers the complete adapter plus capture/replay/storage; production orchestration's authority reads/hold writes must be added when budgeting the final composition (capture invokes that authority twice). The focused run observed at most 19 adapter statements per advance. No hosted database is accessed.
