# Updater Worker entrypoint and offline artifact

WU199 supplies an executable Worker module around the existing independent runtime. It does not provision resources, install secrets, initialize an installation, deploy the artifact, or wire updater self-upgrade. Application restore additionally depends on the accepted runtime restore composition and its positive writer-fence policy.

Build locally with `node scripts/build-updater-worker.mjs --output <new-path>.mjs`. The existing esbuild dependency emits one ESM module, preserving the `cloudflare:workers` builtin. Output is bounded to 16 MiB and refuses overwrite. Build takes no installation configuration, key, or token input; the generic artifact can subsequently enter the distinct signed updater-release packaging workflow. No environment configuration or generated deployment manifest is supplied by this unit.

## Routing and authority

The default public fetch handler accepts only the normalized constructor-pinned HTTPS recovery origin and exact recovery/control paths. Query strings, encoded path alternatives, other origins, private service paths, and bootstrap routes are rejected. The existing recovery and delegated-control services retain their authentication, CSRF, nonce, and absolute session-expiry rules.

Named `ApplicationUpdates` and `MaintenanceLifecycle` WorkerEntrypoint classes expose fetch only. The former accepts exact `https://updater.internal/v1/…` service paths; the latter accepts exact `https://maintenance.internal/private/maintenance/…` lifecycle paths. Their existing independent HMAC verification remains authoritative. They are not reachable through the public handler. Bootstrap must bind the application to these named entrypoints, rather than the default entrypoint. Cloudflare documents named targets in its [service bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/) and [WorkerEntrypoint RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/) documentation.

Every accepted request performs one primary updater-D1 join of singleton state and the encrypted `runtime-bootstrap` operation. The checkpoint key must authenticate a completed bootstrap record for the configured installation before runtime construction. Missing, interrupted, or invalid initialization fails closed. There is no HTTP or RPC initialize method: a later trusted bootstrap workflow must create the schema and complete the existing runtime's resumable initialization before enabling these routes. Runtime construction remains per invocation; no cross-request authority cache is introduced.

## Trusted configuration contract

Exactly these bindings are accepted: `UPDATER_CONFIG`, `APPLICATION_DB`, `UPDATER_DB`, `VALIDATION_DB`, `CHECKPOINT_KEY`, `GITHUB_TOKEN`, `CLOUDFLARE_TOKEN`, `APP_HMAC`, `MAINTENANCE_HMAC`, and `RECOVERY_CREDENTIAL_SHA256`. Extra bindings fail closed. The three actual D1 binding objects and their configured resource IDs must be distinct. Binding-to-resource correspondence still requires trusted provisioning evidence; JavaScript object identity cannot prove the cloud database ID.

`UPDATER_CONFIG` is strict JSON, at most 128 KiB, with exact `format: 1`, existing runtime `pins`, and `trust` fields. Trust uses the application's pinned product/channel/repository/key ID and a 64-character lowercase hex Ed25519 public key. Pins include all three database IDs, account/Worker/Pages identity, production branch, pinned settings and nonsecret bindings, and normalized API/dashboard/recovery HTTPS origins. Requests cannot supply any of these values. The optional exact `fencePolicy` contains `maintenanceService`, `secretBindings`, `adoption`, and `coverage`; the restore-capable runtime validates their detailed attestation contracts. Omitting it leaves restore unavailable.

The checkpoint key and two distinct HMAC secrets are 32-byte lowercase hex values. The recovery credential is supplied only as its SHA-256 hex digest; provider tokens remain separate secret bindings. Configuration errors and internal initialization/runtime errors return a fixed 503 response without exception details. Existing captured Worker settings preserve secret inventories, not recoverable secret values: independent bootstrap secret custody remains necessary.

## Local evidence and remaining gates

`node --test tests/updater-entrypoint.test.mjs` passed 2 focused tests in 21.462 seconds on the WU199 base. One uses actual signed release verification, encrypted storage, SQLite, and trusted runtime initialization to check configuration, binding isolation, public control/recovery routing, wrong origins, and sanitized unavailable responses. The other runs the exact 815,760-byte compiled artifact in workerd through Miniflare, transfers the synthetic initialized state with parameterized D1 writes, and exercises actual named service bindings, authenticated status, maintenance admission, and public/private separation. No provider or hosted account was contacted. The fixture transfer is test-only and is not a bootstrap interface.

The route adds one D1 binding call per invocation before runtime work. This must be included in integrated request budgets (a runtime path using 49 calls leaves 50 including routing, with no margin). Compilation and local routing do not establish hosted CPU, row, storage, or subrequest acceptance. Resource provisioning, an exact trusted initialization runner, secret installation/custody, routing deployment, positive deployed-writer adoption, and hosted acceptance remain explicit gates. This artifact alone does not enable recovery quiescence or self-deployment.
