# Positive deployed writer-fence evidence (WU197)

Dependencies: shared signed application verifier, encrypted artifact store, reviewed API writer coverage, and independently established deployment adoption. This component does not enable restoration or change runtime, maintenance, services, routing or configuration. WU198 must compose its authority callback with WU196 and durable recovery handoff.

## Constructor authority

`createWriterFence({pins, adoption, coverage, token, verifier, store, withAuthority, fetch})` returns `prepare(expected)` and `withWriterFence(expected, callback)`.

`pins` identifies installation, application D1, account, API Worker, maintenance service, exact nonsecret bindings, exact secret name/type inventory and pinned Worker settings. It requires the application DB, MAINTENANCE private service binding, MAINTENANCE_INSTALLATION_ID value, RELEASE_VERSION, and MAINTENANCE_APP_KEY secret inventory. Secret values are never read or persisted. Wrong secret material must fail closed in the reviewed application implementation; inventory proves configuration presence, not secret correctness. Extra/unpinned bindings or supported settings fail closed.

`coverage` is a constructor-owned allowlist of exact API artifact SHA256, protocol `maintenance-v1`, and explicit entry points: HTTP, scheduled handler, scheduler fetch and scheduler alarm. These entries assert a completed review of `runApplication`/execution scopes, D1 writes, provider effects, waitUntil work and scheduler dispatch. Synthetic test bytes carry an explicitly synthetic fixture assertion; they are not evidence that real production bytes have passed that review. A valid release signature authenticates code bytes; it never establishes this coverage assertion by itself.

`adoption` pins the same installation/resources plus a SHA256 reference to an independently retained adoption record and contract `exclusive-writers-fenced-adoption-v1`. This trusted record must establish the complete writer inventory, exclusive deployment/configuration ownership, correctly fenced initial activation and completion of older untracked executions. Services outside the covered API must have no application D1/provider writer authority, or require a separately reviewed extension; this initial component cannot approve them. Neither provider snapshots nor this record's supplied hash verify those external facts. Browser requests, snapshot files and release metadata cannot supply the record or coverage allowlist. Absent prerequisites must block composition; no timeout or caller boolean substitutes for them.

## Use and evidence

`expected` contains `{installationId,applicationDatabaseId,epoch,jobId,operationId,holdId}`. `withAuthority(expected, callback)` is a trusted constructor dependency. It must freshly establish exact primary engine/core/owner identity, the current exclusive live updater hold, no active/ambiguous application execution, original checkpoint/backup lineage, and retain closure through the entire callback. It supplies matching identity plus `currentRelease` and `priorRelease`, each containing retained exact signed manifest/signature bytes. A read-once boolean or stale snapshot is insufficient. Hold IDs change across bounded continuations; the operation/epoch/job tuple cannot.

Preparation is explicitly bounded and persistent. `prepare(expected)` first verifies both signed releases and reviewed coverage, reads/verifies the actual prior API bytes from the sealed encrypted store, and claims an encrypted `prior` phase. It returns `{outcome:'pending'}` without invoking any protected callback. The next call downloads and verifies active code/configuration, then persists completed evidence and returns `{outcome:'ready'}`. A lost claim/write acknowledgment resumes from the exact encrypted phase; absence never authorizes skipping content proof.

The deployed proof reads the pinned deployment, requires one version at100%, verifies its version identity, downloads bounded Worker content, and verifies bytes against the current signed API artifact. Initial scope permits one module; unsupported multipart shapes fail closed. It compares exact nonsecret configuration and secret name/type inventory, then rereads deployment identity to reject a switch during inspection.

`withWriterFence` rejects incomplete preparation. On EVERY use it re-verifies retained signed release identities/coverage, rereads active deployment/settings/final deployment, and compares them with the exact encrypted completed evidence. It does not redownload the content or reread the full prior artifact. This relies on the provider version identity naming immutable content, sealed-store immutability, and the explicit exclusive-deployment adoption prerequisite. Cloudflare documents version immutability in its [IaC version guidance](https://developers.cloudflare.com/workers/platform/infrastructure-as-code/) and distinguishes version identity from storage state in [Versions and deployments](https://developers.cloudflare.com/workers/versions-and-deployments/) (checked September11,2026). It does not treat an arbitrary artifact digest or sealed flag as content proof: actual content was verified before completed evidence was created. Drift rejects; the old record cannot silently authorize another deployment. Calling `prepare` after completion also performs current readback rather than returning cached readiness.

Evidence binds installation/appDB/epoch/job/operation, current and prior manifest hashes, normalized configuration hash, adoption/coverage hashes, and actual deployment/version IDs. `holdId` is supplied only for the current callback and excluded from immutable evidence. The protected callback runs inside `withAuthority`; errors never invoke it. Provider failures propagate fail-closed errors rather than fabricated successful attestation. A callback acknowledgment lost after application mutation remains the consuming transport's durable reconciliation responsibility.

This is conditional evidence under exclusive writer/deployment ownership, not an atomic transaction spanning Cloudflare configuration and D1. A fresh provider read cannot prevent an external administrator changing configuration immediately afterward. The constructor's retained ownership prerequisite is essential. WU198 must retain the same closed epoch through restore, prior-code activation, fresh health and reopening and establish appropriate evidence at each new operation; it must not reuse restore evidence as proof of a later deployment.

## Bounds and verification

Two preparation calls: the first performs no provider calls; the second performs five read-only provider requests. Each later use performs three read-only deployment/settings requests, with one15-second abort deadline for its provider phase. Metadata limit256KiB; Worker content bound17MiB. Token goes only to constructed api.cloudflare.com URLs; redirects are not followed. An actual16MiB fixture measured15 D1 statement executions for prior-byte preparation (171 chunks read16 per query plus metadata/evidence), two for deployed-proof persistence, and one for later evidence readback. Constructor authority and the consuming restore queries are additional and must be measured by runtime composition. Maximum-size local fixture takes about7 seconds including setup/encryption; this does not establish hosted Worker CPU or wall-time eligibility. Hosted CPU/latency acceptance remains required. No D1/provider quota claim is made from this component alone.

`node --test tests/updater-writer-fence.test.mjs` exercises actual SQLite encrypted storage and synthetic signed releases/provider responses: successful evidence, restart/new hold with fresh requests, drift, missing adoption/coverage/configuration, tampered retained/deployed bytes, redirects, oversize and mismatched authority. No provider calls, real credentials or deployment mutations are used.
