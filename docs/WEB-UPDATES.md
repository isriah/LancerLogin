# Web updates

This is the technical reference for dashboard installation updates. The step-by-step procedure for Administrators is on the documentation site: [Update the dashboard](https://isriah.github.io/LancerLogin/updates.html#web-update). A web update changes the Cloudflare installation (Worker, Pages and D1). It is separate from a physical kiosk update; see [kiosk reference](KIOSK.md#update-a-physical-kiosk). For the LancerLogin 1 carry-over checklist and update order, see [Upgrade Community to Modular](COMMUNITY-UPGRADE.md).

## Credentials and variables

One-click updates from **Settings > Updates** need the optional `LANCERLOGIN_WEB_UPDATE_TOKEN` production environment secret: a fine-grained GitHub token whose resource owner is the deployment repository's owner, limited to **only** the private deployment repository, with **Actions: Read and write** (GitHub adds **Metadata: Read-only**). Provisioning, upgrades and **Refresh web update credential** verify the token against the private repository and upload it to the Worker as `WEB_UPDATE_TOKEN`. LancerLogin reads the token's expiry from GitHub, so no expiry variable is needed. When the token nears expiry, has expired or is revoked, Settings > Updates says so and how to replace it. Without the token, the installation updates by running **Install or upgrade LancerLogin** with operation `upgrade`.

The optional plugin selection credential, `LANCERLOGIN_MODULE_SELECTION_TOKEN`, is a separate Contents-write token for the same repository; see [module plugins](MODULE-PLUGINS.md#module-selection-credential). It is verified and uploaded only when configured, and a value equal to the dispatch credential is refused.

Updates use the production environment variables `LANCERLOGIN_INSTALLATION_SLUG`, the exact `LANCERLOGIN_DATABASE_ID` UUID and the exact `LANCERLOGIN_API_URL` HTTPS Worker origin, recorded from the installation run summary. Cloudflare credentials stay in `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Never put any of these values in chat, command arguments, D1, backups, tracked files or logs. **Refresh web update credential** verifies the exact account, D1 database and Worker binding before uploading the update credentials; it cannot recreate resources or rotate `SESSION_KEY`, `INTEGRATION_KEY` or `BOOTSTRAP_CODE_HASH`.

## Repository workflow files

A deployment repository keeps the workflows and scripts it was created with: web updates deploy a new release but never change the repository. Two things keep that from causing failures:

- **Refresh web update credential runs the installed release's script.** The workflow reads the installed release from the Worker's public `/health` (`releaseVersion`, at the exact `LANCERLOGIN_API_URL` origin), accepts only a canonical version, confirms the tag `v<version>` exists in `isriah/LancerLogin`, checks out that tag's commit without a token and runs its `scripts/refresh-web-update-credential.mjs`. The secrets are still given only to that step. When the release cannot be resolved (for example `LANCERLOGIN_API_URL` is missing or the Worker is unreachable), the run prints an `installed_release_unresolved` warning and uses the repository's own copy. `upgrade-web.yml` already runs the release's `scripts/run-web-upgrade.mjs`; only its `--validate` step, which needs no secrets, runs the repository copy.
- **Update repository files.** **Settings > Updates > Setup status** compares the git blob SHAs of `.github/workflows/provision-template.yml`, `upgrade-web.yml`, `refresh-web-update-credential.yml` and the scripts those workflows run from the repository (`scripts/run-web-upgrade.mjs` and `scripts/refresh-web-update-credential.mjs` with their local imports) on `main` with the installed release's tag. When any differ, **Update repository files** creates the branch `lancerlogin/update-files-<version>` with the release's exact files (each checked against its blob SHA) and opens a pull request. It never merges, and never touches `lancerlogin.modules.json`, `lancerlogin.plugin-sources.json`, other files or secrets. Review and merge the pull request on GitHub.

Update repository files uses `LANCERLOGIN_WEB_UPDATE_TOKEN` and needs these extra repository permissions on it: **Contents**, **Pull requests** and **Workflows**, each **Read and write**. Without them the row says which permission to add; editing the token's permissions keeps its value, so no secret or workflow run is needed afterwards. These permissions let the token change workflows, so you can remove them again after merging. The Setup status panel also shows the latest **Refresh web update credential** run: the failure code from its error annotation, explained in plain words, and a link to the run. Reading annotations needs **Checks: Read-only** on the same token; without it the panel names only the failed step. A run that failed without a code, as scripts older than `v2.0.0-beta.17` do, is reported as likely caused by older repository files.

## Update flow

Only an active Admin can prepare, start, or read status, and mutations require the exact dashboard Origin and JSON. The browser cannot select a repository, workflow, ref, slug or executable parameter. Preparation resolves one complete official release allowed by the installation's [update track](UPDATE-TRACKS.md) and pins it by public commit. Downgrades are refused. Starting requires an entire-installation backup exported for that request and an explicit saved-file confirmation; refreshing never confirms it.

The fixed private `upgrade-web.yml` workflow runs on `main`. It checks out the official source at the pinned commit and executes `scripts/run-web-upgrade.mjs` from that release, so the controller under release verification is the controller that deploys. Provision, upgrade and refresh share the `lancerlogin-production-installation` concurrency group and the `production` environment. If that environment requires reviewers, GitHub waits for approval before each run.

After an update completes, a verified Discord connection checks its managed commands on the next five-minute maintenance pass. Command status is in **Settings > Integrations > Discord**. A Discord command failure does not change the update result.

## Apply module changes

The **Modules** card in **Settings > Modules > Manage modules** commits module changes to `lancerlogin.modules.json` in the private repository (see [module plugins](MODULE-PLUGINS.md#manage-modules-in-settings--modules)) and deploys them with **Apply changes** on the same card, a web update that redeploys the installed release. It uses the same request, backup, saved-file confirmation, single dispatch, GitHub approval, claim, build, maintenance, checkpoint, forward-only migration, deployment and health verification as a release update. The controller reads the request's mode from D1 and accepts a target equal to the installed release only for a `modules` request.

Every request prepared while the plugin selection credential is configured records the git blob SHA of `lancerlogin.modules.json` (forty zeros when the file is absent). Before claim, the controller compares it with the selection it checked out and stops on any difference. Plugin changes are refused while an update is dispatched or running and expire a prepared update.

Before claim the controller also refuses to drop a module that moved into a plugin while the installation still uses it. For this refusal and a changed selection, the controller fails the unclaimed request itself with `module_migration_required:<module IDs>` or `module_selection_preflight`. See [module plugins](MODULE-PLUGINS.md#updating-an-installation-that-uses-a-module-that-moved-into-a-plugin).

## Fixed database identity

An installation rename may keep its original D1 name. Set optional `LANCERLOGIN_DATABASE_NAME` in the private repository or production environment; workflows pass it to controller scripts as `DATABASE_NAME`. If unset, it defaults to `<installation-slug>-data`. Never add database identity as a workflow-dispatch input. Backup, restore, migration and recovery commands use the actual database name. A rename is a separate reviewed procedure; do not run fresh provisioning or a same-version upgrade to perform it.

## Worker placement

Installation and web updates deploy the Worker API with Cloudflare [Smart Placement](https://developers.cloudflare.com/workers/configuration/placement/) (`"placement": { "mode": "smart" }`), so Cloudflare can run it near its D1 database instead of at each visitor's nearest location. To pin it to one cloud region instead, set optional `LANCERLOGIN_WORKER_PLACEMENT_REGION` in the private repository or production environment to a placement hint such as `aws:us-east-1`, `gcp:us-east4` or an `azure:` region. Any other value stops the run before deployment (`worker_placement_region_invalid` in a web update). Remove the variable to return to Smart Placement. Repository workflow files from earlier releases do not pass the variable, so a hint applies to web updates only after **Update repository files**.

## Dashboard API

These Worker routes are called under the dashboard's same-origin `/api` prefix. Responses are JSON with `cache-control: no-store`.

| PUT `/admin/update-channel` | `{ "channel": "stable" or "beta", "revision": <current integer>, "betaConfirmed": true }` | Audited atomic change; Beta acknowledgement required. Does not install. Active updates lock the choice and prepared requests expire on a change. |
| GET `/admin/releases/latest` | None | Complete official selected-track release metadata, last successful `checkedAt`, last provider `attemptedAt`, `fresh`, and optional failure diagnostics / `retryAt`. Discovery does not prepare or dispatch. |
| POST `/admin/web-updates/prepare` | `{}` or `{ "mode": "modules" }` | Active request or new selected-track pinned request; thirty-minute expiry. | POST `/admin/web-updates/repository-files` | `{}` | Opens the pull request with the installed release's workflow files (HTTP 201, audited as `web_update.repository_files_proposed`), or returns the one already open (HTTP 200): `{ pullRequest: { number, url }, created, release, files }`. Refused with `repository_files_current`, or with `repository_files_contents_permission`, `repository_files_pull_requests_permission` or `repository_files_workflows_permission` naming the permission to add. Never merges. |
| POST `/admin/web-updates/setup/recheck` | `{}` | **Check again** on the Repository workflow files and Latest credential refresh rows, also sent when the tab becomes visible again while either row is outdated, failed, running or unknown (at most once a minute per tab). Prepare, start and status return `{ releaseVersion, workflowUrl, request, activeRequest, latestCompletedRequest }`. A request's `mode` is `release` or `modules`. `activeRequest` contains prepared, dispatched, running, verifying or recovery-required work; `latestCompletedRequest` contains succeeded, failed or expired history. A request includes `requestId`, `targetTag`, `targetCommit`, `channel`, plain-text `releaseNotes`, fixed official `releaseUrl`, `previousVersion`, `state`, `stage`, `createdAt`, `expiresAt`, `updatedAt`, `backupExported`, `maintenance`, nullable `errorCode`, nullable `runUrl`, and `reloadReady`. Render notes as text or sanitized Markdown, never trusted HTML. HTTP 202, a successful dispatch and a successful GitHub run are each insufficient evidence of completion.

States: `prepared`, `dispatching`, `queued`, `awaiting_approval`, `running`, `verifying`, `succeeded`, `failed`, `recovery_required`, `expired`. Stages identify build, checkpoint, migrations, API deployment, Pages deployment and health. Environment approval stays in GitHub. Reloads resume through status without browser-local request storage. Failed and expired requests permit a deliberate new prepare; recovery-required keeps the active lock. Started requests impose a two-minute cooldown.

The Dashboard card tracks the Worker release, the release served by Pages, the JavaScript bundle running in the current tab, and the latest discovered selected-track release independently. New updates stay disabled while Worker and Pages disagree. **Reload updated dashboard** appears when Worker and Pages agree on a release newer than the running bundle. Persisted success never causes automatic reload loops.

Errors use `{ error, code }`. Plugin management adds `selection_credential_required`, `selection_credential_expired`, `selection_credential_permission`, `selection_invalid`, `selection_changed`, `source_not_allowed`, `reauthentication_required`, `reauthentication_failed`, `trust_confirmation_required`, `update_active`, `module_in_use` and `module_migration_required`. A request whose controller stopped before claim may carry `module_migration_required:<module IDs>` or `module_selection_preflight` instead of `preflight_failed`; a request expired by a plugin change carries `module_selection_changed`. Other safe codes: `not_configured`, `credential_required`, `credential_expired`, `not_private`, `workflow_required`, `cooldown`, `already_current`, `release_unavailable`, `invalid_request`, `request_missing`, `request_expired`, `backup_required`, `provider_unavailable`, `run_mismatch`, `channel_changed`, `channel_locked`, `beta_confirmation_required`, `controller_upgrade_required`. A definite dispatch credential or cooldown rejection is retained as `request.errorCode`; uncertain outcomes use `dispatch_ambiguous`. Reconciliation matches the exact request run-name and workflow path; multiple or unresolved runs become `dispatch_unresolved` recovery after fifteen minutes. Never blind-redispatch. A completed failure before executor claim is `failed/preflight_failed`; a completed claimed executor without verified finalization requires recovery.

The partial unique installation index and permanent executor claim prevent concurrent dispatch and duplicate-run mutation. Database audit triggers record the authenticated Admin on prepare and start. Reads and sign-in remain available during maintenance; domain mutations, kiosk attendance writes and scheduled provider writes pause. Kiosks receive retryable HTTP 503 with Retry-After and keep their disk queues. Durable scheduler alarms retain due work and resume after maintenance clears.

## Release discovery

Release discovery uses the same-origin API, not direct browser access to GitHub. When the web-update credential is configured and valid, the Worker authenticates its fixed GitHub release requests, sending the credential only to `api.github.com` with redirects disabled; otherwise it uses the public anonymous feed. Successful checks are cached for at most fifteen minutes and concurrent requests within an isolate are coalesced. Failures keep previous metadata unconfirmed and distinguish rate limits, timeouts, network failures, invalid releases and other provider errors, with a relative `Retry-After`. Browser-cached metadata is a display hint only: preparation independently resolves the release and pins its commit.

## Executor

Exact resources and secrets are checked before the durable executor claim. API and dashboard builds precede maintenance. After maintenance and a sixty-second drain, the controller records a D1 Time Travel bookmark, the previous API version, Worker deployment and version IDs and the Pages production deployment ID in the operational `recovery_json`. A checkpoint failure stops before migration. It then applies compatible forward-only migrations, prepares the `FINGERPRINT_VAULT_KEY` if missing, deploys API and Pages, and allows a three-minute propagation window. Success requires API ready and release, Pages' `/__lancerlogin-release`, same-origin proxy health, the canonical Pages commit, the retained D1 binding, `ALLOWED_ORIGIN`, secret names and the registered dashboard domain. Health must report exactly the composed modules and the run's random `DEPLOYMENT_MARKER`, so a previous Worker still propagating cannot pass, and the canonical Pages deployment must differ from the one recorded at the checkpoint. No automatic code rollback or D1 restore occurs.

A run cancelled or timed out before migrations changes nothing: before claim the controller exits; after claim it clears maintenance and fails the request with `<stage>_cancelled`. Once a migration or deployment may have started, it leaves the request for recovery. If the controller cannot record this itself, the Worker fails a claimed request whose run stopped in `preflight`, `building` or `maintenance` with `workflow_stopped_unchanged`.

`scripts/web-upgrade-policy.json` is release-owned compatibility metadata: every migration's LF-normalized SHA-256, explicit forward compatibility, the minimum installed version and disabled automatic code rollback. Applied migrations must be an exact prefix, except the reviewed independent bridge `0061_update_channels.sql`. Unknown or ahead schema, changed hashes, an unsupported installed version or a downgrade fails before claim. Never regenerate hashes to bypass a failed compatibility check.

The `FINGERPRINT_VAULT_KEY` is generated only when it is missing and cloud fingerprint storage is disabled with no stored templates. Existing keys are never rotated by an update or copied into backups, output or files. A missing key while cloud storage is enabled or templates exist is a recovery condition: restore the original key; never generate a replacement. See [privacy](PRIVACY.md#optional-fingerprint-cloud-storage).

## Recovery

On recovery-required, the installation stays in write suspension. Inspect the private run and the operational recovery record securely, record the exact API and Pages releases, IDs, migrations and bookmark, and take a fresh D1 export outside source and logs. An unresolved dispatch without a proved run cannot unlock automatically. Review schema compatibility before any code rollback. Restoring the database requires its own explicit decision and the retained encryption, session and pairing secrets; never automate it.

After a known completed run, when all dashboard origins are healthy on the previous, target or a later release on an allowed track, `scripts/recover-web-update.mjs` can clear maintenance. Provide the fixed resource metadata and provider credentials through the process environment, `RECOVERY_REQUEST_ID`, the exact `RECOVERY_CONFIRMATION=RECOVER WEB UPDATE <UUID>`, and `RECOVERY_SCHEMA_COMPATIBILITY_REVIEWED=yes` after review. It verifies the account, resources, the completed workflow request, Worker, Pages and proxy agreement, the retained origin and the dashboard domain. It performs no restore, rollback, resource creation or credential rotation. Never fabricate a run ID.

Operational rows are excluded from dashboard backups and restores, so an application restore cannot erase an active lock. Full D1 exports and Time Travel retain them; inspect restored control state before resuming service.

## Verification

`npm run rehearse:update` and `npm run rehearse:web-upgrade` exercise updates against synthetic data on a local computer, and `npm run verify:migrations` applies the migrations to synthetic LancerLogin 1 databases. See [development](DEVELOPMENT.md#local-update-rehearsal). These checks do not contact Cloudflare or GitHub and do not replace checking each installation's own result.
