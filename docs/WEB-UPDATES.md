# Web updates

This is the technical reference for dashboard installation updates. The step-by-step procedure for Administrators is on the documentation site: [Update the dashboard](https://isriah.github.io/LancerLogin/updates.html#web-update). A web update changes the Cloudflare installation (Worker, Pages and D1). It is separate from a physical kiosk update; see [kiosk reference](KIOSK.md#update-a-physical-kiosk). For the LancerLogin 1 carry-over checklist and update order, see [Upgrade Community to Modular](COMMUNITY-UPGRADE.md).

## Credentials and variables

One-click updates from **Settings > Updates** need the optional `LANCERLOGIN_WEB_UPDATE_TOKEN` production environment secret: a fine-grained GitHub token whose resource owner is the deployment repository's owner, limited to **only** the private deployment repository, with **Actions: Read and write** (GitHub adds **Metadata: Read-only**). Provisioning, upgrades and **Refresh web update credential** verify the token against the private repository and upload it to the Worker as `WEB_UPDATE_TOKEN`. LancerLogin reads the token's expiry from GitHub, so no expiry variable is needed, and **Settings > Updates > Setup status** shows the expiry date (or "No expiry"). Choose a long expiration, such as one year, so the token is not replaced for every update. GitHub [allows a fine-grained token with no expiration](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens#creating-a-fine-grained-personal-access-token) unless an organization or enterprise policy sets a maximum lifetime, which for organizations defaults to 366 days; LancerLogin accepts either. When the token nears expiry, has expired or is revoked, Settings > Updates says so and how to replace it. The token is optional on both update tracks: without it, the installation updates by running **Install or upgrade LancerLogin** with operation `upgrade` (see [Update without the token](#update-without-the-token)).

The optional module management credential (**Module management credential** on **Settings > Updates**; also called the module selection credential), `LANCERLOGIN_MODULE_SELECTION_TOKEN`, is a separate Contents-write token for the same repository; see [module plugins](MODULE-PLUGINS.md#module-selection-credential). It is verified and uploaded only when configured, and a value equal to the dispatch credential is refused.

One-click updates (`upgrade-web.yml`) and **Refresh web update credential** (`refresh-web-update-credential.yml`) use the production environment variables `LANCERLOGIN_INSTALLATION_SLUG`, the exact `LANCERLOGIN_DATABASE_ID` UUID and the exact `LANCERLOGIN_API_URL` HTTPS Worker origin, recorded from the installation run summary. **Install or upgrade LancerLogin** (`provision-template.yml`) reads none of the three: it takes the slug from its `installation_slug` input and finds the D1 database, Worker and Pages project in the Cloudflare account, so its `upgrade` operation works without them. It reads only the optional variables `LANCERLOGIN_DATABASE_NAME` and `LANCERLOGIN_WORKER_PLACEMENT_REGION`. Cloudflare credentials stay in `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Never put any of these values in chat, command arguments, D1, backups, tracked files or logs. **Refresh web update credential** verifies the exact account, D1 database and Worker binding before uploading the update credentials; it cannot recreate resources or rotate `SESSION_KEY`, `INTEGRATION_KEY` or `BOOTSTRAP_CODE_HASH`.

## Repository workflow files

A deployment repository keeps the workflows and scripts it was created with: web updates deploy a new release but never change the repository. Two things keep that from causing failures:

- **Refresh web update credential runs the installed release's script.** The workflow reads the installed release from the Worker's public `/health` (`releaseVersion`, at the exact `LANCERLOGIN_API_URL` origin), accepts only a canonical version, confirms the tag `v<version>` exists in `isriah/LancerLogin`, checks out that tag's commit without a token and runs its `scripts/refresh-web-update-credential.mjs`. The secrets are still given only to that step. When the release cannot be resolved (for example `LANCERLOGIN_API_URL` is missing or the Worker is unreachable), the run prints an `installed_release_unresolved` warning and uses the repository's own copy. `upgrade-web.yml` already runs the release's `scripts/run-web-upgrade.mjs`; only its `--validate` step, which needs no secrets, runs the repository copy.
- **Update repository files.** **Settings > Updates > Setup status** compares the git blob SHAs of `.github/workflows/provision-template.yml`, `upgrade-web.yml`, `refresh-web-update-credential.yml` and the scripts those workflows run from the repository (`scripts/run-web-upgrade.mjs` and `scripts/refresh-web-update-credential.mjs` with their local imports) on `main` with the installed release's tag. When any differ, **Update repository files** creates the branch `lancerlogin/update-files-<version>` with the release's exact files (each checked against its blob SHA) and opens a pull request. It never merges, and never touches `lancerlogin.modules.json`, `lancerlogin.plugin-sources.json`, other files or secrets. Review and merge the pull request on GitHub.

Update repository files uses `LANCERLOGIN_WEB_UPDATE_TOKEN` and needs these extra repository permissions on it: **Contents**, **Pull requests** and **Workflows**, each **Read and write**. Without them the row says which permission to add; editing the token's permissions keeps its value, so no secret or workflow run is needed afterwards. These permissions let the token change workflows, so you can remove them again after merging. The Setup status panel also shows the latest **Refresh web update credential** run: the failure code from its error annotation, explained in plain words, and a link to the run. Reading annotations needs **Checks: Read-only** on the same token; without it the panel names only the failed step. A run that failed without a code, as scripts older than `v2.0.0-beta.17` do, is reported as likely caused by older repository files.

**Updating a workflow file by hand.** Without the token, or to take a workflow from a release newer than the installed one:

1. In the [LancerLogin releases](https://github.com/isriah/LancerLogin/releases), open the release's tag and copy the raw contents of `.github/workflows/provision-template.yml` (or another file listed above).
2. In the private repository, open the same file on `main`, choose **Edit this file**, replace its contents with the copy and commit directly to `main`.
3. Open **Actions** and check the workflow's **Run workflow** form.

`provision-template.yml` runs no script from the private repository, so copying that one file is enough to get a newer installation workflow.

## Update without the token

**Install or upgrade LancerLogin** (`provision-template.yml`) with operation `upgrade` updates an installation without `LANCERLOGIN_WEB_UPDATE_TOKEN`. Take an entire-installation backup from **Settings > Data** first; this path does not record one. The `release` input chooses what is installed:

| `release` | Installs | Allowed when |
| --- | --- | --- |
| `latest stable` | GitHub Latest: the newest published stable release with a canonical `vX.Y.Z` tag. | Any operation, either track. |
| `latest beta` | What the Beta track offers: the highest version among complete official releases, beta or stable, so a stable release is installed when it is newer than every beta. A beta must be a published, immutable GitHub prerelease with a canonical `vX.Y.Z-beta.N` tag and every kiosk asset, the same rule the dashboard updater applies. A release list that cannot be read completely stops the run with `release_invalid`. | Operation `upgrade` only (`beta_requires_upgrade` otherwise), and only when the installation is on the Beta track (`beta_track_required` otherwise). |

- **An unusable token never blocks it.** `LANCERLOGIN_WEB_UPDATE_TOKEN` and `LANCERLOGIN_MODULE_SELECTION_TOKEN` are checked before any cloud change. When one is set but GitHub rejects it (expired or revoked), it cannot read the repository, the selected release does not accept it, or GitHub cannot be reached, operations `resume` and `upgrade` print a warning with the code (`dispatch_credential_rejected`, `dispatch_credential_access_denied`, `dispatch_credential_check_unavailable`, `dispatch_credential_check_failed`, `token_expiration_unreadable`, `reviewed_workflow_required`, or a `selection_credential_*` code) and continue as if that token were not set. Nothing is uploaded for a skipped token, so the Worker keeps the credential it already has and **Settings > Updates > Setup status** reports that one as **Expired** or **Rejected by GitHub**; a new installation shows **Not set up**. An unusable plugin token is skipped by itself, and the dashboard update token is still installed. Replace the token and run **Refresh web update credential** to turn one-click updates back on, or delete the secret to stop the warning. Operation `create` stops instead, before anything is created, so a mistyped token is noticed at once; its error says the token is optional and the secret can be deleted. A repository that is not private, or a missing installation slug, still stops every operation. This rule, like `latest beta`, lives in the deployment repository's own copy of `provision-template.yml` and was added in v2.1.0-beta.10: an older copy stops every operation at an expired or revoked token (`dispatch_credential_rejected`) until the secret is deleted or the file is replaced [by hand](#repository-workflow-files). **Update repository files** cannot replace it while the token is expired, because it uses that token.
- **Track.** The workflow reads the track from the installation's D1 database (`installation_update_settings`), where **Settings > Updates > Update track** stores it. An installation whose release predates update tracks has no such table and counts as Stable. Choose Beta in the dashboard before running `latest beta`; the workflow never changes the track.
- **No downgrade.** Before any change, the workflow reads the installed release from the Worker's public `/health` (`releaseVersion`) at `https://<slug>-api.<account subdomain>.workers.dev` and compares it with the selected release. An older selection stops with `release_downgrade_refused`, for example `latest stable` while a newer beta is installed. The same release is deployed again with a `release_already_installed` notice, which is how a change to `lancerlogin.modules.json`, a Worker placement change or a refused Pages binding is applied without the token. When `/health` does not answer with a release, the workflow reads the Worker's plain-text `RELEASE_VERSION` variable from its Cloudflare settings instead, which works while the Worker is down. If neither gives a release, `latest beta` stops with `installed_release_unreadable`, while `latest stable` only warns under the same code and continues, because `upgrade` with `latest stable` is also the recovery route for a Worker that cannot answer.
- **Getting the `latest beta` choice.** The choice was added in v2.1.0-beta.10, and a deployment repository keeps the workflow it was created with. Replace `provision-template.yml` by hand as described above, or use **Update repository files** once the installation runs v2.1.0-beta.10 or later (it proposes the installed release's files and needs the token).

The run summary names the release installed and whether it is a beta or a stable release. Everything else is the same for both choices: the module-migration check, builds, forward-only D1 migrations, the Worker deployment, the Pages API binding and the Pages deployment. Unlike a dashboard update, this path does not put the installation into maintenance or record a recovery checkpoint. Its last step checks the deployment: it polls the Worker's public `/health` at `https://<slug>-api.<account subdomain>.workers.dev` and the dashboard's `https://<slug>-dashboard.pages.dev/api/health` every five seconds, for up to two minutes, until both report the release just installed in the mode `ready`, and adds **Health check passed** to the run summary. Every release reports `ready` whenever its D1 database is bound, also before the first Admin exists and during maintenance, so the same rule applies to `create`, `resume` and `upgrade`. Otherwise the run fails with `installation_health_no_answer`, `installation_health_release_mismatch` or `installation_health_not_ready`, naming the address and what it reported; the deploy steps themselves have completed by then. This check was added to `provision-template.yml` in v2.1.0-beta.11 and, like `latest beta`, runs only once the deployment repository's own copy of the workflow is updated.

## Update flow

Only an active Admin can prepare, start, or read status, and mutations require the exact dashboard Origin and JSON. The browser cannot select a repository, workflow, ref, slug or executable parameter. Preparation resolves one complete official release allowed by the installation's [update track](UPDATE-TRACKS.md) and pins it by public commit. Downgrades are refused. Starting requires an entire-installation backup exported for that request and an explicit saved-file confirmation; refreshing never confirms it.

The fixed private `upgrade-web.yml` workflow runs on `main`. It checks out the official source at the pinned commit and executes `scripts/run-web-upgrade.mjs` from that release, so the controller under release verification is the controller that deploys. Before anything else, it reads the official release and its commit from GitHub. Those two read-only checks are retried a few times within about 30 seconds when GitHub is briefly unavailable (a network error, timeout, rate limit or server error), honouring GitHub's Retry-After within that time; if GitHub still does not answer, the run stops with `provider_request_failed` and nothing changes.

Re-running a workflow run in GitHub never retries an update. Once a request has ended (failed, expired, succeeded or needing recovery), the controller cannot claim it, deploys nothing, explains why in the run log and fails with `request_not_claimable`. To try again, select **Apply changes**, or start the update again, in the dashboard: that prepares a new request. A re-run of a run that already claimed its request and finished it, or a run whose request another run is still handling, deploys nothing and stays green.

Provision, upgrade and refresh share the `lancerlogin-production-installation` concurrency group and the `production` environment. If that environment requires reviewers, GitHub waits for approval before each run.

After an update completes, a verified Discord connection checks its managed commands on the next five-minute maintenance pass. Command status is in **Settings > Integrations > Discord**. A Discord command failure does not change the update result.

## Updating from 2.0 to 2.1

The adopter steps are on the documentation site: [Updating from LancerLogin 2.0 to 2.1](https://isriah.github.io/LancerLogin/updates.html#from-2-0). What the update does, for reference:

- **Passwords.** Each local account's first sign-in converts its stored hash to the browser-derived form (see [security](SECURITY.md#access-and-sessions)). A dashboard tab loaded before the update sends the old request shape and gets `409 reload_required` ("This page is out of date. Reload the page and try again."), or "Invalid username or password" on the sign-in page, until it is reloaded.
- **Early arrival allowance.** Migration `0099_early_scan_minutes.sql` adds the allowance at 15 minutes for existing installations too. Setting it to 0 in **Settings > Modules > Attendance > Meeting configuration** restores the earlier behavior of refusing scans before a meeting starts. Meetings saved earlier may now overlap by that allowance; a scan in both windows goes to the earlier meeting.
- **Scan reviews and simulator.** Open rejected-scan reviews are dismissed, and migration `0092_remove_simulator.sql` drops the browser simulator and its saved data.
- **Discord.** Absence-notice cleanup needs the bot's **Manage Threads** permission in the attendance channel; without it, deleting a notice's thread keeps being retried.
- **Kiosks.** Pi kiosks keep working on their installed release. The new refusal notices, rescan prompts, member search, PINs and Discord codes need a kiosk update afterwards. **Require PIN** can be turned on for a Pi kiosk only after it reports release 2.1.0-beta.3 or later, so update Pi kiosks first; web kiosks are never blocked.
- **Pages API binding.** The controller adds the Pages project's `API` service binding before it deploys Pages. If Cloudflare refuses it (usually a token without Cloudflare Pages: Edit), the run logs the warning "Pages API binding not added" and still succeeds; sign-in limits then stay shared between visitors. Preparing the same release again is refused with `already_current`, so the binding is added by the next deployment that runs the controller: the next release update, or **Apply changes** for a pending module change. The installation workflow treats a refused binding the same way: it warns in the run log and the job summary and still deploys the dashboard. Running it again with the operation `resume` and the same slug adds the binding once the token is fixed.

## Apply module changes

**Settings > Modules > Manage modules** commits module changes to `lancerlogin.modules.json` in the private repository (see [module plugins](MODULE-PLUGINS.md#manage-modules-in-settings--modules)) and deploys them with **Apply changes** on the same page, a web update that redeploys the installed release. It uses the same request, backup, saved-file confirmation, single dispatch, GitHub approval, claim, build, maintenance, checkpoint, forward-only migration, deployment and health verification as a release update. The controller reads the request's mode from D1 and accepts a target equal to the installed release only for a `modules` request.

Every request prepared while the module management credential is configured records the git blob SHA of `lancerlogin.modules.json` (forty zeros when the file is absent). Before claim, the controller compares it with the selection it checked out and stops on any difference. Plugin changes are refused while an update is dispatched or running and expire a prepared update.

Before claim the controller also refuses to drop a module that moved into a plugin while the installation still uses it. For this refusal and a changed selection, the controller fails the unclaimed request itself with `module_migration_required:<module IDs>` or `module_selection_preflight`. See [module plugins](MODULE-PLUGINS.md#updating-an-installation-that-uses-a-module-that-moved-into-a-plugin).

## Fixed database identity

An installation rename may keep its original D1 name. Set optional `LANCERLOGIN_DATABASE_NAME` in the private repository or production environment; workflows pass it to controller scripts as `DATABASE_NAME`. If unset, it defaults to `<installation-slug>-data`. Never add database identity as a workflow-dispatch input. Backup, restore, migration and recovery commands use the actual database name. A rename is a separate reviewed procedure; do not run fresh provisioning or a same-version upgrade to perform it.

## Worker placement

Installation and web updates deploy the Worker API with Cloudflare [Smart Placement](https://developers.cloudflare.com/workers/configuration/placement/) (`"placement": { "mode": "smart" }`), so Cloudflare can run it near its D1 database instead of at each visitor's nearest location. To pin it to one cloud region instead, set optional `LANCERLOGIN_WORKER_PLACEMENT_REGION` in the private repository or production environment to a placement hint such as `aws:us-east-1`, `gcp:us-east4` or an `azure:` region. Any other value stops the run before deployment (`worker_placement_region_invalid` in a web update). Remove the variable to return to Smart Placement. Repository workflow files from earlier releases do not pass the variable, so a hint applies to web updates only after **Update repository files**.

Prepare, start and status return `{ releaseVersion, workflowUrl, request, activeRequest, latestCompletedRequest }`. A request's `mode` is `release` or `modules`. `activeRequest` contains prepared, dispatched, running, verifying or recovery-required work; `latestCompletedRequest` contains succeeded, failed or expired history. A request includes `requestId`, `targetTag`, `targetCommit`, `channel`, plain-text `releaseNotes`, fixed official `releaseUrl`, `previousVersion`, `state`, `stage`, `createdAt`, `expiresAt`, `updatedAt`, `backupExported`, `maintenance`, nullable `errorCode`, nullable `runUrl`, and `reloadReady`. Render notes as text or sanitized Markdown, never trusted HTML. HTTP 202, a successful dispatch and a successful GitHub run are each insufficient evidence of completion.

States: `prepared`, `dispatching`, `queued`, `awaiting_approval`, `running`, `verifying`, `succeeded`, `failed`, `recovery_required`, `expired`. Stages identify build, checkpoint, migrations, API deployment, Pages deployment and health. Environment approval stays in GitHub. Reloads resume through status without browser-local request storage. Failed and expired requests permit a deliberate new prepare; recovery-required keeps the active lock. Started requests impose a two-minute cooldown.

The Dashboard card tracks the Worker release, the release served by Pages, the JavaScript bundle running in the current tab, and the latest discovered selected-track release independently. New updates stay disabled while Worker and Pages disagree. **Reload updated dashboard** appears when Worker and Pages agree on a release newer than the running bundle. Persisted success never causes automatic reload loops.

Errors use `{ error, code }`. Plugin management adds `selection_credential_required`, `selection_credential_expired`, `selection_credential_permission`, `selection_invalid`, `selection_changed`, `source_not_allowed`, `reauthentication_required`, `reauthentication_failed`, `trust_confirmation_required`, `update_active`, `module_in_use` and `module_migration_required`. A request whose controller stopped before claim may carry `module_migration_required:<module IDs>` or `module_selection_preflight` instead of `preflight_failed`; a request expired by a plugin change carries `module_selection_changed`. Other safe codes: `not_configured`, `credential_required`, `credential_expired`, `not_private`, `workflow_required`, `cooldown`, `already_current`, `release_unavailable`, `invalid_request`, `request_missing`, `request_expired`, `backup_required`, `provider_unavailable`, `run_mismatch`, `channel_changed`, `channel_locked`, `beta_confirmation_required`, `controller_upgrade_required`. A definite dispatch credential or cooldown rejection is retained as `request.errorCode`; uncertain outcomes use `dispatch_ambiguous`. Reconciliation matches the exact request run-name and workflow path; multiple or unresolved runs become `dispatch_unresolved` recovery after fifteen minutes. Never blind-redispatch. A completed failure before executor claim is `failed/preflight_failed`; a completed claimed executor without verified finalization requires recovery.

The partial unique installation index and permanent executor claim prevent concurrent dispatch and duplicate-run mutation. Database audit triggers record the authenticated Admin on prepare and start. Reads and sign-in remain available during maintenance; domain mutations, kiosk attendance writes and scheduled provider writes pause. Kiosks receive retryable HTTP 503 with Retry-After and keep their disk queues. Durable scheduler alarms retain due work and resume after maintenance clears.

## Release discovery

Release discovery uses the same-origin API, not direct browser access to GitHub. When the web-update credential is configured and valid, the Worker authenticates its fixed GitHub release requests, sending the credential only to `api.github.com` with redirects disabled; otherwise it uses the public anonymous feed. Successful checks are cached for at most fifteen minutes and concurrent requests within an isolate are coalesced. **Check for updates** in **Settings > Updates** asks the Worker to skip that cache: with a usable web-update credential it reads GitHub again, at most once a minute per Worker isolate and never before GitHub's own `Retry-After` or rate-limit reset, and it also skips the local failure backoff. Without a usable credential it behaves like an automatic check. Automatic checks, the header indicator and page loads never skip the cache. "Last successful check" shows when GitHub was actually read. Failures keep previous metadata unconfirmed and distinguish rate limits, timeouts, network failures, invalid releases and other provider errors, with a relative `Retry-After`. Browser-cached metadata is a display hint only: preparation independently resolves the release and pins its commit.

## Executor

Exact resources and secrets are checked before the durable executor claim. API and dashboard builds precede maintenance. After maintenance and a sixty-second drain, the controller records a D1 Time Travel bookmark, the previous API version, Worker deployment and version IDs and the Pages production deployment ID in the operational `recovery_json`. A checkpoint failure stops before migration. It then applies compatible forward-only migrations, prepares the `FINGERPRINT_VAULT_KEY` if missing, deploys the API, adds the Pages project's `API` service binding to the Worker, deploys Pages, and allows a three-minute propagation window. A refused binding only logs a warning, because the proxy can fall back to a fetch; per-client sign-in limits then stay shared until a later update adds it. Success requires API ready and release, Pages' `/__lancerlogin-release`, same-origin proxy health, the canonical Pages commit, the retained D1 binding, `ALLOWED_ORIGIN`, secret names and the registered dashboard domain. Health must report exactly the composed modules and the run's random `DEPLOYMENT_MARKER`, so a previous Worker still propagating cannot pass, and the canonical Pages deployment must differ from the one recorded at the checkpoint. No automatic code rollback or D1 restore occurs.

A run cancelled or timed out before migrations changes nothing: before claim the controller exits; after claim it clears maintenance and fails the request with `<stage>_cancelled`. Once a migration or deployment may have started, it leaves the request for recovery. If the controller cannot record this itself, the Worker fails a claimed request whose run stopped in `preflight`, `building` or `maintenance` with `workflow_stopped_unchanged`.

`scripts/web-upgrade-policy.json` is release-owned compatibility metadata: every migration's LF-normalized SHA-256, explicit forward compatibility, the minimum installed version and disabled automatic code rollback. Applied migrations must be an exact prefix, except the reviewed independent bridge `0061_update_channels.sql`. Unknown or ahead schema, changed hashes, an unsupported installed version or a downgrade fails before claim. Never regenerate hashes to bypass a failed compatibility check.

The `FINGERPRINT_VAULT_KEY` is generated only when it is missing and cloud fingerprint storage is disabled with no stored templates. Existing keys are never rotated by an update or copied into backups, output or files. A missing key while cloud storage is enabled or templates exist is a recovery condition: restore the original key; never generate a replacement. See [privacy](PRIVACY.md#optional-fingerprint-cloud-storage).

## Recovery

On recovery-required, the installation stays in write suspension. Inspect the private run and the operational recovery record securely, record the exact API and Pages releases, IDs, migrations and bookmark, and take a fresh D1 export outside source and logs. An unresolved dispatch without a proved run cannot unlock automatically. Review schema compatibility before any code rollback, and check first that Cloudflare allows it (below). Restoring the database requires its own explicit decision and the retained encryption, session and pairing secrets; never automate it.

**The Worker cannot be rolled back from 2.1 to 2.0.** The first 2.1 deployment of the API Worker applies a Durable Object migration, which creates the `PlatformScheduler` class behind the scheduler. Cloudflare blocks a rollback to any Worker version from before a Durable Object migration (see [Cloudflare's rollback limits](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollbacks/)), so once an update from 2.0.1 has deployed the 2.1 Worker, the 2.0.1 version recorded at the checkpoint is no longer a rollback target, in the Cloudflare dashboard or with Wrangler. The update's database migrations are also forward-only. Recover forward instead:

- **Finish on the target release or a later one.** Fix what the run reports, then deploy the target release, or a later one. The installation workflow's `upgrade` operation with the same slug does this when the release it offers is the target or later. Once the deployment is healthy, clear maintenance as described below.
- **Restore data only when data is the problem.** Follow [backup and restore](BACKUP-RESTORE.md). A supported backup taken before the update restores into the newer release, so it does not need the older code.

Rollback between Worker versions that are both on 2.1 or later stays subject to the same Cloudflare limits and to the schema review above. If the 2.1 Worker was never deployed (the run stopped before the API deployment), the installation is still running the 2.0.1 Worker and no rollback is needed.

After a known completed run, when all dashboard origins are healthy on the previous, target or a later release on an allowed track, `scripts/recover-web-update.mjs` can clear maintenance. Provide the fixed resource metadata and provider credentials through the process environment, `RECOVERY_REQUEST_ID`, the exact `RECOVERY_CONFIRMATION=RECOVER WEB UPDATE <UUID>`, and `RECOVERY_SCHEMA_COMPATIBILITY_REVIEWED=yes` after review. It verifies the account, resources, the completed workflow request, Worker, Pages and proxy agreement, the retained origin and the dashboard domain. It performs no restore, rollback, resource creation or credential rotation. Never fabricate a run ID.

Operational rows are excluded from dashboard backups and restores, so an application restore cannot erase an active lock. Full D1 exports and Time Travel retain them; inspect restored control state before resuming service.

## Verification

`npm run rehearse:update` and `npm run rehearse:web-upgrade` exercise updates against synthetic data on a local computer, and `npm run verify:migrations` applies the migrations to synthetic LancerLogin 1 databases.
