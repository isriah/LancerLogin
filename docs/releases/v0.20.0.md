# LancerLogin v0.20.0 - Attendance insights, Discord operations, and setup guidance

## Included work units

- WU-061, WU-062, WU-063, WU-064, WU-065, WU-066, WU-067, WU-068, WU-069, WU-070, WU-071, WU-072, and WU-073

## Changed

- Google OAuth setup now follows the current Google Auth Platform flow, keeps the installation-specific callback visible, and links first-time and returning Admins to one illustrated public guide.
- The public documentation now uses LancerLogin's fixed red-and-gold identity with complete light and dark palettes, clearer task-focused pages, accessible controls, and responsive screenshots and tables.
- Dashboard meeting selection now matches the shared form-control language, while operational pages use wide desktop displays more effectively without making text-heavy content difficult to read.
- A missing tracked Discord kiosk-status message is recreated safely in the configured attendance channel, and its replacement becomes the only tracked status message.
- Admins can enable a Discord attendance-channel manager that maintains one pinned kiosk-status message, one guidance message, controlled absence notices, and the configured contest window without changing unrelated channel content.
- Discord contest review now shows the member's lifetime contest count and whether the disputed meeting has a partial, missing, or completed raw scan. Meeting attendance rows also show the authoritative check-in and check-out times.
- Admins can set independent late-arrival and early-departure thresholds, both defaulting to 10 minutes. Member detail reports the mean qualifying anomaly across that member's complete preserved history from their participation start date.
- Admins can direct one post-meeting anomaly report to a separate private Discord channel. Delivery starts only after configuration, waits until the meeting's late-scan window closes, sends nothing for an empty meeting, and records one retry-safe result per meeting.
- Admins can create, order, edit, retire, and restore reusable meeting-weight categories. Meeting creation uses the first matching duration rule unless an authorized creator chooses another category or the default 1x value.
- Each meeting keeps a snapshot of its selected category name and weight. Reports, private Discord attendance reports, and attendance CSV exports use those saved weights without allowing later category edits to rewrite history.
- A linked Discord member can request their own private attendance report through the slash command or the single button on the managed guidance message. Responses remain ephemeral, provider-bounded, and bound to the configured server, channel, message, and member.

## Required live Discord release check

Before publishing the release tag, run steps 5-8 under **Manual verification after upgrade** on a supported Discord server. Confirm the managed messages, deleted-status recovery, private attendance-report button, and private anomaly delivery all behave as described.

## Upgrade impact

- Four D1 migrations run in order: `0022_discord_channel_manager.sql`, `0023_attendance_anomaly_thresholds.sql`, `0024_discord_anomaly_reports.sql`, and `0025_meeting_weights.sql`.
- Existing meetings receive a saved attendance weight of 1, so their attendance results do not change during migration.
- Existing organizations receive separate 10-minute late-arrival and early-departure thresholds. These thresholds describe anomalies only; they do not change attendance outcomes or the late-scan allowance.
- Discord attendance-channel management and private anomaly reports remain off until an Admin explicitly configures them. The anomaly-report channel must be a private text channel in the verified server and cannot be the member-facing attendance channel.
- No new environment secrets, dependency changes, Pi service changes, or kiosk installation are required.

## Before upgrading

1. Download an **Entire installation** backup from **Settings -> Updates**.
2. Confirm the Discord bot has the permissions needed for the enabled features, including **View Channel**, **Send Messages**, **Read Message History**, and **Pin Messages** in the attendance channel.
3. Restrict the separate anomaly-report channel to authorized attendance staff before enabling reports.
4. Run the guarded private-repository upgrade workflow using **Latest stable** and the required confirmation.
5. A physical kiosk update is not required for this release.

## Manual verification after upgrade

1. Open the updated Google OAuth guide and confirm the displayed callback matches the adopter's Pages URL before changing any Google configuration.
2. At desktop and phone widths, check Dashboard, a meeting, Reports, member detail, Organization settings, Integrations, and the public documentation in light and dark modes.
3. Add two meeting-weight categories with matching duration rules, reorder them, and create a meeting. Confirm the first matching rule is shown, a manual choice remains available, and later category edits do not change the meeting's saved weight.
4. Confirm Reports and the attendance CSV use saved meeting weights, while member anomaly history remains independent of the current Reports date range.
5. In a supported Discord server, enable the attendance-channel manager and confirm exactly one current status message is pinned, exactly one guidance message contains the attendance-report button, and unrelated messages remain unchanged.
6. Delete the tracked status message, run the authorized kiosk-status refresh, and confirm exactly one replacement is created and reused by the next unchanged refresh.
7. Click the attendance-report button as a linked member and confirm the response is private and contains only that member's weighted attendance. Confirm an unlinked member receives a private non-disclosing error.
8. Configure the separate private anomaly channel, complete a meeting with a qualifying late arrival or early departure, and confirm one no-mention report arrives only after the late-scan window closes. Confirm a meeting without qualifying anomalies creates no message.

## Known limits

- Automated verification uses local D1 and provider fakes. The managed Discord messages, button interaction, Pin Messages permission, status-message recovery, and private anomaly delivery must pass the supported-server checks above before the release tag is published.
- Google Calendar meeting sync is deliberately excluded. LancerLogin remains authoritative, and WU-074 begins only after v0.20.0 is published.
- This release does not deploy or upgrade any private adopter installation and does not update a Raspberry Pi.
- The repository's configured visual browser is Chromium; Firefox and WebKit were not run separately.
