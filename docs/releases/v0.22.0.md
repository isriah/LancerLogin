# LancerLogin v0.22.0 - Reliable updates and calendar delivery

## Included work units

- WU-075, WU-076, WU-077, WU-078, and WU-079

## Changed

- Dashboard kiosk updates now resolve to a stable installed-version result or an actionable terminal failure after the kiosk restarts. Offline, stale, unchanged, mismatched, and explicit installer-failure outcomes remain distinct.
- Dashboard Table view lists meetings from oldest to newest with stable ordering for equal start times. Search, row selection, bulk actions, and meeting navigation keep their existing behavior.
- Routine successful Dashboard loads no longer leave an empty status card, and meeting detail no longer repeats the attendance-closing timestamp. Loading, mutation, and error feedback remain accessible.
- Enabled and verified Google Calendar and Discord integrations now receive the same meeting create, supported edit, hide, restore, retry, and manual recovery requests. Meeting detail can sync one meeting to every configured calendar, and each provider has its own bounded **Sync all meetings** action.
- Discord scheduled-event delivery uses durable operation leases and opaque generation-specific correlation so ambiguous responses and concurrent retries reconcile without creating duplicate events.
- Discord verification now creates or reconciles exactly the guild-scoped `/pair` and `/attendance-report` commands. Reverification and credential rotation reuse those schemas without manual command payloads or duplicate commands.

## Required live release checks

Before publishing the release tag:

1. On a supported Google Calendar account and Discord server, create a test meeting with both calendars enabled and verified. Confirm one event appears in each provider, supported time edits update the same events, hiding removes only the tracked events, and restoring creates one new generation per provider.
2. Exercise the meeting-level multi-provider sync and each provider-specific **Sync all meetings** action. Temporarily make one provider unavailable, confirm the LancerLogin meeting change still saves and the other provider can succeed, then recover and retry without duplicate events.
3. Run Discord verification and confirm the configured guild contains exactly `/pair` and `/attendance-report` with the documented schemas. Repeat verification and rotate credentials; confirm the same two guild commands are reconciled without duplicates. Confirm invalid credentials or missing access leave the integration in **Verification required** with safe retry guidance.

The immutable v0.22.0 kiosk package must also receive supported-Pi validation after publication: queue **Update to latest stable**, confirm the systemd updater restarts into v0.22.0, and confirm Dashboard settles on the installed-version success state. Exercise one controlled installer failure and confirm its terminal guidance remains stable.

## Upgrade impact

- D1 migration `0027_kiosk_update_outcomes.sql` adds requested, previous, resolved, and terminal outcome fields to kiosk update commands.
- D1 migration `0028_discord_calendar_delivery.sql` adds Discord meeting-event mappings and durable delivery operations, including correlation and processing-lease state.
- Existing provider credentials remain encrypted. Discord command registration and calendar delivery remain unavailable until the integration is enabled and successfully verified.
- Discord calendar sync needs **Manage Events** in the configured server. Existing attendance-channel and optional channel-manager features retain their documented channel access and **Pin Messages** requirements.
- Google Calendar authorization remains separate from Google sign-in and retains its narrow calendar-list read and calendar-event write access.
- No dependency or new environment-secret changes are included. The private Dashboard installation and physical kiosk must both be upgraded to receive the complete release.

## Before upgrading

1. Download an **Entire installation** backup from **Settings -> Updates**.
2. Confirm the Discord bot is installed in the intended server, can access the configured attendance channel, and has **Manage Events** if Discord calendar delivery will be enabled.
3. Confirm the Google Calendar OAuth client still contains the exact callback displayed by the installation.
4. Run the guarded private-repository upgrade workflow using **Latest stable** and the required confirmation.
5. After the Dashboard upgrade, update the physical kiosk to **Latest stable** from **Kiosks** or **Settings -> Updates**. If the fixed updater is not yet installed on that Pi, use the version-matched guided installer once.

## Manual verification after upgrade

1. Open Dashboard Table view and confirm rows progress from older meetings toward future meetings while search, selection, bulk actions, keyboard navigation, and row opening remain independent.
2. Open meeting detail and confirm the summary omits **Attendance closes** without changing actual scan eligibility. Refresh Dashboard and confirm routine success does not leave an empty status card, while loading and failures remain visible.
3. Repeat the supported Google Calendar and Discord lifecycle checks above, including partial-provider failure and retry recovery.
4. Confirm Discord verification manages exactly the two guild commands, and invoke `/pair` and `/attendance-report` to verify their existing signed, private, linked-member behavior is unchanged.
5. Update the supported Pi and confirm the final installed release or terminal failure appears correctly after restart and remains stable across refreshes.

## Known limits

- Calendar sync is one-way. Provider-side changes never modify LancerLogin, and enabling a calendar does not backfill existing meetings without an explicit sync action.
- Google Calendar continues to receive only the fixed generic event name, opaque identity, and start/end times. Discord receives only its documented provider-specific event fields.
- Removing an integration clears local authorization and mappings but does not claim to remove provider events whose delivery cannot be verified.
- Automated verification uses local D1, provider fakes, and mocked kiosk execution. It sends no live provider traffic and cannot prove physical systemd, network, or sensor behavior.
- This community release publishes source and immutable artifacts only. It does not deploy or upgrade a private adopter installation or update a Raspberry Pi.
- The configured visual browser is Chromium; Firefox and WebKit are not run separately.
