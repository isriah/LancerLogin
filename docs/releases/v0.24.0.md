# LancerLogin v0.24.0 - Safe upgrades and in-app web updates

## Changed behavior

Admins can prepare a pinned official Dashboard release, read its notes, download the associated Entire installation backup, confirm the file was saved, then start and track the fixed private GitHub Actions upgrade inside Settings → Updates. Progress survives reloads and other tabs. Required environment approval remains explicit through the displayed GitHub link. Reload is offered only after API and Pages independently report the target release and healthy operation. Credential, cooldown, uncertain dispatch and recovery states retain diagnostics and manual recovery guidance.

The Physical kiosk card updates the Pi separately. Its fixed privileged helper accepts strict stable semantic versions across major versions, rejects malformed/draft/prerelease/incomplete releases and accepts no caller-selected arguments. The installer verifies actual root-owned helper replacement. Bridge both the web installation and Pi to v0.24.0 before V1.0.0 becomes latest. Older helpers that missed the bridge need the checksum-verified exact-v0.24.0 procedure in [the kiosk guide](../KIOSK.md).

Clean public history begins with this release. Earlier development releases/assets remain private; their old public links are retired. Existing public forks retain their history.

Guided setup offers meeting creation when no meeting is available. Create a meeting whose attendance window includes the current time, submit simulator arrival and departure scans, then verify attendance before completing setup. Creating a meeting alone does not complete the input or attendance checks.

## Migration and configuration impact

- Migration `0029_web_updates.sql` adds operational update requests, concurrency guards and audit records. These records survive application data restore/delete. Reviewed forward migrations preserve attendance and roster data; D1 is never automatically restored.
- Existing private deployment repositories need a reviewed controller/workflow helper patch before the initial bridge. An application upgrade does not update that private checkout. Preserve compatible package manifests, lockfile, installation configuration and history.
- Configure exact retained installation slug, D1 UUID and Worker URL as production variables. Store a separate repository-only fine-grained Actions-write token through secure provider interfaces, with ISO UTC expiry (ninety days by default where policy permits). The Worker holds the dispatch credential; browser state, D1 backups and logs do not contain it.
- The controller builds before maintenance, captures recovery metadata, verifies retained resources/secrets, applies reviewed compatible migrations, deploys API then Pages and verifies both. Maintenance suspends domain writes and returns retryable kiosk errors so scans remain queued. Authentication and reads stay available. No automatic code rollback or D1 restore occurs.
- Dependency versions are unchanged.

Read [web update and recovery guidance](../WEB-UPDATES.md), [installation setup](../BOOTSTRAPPING.md), and [backup and restore](../BACKUP-RESTORE.md).

## Manual acceptance and known limits

Publication does not upgrade any installation or Pi. Measure installed web and Pi versions independently. Rehearse with synthetic data in an isolated installation before live deployment. Exact fixed-workflow release dispatch requires published official targets; local mocks and prepublication checks do not prove installed acceptance.

After authorized bridging, verify retained URLs, D1 identity, secret names, sign-in, roster/attendance and pairing; matching API/Pages release and health; actual installed helper equality and root:root:755 mode; normal/offline scans, pending-queue restart/replay, enrollment, reader, service restart and full reboot. Preserve secure backups and checkpoints. Stop on recovery-required; use reviewed, explicitly authorized recovery only after a known completed run and matching healthy releases. Never automatically restore D1 or discard pending scans.
