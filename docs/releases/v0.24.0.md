# LancerLogin v0.24.0 - Safe upgrades and in-app web updates

> Historical release note. This bridge was part of the completed 1.0.2 migration. Do not use it as a new-installation procedure. Read the [current web-update guide](../WEB-UPDATES.md) and the [1.0.2 release note](v1.0.2.md) for current context.

## Changed behavior

Admins can prepare a pinned official Dashboard release, read its notes, download the associated Entire installation backup, confirm the file was saved, then start and track the fixed private GitHub Actions upgrade inside Settings → Updates. Progress survives reloads and other tabs. Required GitHub environment approval remains explicit. Reload is offered only after API and Pages independently report the target release and healthy operation. Credential, cooldown, uncertain dispatch and recovery states retain useful diagnostics.

The Physical kiosk card remains separate. The fixed privileged helper accepts strict stable semantic versions across major versions, rejects malformed/draft/prerelease/incomplete releases and accepts no caller-selected arguments. The installer verifies the actual root-owned helper replacement. Bridge both the web installation and Pi to v0.24.0 before V1.0.0 becomes latest. Older helpers that missed the bridge need the checksum-verified exact-v0.24.0 bootstrap in KIOSK.md.

Clean public history begins with this release. Earlier development releases/assets remain in private development history; their old public links are retired. Public source has independent history, account-neutral configuration and explicit reviewed documentation adaptations.

Guided setup exposes the existing authenticated meeting-creation dialog when no meeting is available. Admins can select a current attendance window, submit actual simulator arrival/departure scans and verify attendance before completing setup. Creating a meeting alone does not complete the input or attendance checks.

## Migration and configuration impact

- Migration `0029_web_updates.sql` adds operational update requests, concurrency guards and audit records. These records survive application data restore/delete. Reviewed forward migrations preserve attendance and roster data; D1 is never automatically restored.
- Existing private deployment repositories need the reviewed controller/workflow helper patch before the bridge. An application upgrade does not update that private checkout. Preserve its compatible package manifests, lockfile, installation configuration and history.
- Configure exact retained installation slug, D1 UUID and Worker URL as production variables. Store the separate repository-only fine-grained Actions-write token through secure provider interfaces, with ISO UTC expiry (ninety days by default where policy permits). The Worker holds the dispatch credential; it is absent from browser state, D1 backups and logs.
- The controller builds before maintenance, captures recovery metadata, verifies retained resources/secrets, applies reviewed compatible migrations, deploys API then Pages and verifies both. Maintenance suspends domain writes and returns retryable kiosk errors so scans remain queued. Authentication and reads stay available. No automatic code rollback or D1 restore occurs.
- Dependency versions are unchanged. Root release version/lock metadata alone changes to 0.24.0.

## Manual acceptance and limits

Publication does not upgrade any installation or Pi. Existing web version must be measured independently of the operator-confirmed v0.23.2 Pi. Before live deployment, rehearse supported baseline/provider behavior with synthetic data in an isolated installation. Exact v0.24.0/V1 fixed-workflow dispatch requires those official targets to be published; record it separately from local mocks and prepublication rehearsal.

Require authorized bridge acceptance: retained URLs, D1 identity, secret names, sign-in, roster/attendance and pairing; matching API/Pages version and health; actual root:root:755 helper `cmp`; normal/offline scans, pending-queue restart/replay, enrollment, reader, service restart and full reboot. Preserve secure backups and checkpoints. Stop on recovery-required and use reviewed, explicitly authorized recovery only after a known completed run and matching healthy releases.

Local implementation and integration checks passed. Final versioned-export release/browser/Linux gates and exact-public-commit GitHub CI remain required before tagging. Actual provider, existing installation and Pi acceptance are separate live checkpoints and are not claimed by these notes.
