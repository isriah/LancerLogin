# LancerLogin v0.7.0 — Verified integrations

This release replaces credential-presence checks with end-to-end provider verification, streamlines integration setup, and removes release-tag typing from the normal update path. It upgrades an adopter-owned LancerLogin installation in place and does not connect to or migrate any pre-LancerLogin attendance system.

## What changed

- Integration cards now distinguish **Not configured**, **Verification required**, and **Configured**. A configured card collapses to its title and status; opening it reveals rotation and removal controls.
- Google OAuth becomes configured after Google returns a valid identity for an active LancerLogin Admin.
- Resend sends a real six-digit code to an Admin-selected address. The code expires after ten minutes, and D1 stores only its SHA-256 hash while verification is pending.
- Discord validates the bot token and configured server, sends a button to the configured attendance channel, and becomes configured only after a user completes that signed interaction.
- Saved but unverified Resend and Discord credentials cannot power attendance communications, calendar synchronization, contests, or kiosk-status messages.
- Provider instructions place each value field directly after the step that tells the Admin to copy it. The Discord Interactions Endpoint URL instruction now leads directly from Copy to the matching Discord field.
- First-time saves say that credentials were saved; replacement language appears only for actual credential rotation.
- The five-week Home calendar subtly shades dates from earlier calendar months.
- **Install or upgrade LancerLogin** uses a dropdown. **Latest stable** is the default; **Original template release** provides a known fallback without typing a tag.

## Data migration and security

Migration `0007_integration_verification.sql` adds a verification timestamp and an expiring challenge table. Challenges store a hash, provider target, provider message identifier, expiry, and creating Admin—not an email code, Discord button token, roster data, attendance data, or biometric data. Pending challenges are not included in dashboard backups.

Existing saved integrations are intentionally marked **Verification required** after upgrade. Google is verified by the next successful active-user sign-in. Resend and Discord must be verified from **Settings → Integrations** before their operational workflows resume. Rotating any credential clears its earlier verification.

Entire-installation dashboard backups now use schema version 4. Versions 1–3 remain accepted and restore earlier integrations as unverified so they cannot silently regain provider access.

## Before upgrading

Download an **Entire installation** backup from **Settings → Updates**. In the private deployment repository, manually run **Install or upgrade LancerLogin**, choose **Upgrade**, keep **Latest stable** selected, enter the existing installation slug, and type the required confirmation. The dashboard does not store a GitHub credential and cannot dispatch the workflow automatically.

## Manual verification after upgrade

1. Confirm the rolling Home calendar shades only dates before the current calendar month.
2. Open **Settings → Integrations** and confirm each existing provider says **Verification required**.
3. Complete Google, Resend, or Discord verification for the providers your organization uses.
4. Confirm each verified card collapses to a **Configured** status and reopens for credential management.
5. For Resend, confirm the test code arrives only at the address entered for verification.
6. For Discord, confirm the verification message appears in the selected attendance channel and its button completes dashboard verification.
7. Confirm an unverified provider cannot send an operational attendance message.

## Known limits

- GitHub workflow dropdowns cannot dynamically enumerate release tags. Routine updates resolve **Latest stable** through GitHub Releases; arbitrary rollback tags require repository-maintainer intervention.
- A repository created from an older template keeps its original private workflow file because application upgrades never write to the adopter's GitHub repository. Its existing **latest** choice still installs v0.7.0 without typing an exact tag; the simplified two-choice form appears in new v0.7.0 template repositories or after the adopter deliberately copies the reviewed v0.7.0 workflow into the private repository.
- A fully rendered kiosk-screen simulator with manual fingerprint-event selection remains future work. The existing guided-setup simulator remains available for isolated test-meeting scans.
- No physical Raspberry Pi/R503 acceptance is claimed by this release.
