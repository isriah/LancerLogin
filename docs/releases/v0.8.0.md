# LancerLogin v0.8.0 — Roster polish and remote kiosk pairing

This release refines everyday dashboard layout and removes the need to type deployment details on a Raspberry Pi touchscreen. It upgrades an adopter-owned LancerLogin installation in place and does not connect to or migrate any pre-LancerLogin attendance system.

## What changed

- Roster members are now the primary page content. **Import roster** opens a focused dialog with merge/replace selection, local validation, a complete change preview, and explicit confirmation.
- Admins can add one roster member directly without preparing a CSV file. Existing dashboard-account linking remains below the roster directory.
- The redundant meeting-count card is removed; meeting success and error notices still appear when an action needs feedback.
- Routed pages share one vertical spacing system, and narrow layouts are covered by a real-browser overflow smoke test.
- Dashboard headings use the self-hosted Bebas Neue font and body content uses self-hosted Roboto. No font request leaves the installation.
- Dark mode uses neutral charcoal surfaces instead of olive-tinted panels. Organization primary and secondary colors remain the action and accent colors.
- Organization color controls accept hexadecimal or RGB values, synchronize numeric sliders, use rounded previews, and remain themed in dark mode. Logo contrast choices use the same themed controls.
- A fresh Pi installs and starts without requesting a Worker URL or OTP in its terminal. The dashboard creates one ten-minute pairing key containing the installation address, one-time code, and kiosk name.
- From a phone or laptop on the same network, an Admin opens the Pi's local setup address and pastes the key. The Pi redeems it, saves only the returned kiosk credential with owner-only permissions, clears the field, and closes the pairing panel.
- Remote LAN access is limited to the local pairing surface. Attendance, fingerprint enrollment, and slot mappings remain available only from the kiosk itself.
- CI adds focused Chromium smoke tests and actionlint as parallel jobs; the full typecheck, test, build, migration, and dependency gate remains required before release packaging.

## Data migration and security

No D1 migration is required. Existing meetings, attendance, roster, dashboard users, integrations, settings, and kiosk credentials are preserved.

The Worker API URL is public routing information, not a credential. It is embedded only in the time-limited pairing key so the Pi can find its adopter-owned Worker without a central discovery service. The underlying pairing code remains hashed in D1, expires after ten minutes, and is single-use. The combined key is not stored on the Pi; only the returned kiosk bearer credential is saved, and D1 stores only its hash.

The local service listens on the LAN so a phone or laptop can open the pairing page. Requests from another device cannot call attendance, enrollment, scanning, or mapping routes. Once paired, the pairing endpoint refuses another key.

## Before upgrading

Download an **Entire installation** backup from **Settings → Updates**. In the private deployment repository, manually run **Install or upgrade LancerLogin**, choose **Upgrade**, keep **Latest stable** selected, enter the existing installation slug, and type the required confirmation. The dashboard does not dispatch the workflow automatically.

An already paired v0.7 kiosk continues to work. To use the new local-network pairing flow on a fresh or replacement Pi, download and run the v0.8 installer after the dashboard upgrade.

## Manual verification after upgrade

1. Confirm Roster opens with the member directory first, and that **Import roster** and **Add member** each open a focused dialog.
2. Preview a CSV in merge mode without confirming it, then repeat in replace mode and review every proposed deactivation.
3. Confirm Meetings no longer shows a passive meeting-count card.
4. In **Settings → Organization**, test Hex and RGB color edits, logo contrast choices, light mode, and dark mode.
5. At a half-width browser window, confirm cards remain inside their parent panels and vertical gaps are consistent.
6. On a fresh Pi, run the installer and confirm it finishes without asking for a Cloudflare URL, kiosk name, or OTP.
7. From another device on the same network, open the printed `.local` or IP address, paste the dashboard pairing key, and confirm the Kiosks page reports the device online.
8. Confirm the phone/laptop cannot use the Pi's attendance, enrollment, scan, or mapping endpoints.

## Known limits

- `.local` discovery depends on the local network and Raspberry Pi OS mDNS support. The installer also prints the Pi's LAN IP address as a fallback.
- The full kiosk-screen simulator with manual fingerprint-event selection remains deferred. The existing guided test-meeting simulator remains available.
- Physical Raspberry Pi, display, UART, and R503 acceptance still requires the adopter's hardware test.
