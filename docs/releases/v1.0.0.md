# LancerLogin v1.0.0 - Community Edition

> Historical release note. v1.0.0 remains immutable release history, but v1.0.2 is the stable public release. The transition described below is complete; use the [current web-update guide](../WEB-UPDATES.md) for future maintenance.

## Release scope

This release establishes the Community Edition after the v0.24.0 bridge. It retains the same attendance, dashboard, kiosk, onboarding and guarded update behavior shipped in v0.24.0. No new work units or runtime features are added in this release.

Admins update the Dashboard through Settings → Updates: review the pinned official release notes, save the associated Entire installation backup, confirm it was saved, then start and track the fixed private GitHub Actions workflow. Progress survives reloads; reload the dashboard only after API and Pages independently verify the target release. The Physical kiosk is updated separately.

## Migration and configuration impact

- No additional D1 migration or dependency change beyond v0.24.0. Migration 0029 and the private update controller must already be installed by the bridge.
- Root release and lock metadata become 1.0.0; the public template's original-release selection pins v1.0.0. Existing private controllers retain their reviewed installation configuration and history.
- Existing installations must first bridge both web and Pi to v0.24.0. Confirm the actual installed helper, root ownership, fixed no-argument update service and installed version. If the Pi missed the bridge, use the checksum-verified exact-v0.24.0 bootstrap in [KIOSK.md](../KIOSK.md).
- Preserve existing D1 identity, URLs, pairing, pending attendance and encryption/session credentials. Keep private web/Pi recovery copies. No automatic database restore, resource recreation or credential rotation.
- Repository-scoped Actions-write credentials remain server-side with their configured expiration. GitHub approvals remain required wherever configured and supported.

## Verification and acceptance limits

Publication does not upgrade an installation. Automated release, browser, dependency-audit and Linux packaged-artifact checks must pass on the exact public candidate before tagging. Actual in-app V1 dispatch, deployment tracking and installed web/Pi acceptance require separate live authorization after the official release exists.

The existing installation's v0.24.0 web bridge passed API/Pages health and retained-data checks. The operator confirmed Pi v0.24.0, active service, helper ownership/replacement, fixed no-argument update service, touchscreen, reader test, maintenance PIN and retained fingerprint mappings. The operator chose to skip additional bridge normal/offline scanning, controlled pending-queue restart/replay, enrollment and reboot recovery tests. These tests are not claimed passed; earlier v0.23.2 operation and automated tests do not establish current physical replay acceptance.

Use [WEB-UPDATES.md](../WEB-UPDATES.md) for maintenance, dispatch ambiguity and deliberate recovery. Stop on recovery-required or mismatched releases; never restore an older pending queue or D1 automatically.
