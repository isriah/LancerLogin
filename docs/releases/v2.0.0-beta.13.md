# LancerLogin v2.0.0-beta.13

This beta is a security and reliability release. It closes several sign-in and dashboard proxy weaknesses, fixes Google Calendar connection, makes kiosk updates roll back automatically when a new release does not start, keeps offline kiosk scans safe in more failure cases and makes the dashboard keep working through brief connection problems. It also adds a local development loop and an author guide for module plugins. Installations must update three workflows in their private deployment repository before updating, as described below.

## Bugs fixed

- The dashboard's API proxy no longer forwards requests whose path starts with a doubled slash or a backslash (for example `/api//other-host/`) to another host with the visitor's cookies. Such requests are refused. Dashboard pages also can no longer be embedded in another site's frame.
- Connecting Google Calendar in **Settings > Integrations** now completes. Google's return to the dashboard was previously refused because it does not carry the sign-in cookie.
- A Google sign-in or Calendar connection request can no longer be used as a sign-in session, and a session can no longer be used as either request.
- Many simultaneous wrong passwords can no longer get past the account lock. Five failures lock the account for 15 minutes. Local sign-in, first-Admin setup and kiosk pairing are also limited per network address.
- The first-Admin setup code now works only once. After **Delete installation**, only the browser that deleted it can run setup again with the same code, within one hour; otherwise set a new setup code as described in [bootstrapping](../BOOTSTRAPPING.md). Running setup again after **Delete installation** also no longer fails with a database error.
- Signing out, an Admin password reset and deactivating a member now end that member's existing sessions. A password reset also clears an account lock. Existing sessions stay signed in when this release is installed.
- Unexpected errors no longer show internal error messages to signed-out visitors. They show a short error reference that matches the server log instead.
- Restoring meetings from a backup no longer disconnects them from their Google Calendar and Discord events, so the next sync no longer creates duplicate events. Meetings missing from the backup are still removed, and the restore reports how many calendar links were dropped with them.
- **Delete installation** now also removes plugin data, so it cannot reappear after the next first-Admin setup.
- A restore too large for Cloudflare D1's limits now says that nothing was changed and suggests restoring by category, instead of a general failure.
- Recording or correcting scans during a meeting no longer makes every kiosk download the roster again. Kiosks download it only when the roster itself changes.
- Creating or editing meetings reads far fewer older meetings when checking for overlaps, and saving branding repeats that check only when the late-scan window grows.
- A correction for a member or meeting that does not exist now reports that clearly, and a correction for a deleted meeting is refused.
- A plugin whose database update failed is retried after a minute instead of waiting for the next scheduled pass.
- A kiosk update that fails to start now rolls back to the previous release automatically, including its system services and update helper. A kiosk whose clock is wrong by up to several days can still update, and a kiosk update request cannot be replayed. Kiosks install only immutable releases whose files match GitHub's published checksums, and stalled downloads time out.
- A kiosk that starts without a network connection now shows a "Starting attendance" page and opens attendance once its service is ready, instead of leaving the bare desktop.
- An unexpected server response no longer makes a kiosk discard queued scans. The kiosk keeps them and tries again later.
- Kiosks save offline scans with much less writing to the SD card, keep them safe through power loss, and clear old acknowledged rejected scans after 30 days or beyond 1,000 records.
- A kiosk now answers only requests addressed to its own name or address, keeps PIN lockouts across restarts, and removes old unpair archives after re-pairing or 30 days.
- The dashboard keeps open pages and unsaved work when module information briefly fails to load, and shows a notice instead. **Settings > Updates** stays available when the dashboard and server versions differ, so an Admin can finish an update.
- A failure inside one page or plugin now shows an error for that part only, with a way to reload, instead of a blank dashboard.
- Reopened attendance setup can be closed, and leaving unfinished setup defers it in the same way as **Finish setup later**.
- First-Admin setup no longer stops responding after a network or server error, and sign-in tells too many attempts and server errors apart from a wrong password.
- The dashboard checks for module and update changes less often and pauses those checks in hidden tabs.
- Older installation and update workflows that do not include plugins now stop before changing anything, instead of building a dashboard without the installation's modules.
- Deployment secrets are now given only to the workflow steps that need them, so dependency installation, plugin composition and builds never receive them.
- A dashboard update that is cancelled or times out before database changes start now clears maintenance and reports that nothing was changed.
- A plugin change is reported healthy only after the new Worker and dashboard are both live with exactly the selected modules.
- Plugins can no longer read the Worker's secrets through Cloudflare runtime imports, the optional plugin token is sent only to GitHub and allowlisted plugin hosts, and code a plugin ships can no longer depend on development-only packages.
- Tests that create temporary Git repositories no longer change the checkout they run in when started from a Git hook.

## Features added

- A local development loop for module plugins. `npm run plugins:dev -- --plugin ../my-plugin` composes a plugin folder with the same checks a pinned plugin gets, runs the API and dashboard locally and recomposes when plugin files change.
- A plugin author guide, [PLUGIN-AUTHORING.md](../PLUGIN-AUTHORING.md), and a [plugin template repository](https://github.com/isriah/lancerlogin-plugin-template) to start a new plugin from.
- `npm run check:quick` typechecks the changed workspaces and runs the fast tests for the changed files, usually in seconds. An optional pre-push hook runs it (`npm run hooks:install`).

## Features removed

None.

## Required actions

1. **Update the deployment workflows first.** Before preparing this update, replace `.github/workflows/provision-template.yml`, `.github/workflows/upgrade-web.yml` and `.github/workflows/refresh-web-update-credential.yml` in the private deployment repository with the versions from this release, and commit them to `main`. The new versions give secrets only to the steps that use them and run on Node.js 24.22.1 (`provision-template.yml` and `refresh-web-update-credential.yml` previously used Node.js 22). This release's build refuses to run in GitHub Actions unless the installation's plugins were composed first, so an installation or update workflow from before LancerLogin 2.0 stops at its build step, before any database change or deployment, with a message naming these workflows. Then prepare the update in **Settings > Updates** as usual.
2. **Kiosks.** Update the dashboard first, then update each kiosk with **Update kiosk** on the Kiosks page. The first update moves the kiosk to versioned release directories under `/opt/lancerlogin/releases/` and keeps the previous release for automatic rollback. After that, an installer from an older release cannot install over it; use **Update kiosk**. Pairing an unpaired kiosk from another device on the network now needs the six-digit setup code shown on the kiosk's own screen. Pairing on the kiosk itself needs no code. See [kiosk](../KIOSK.md).
3. **Signing out signs out every device.** Signing out now ends all of that member's sessions on every device, and an Admin who resets their own password is signed out.
