# LancerLogin v2.1.0-beta.12

This beta makes the calendar connections harder to break and adds a shared Notion connection for plugins. Saving the Discord bot's credentials again, for example after a token reset, or removing Discord and setting it up again, no longer creates a second Discord event for every meeting. When Discord refuses every request, because the token was reset, the bot was removed or a permission is missing, LancerLogin now pauses Discord's calendar work and resumes it by itself instead of failing each event in turn, and the Discord card gets **Retry failed delivery**. **Settings > Integrations** loads again when saved credentials can't be read, the Google Calendar card says when its authorization has ended, and the confirmation for disabling Attendance says which calendar events stay behind. Reports, the Leaderboard and the Roster's attendance rates take less processing time on the Free plan. A new **Notion** card holds one Notion connection that plugins built for it can use; the included modules don't use it yet.

## Bugs fixed

- **Saving Discord credentials again no longer doubles calendar events.** Saving the **Discord bot** credentials again, for example after a bot token reset, made LancerLogin forget which Discord events it had created, so the next delivery created a second event for every meeting. Removing the integration and setting it up again did the same, and an event being created at that moment was left unlinked. Credentials for the same server now keep the events and any changes still waiting to be sent: nothing is sent until you verify again, and verifying updates the events that are there. Setting up the same server again after **Remove integration** links each event to its meeting again. For credentials for a different server, see Features added.
- **Discord calendar work waits out a refusal.** When Discord refused every request, because the bot token was reset, the bot was removed from the server, a permission was missing or Discord was rate limiting, each queued event was sent and refused in turn and many were failed for good, and a delete refused because Discord couldn't find the server was counted as done although the event was still there. LancerLogin now holds the Discord queue instead: for 15 minutes after a rejected token, a server the bot can't find or a missing permission, and for as long as Discord asks after a rate limit (one minute to an hour). A missing permission holds only the kind of work Discord refused, creating and updating events or removing them. Nothing is given up: the card counts the refused event as needing another attempt with Discord's reason, and the queue is tried again by itself when the hold ends.
- **An event created during a deletion is removed.** A Discord event that Discord was creating at the moment **Meetings and attendance** was deleted in **Settings > Data**, or a meetings backup was restored, stayed on the server with nothing in LancerLogin pointing at it. It is now removed like the meeting's other events.
- **Settings > Integrations loads when saved credentials can't be read.** When the saved Discord credentials could no longer be decrypted, for example because the installation's encryption key was replaced or a backup was restored onto an installation with another key, the Integrations page failed to load. It now loads, the card shows **Saved, but can't be read**, and **Replace credentials** fixes it. The same applies to Google sign-in, Google Calendar and Resend: an action that needs those credentials now says they can't be read instead of failing.
- **The Google Calendar card shows when authorization has ended.** After Google refused the authorization, the card's status still said **Configured**; it now says **Re-authorization required**. When Google gives an authorization an end date, the card now also shows this once that date passes, before a delivery fails. This works for authorizations made with this release or later; choose **Re-authorize Google Calendar** once to get it for an existing one.
- **Deleting meetings no longer leaves Google Calendar deletes that can't succeed.** Deleting a meeting whose Google Calendar event had never been created, for example while the authorization had ended, queued a delete that failed and stayed on the card as needing another attempt until an Admin retried it. Nothing is queued now for an event that was never created, and its waiting create is dropped, so the event can't appear later. A create that failed with an error LancerLogin retries is still followed by a delete, because Google may have made the event anyway.
- **Meeting saves and allowance changes can't overlap meetings.** Saving a meeting at the same moment as a change to **Early arrival allowance** or **Late scan allowance** (in **Settings > Modules > Attendance > Meeting configuration**, or in Attendance setup) could leave two meetings' attendance windows overlapping. The change that arrives second is now refused with the usual message naming the meetings.
- **A meeting import committed twice at once no longer fails.** With Discord connected, committing the same meeting CSV import twice at the same moment, with rows that only update a meeting's notes, attendance or audience, could answer with an error or leave a meeting with no Discord event until the next **Sync all meetings**.
- **Reports keep working after one stopped request.** On the Free plan, after one report request was stopped for using too much processing time, the **Leaderboard** and other attendance reports could fail on every load for about five minutes.
- **Reports take less processing time.** Attendance reports, the **Leaderboard**, the attendance rates on **Roster** and custom reports in **Reports** now do the same work in less processing time, much less when the same data is opened again, and the Leaderboard and Roster download far less data. Results are unchanged.
- **Check again on Settings > Updates keeps its answer.** After **Check again** under **Setup status**, a status refresh sent just before the check answered could show the rows' old state again for up to 10 seconds.
- **Smaller fixes.** Previewing a meeting change, a meeting CSV import, or a label or Discord role sync no longer starts background work that has nothing to do.
- **Documentation.** New sections cover the Notion connection, what happens to Discord events when the bot's credentials are replaced or point to another server, Discord's calendar hold, and what **Saved, but can't be read** means and how to fix it.

## Features added

- **A shared Notion connection.** A new **Notion** card in **Settings > Integrations**, after Discord, holds one Notion connection that any module built for it can use, for example a plugin that adds rows to a team's ordering database. An Admin creates an internal integration in Notion, pastes its token into **Integration token** and chooses **Save**; LancerLogin checks the token with Notion, stores it encrypted and never shows it again. The card has an on/off switch, **Check** and **Remove**, shows for each of Notion's five capabilities what LancerLogin has seen (**Working**, **Refused by Notion** or **Not used yet**), and under **Databases** lists each database an installed module asks for, with **Save database** and **Clear**. Modules never see the token, can use only the databases an Admin chose for them, and receive people's email addresses only when they declared that they need them. When Notion asks LancerLogin to slow down, every module waits. Entire-installation backups carry the encrypted token and the chosen databases; older backups restore with no Notion connection. None of the included modules uses Notion yet, so the card says **No installed module uses Notion yet.**
- **Retry failed delivery on the Discord card.** The Discord card's **Calendar delivery** panel now has **Retry failed delivery** beside **Sync all meetings**, as the Google Calendar card does. It makes failed events and set-aside removals due again, ends a hold at once and says how many events it queued.
- **Moving Discord to another server.** Saving credentials for a different Discord server now says how many events LancerLogin created on the previous server are still there. After you verify the new server, LancerLogin removes them from the previous one if the bot can still reach it; an event it can't remove is recorded in the audit log for you to delete in Discord. Saving credentials for the previous server again, for example after correcting a mistyped server ID, links its events to their meetings again instead of creating new ones.
- **Disabling Attendance says what stays on the calendars.** While Attendance is disabled nothing is sent to Google Calendar or Discord. **Confirm module disable** in **Settings > Modules** now says how many events of each connected provider are waiting to be removed and how many events of current and upcoming meetings disabling leaves in place, and that they must be deleted by hand if Attendance isn't enabled again within 7 days. With nothing left behind it reads as before.
- **For plugin authors:** module SDK 1.8.0 adds `services.notion`, which reads and writes the Notion databases an Admin chose for the plugin through Core's connection, and `NotionBindingField` for choosing them on a plugin's own setup page. SDK 1.7.0 adds read-only Attendance day projections for module jobs (`meetingsOnLocalDate`, `presentMembersForDay` and `expectedMembersForDay`) and `listActiveRosterWithLabels`.

## Features removed

None.
